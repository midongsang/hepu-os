# 挂载策略定案（D1）

> 2026-11-23。结论：**懒加载是正式语义，全量扫描降级为调试模式。**

## 为什么不是启动全量建树

- 32 位 IDE 走 PIO，全量遍历所有目录 + 读所有 inode 是秒级开销，启动变慢
- 每个节点常驻内存，几千个 inode 就是持续占用
- 启动后盘上内容再变，内存树无法感知，反而制造“内存与磁盘不一致”
- fsck 必须面对裸盘，全量建树会把它和挂载顺序绑死

## 正式语义

1. 路径解析统一走 `vfs_find` / `vfs_open` 内部触发的懒加载；
2. 目录内容按需从盘上读（`vfs_readdir` → `ext2_readdir_ino`）；
3. 根节点 `inode_num = 2` 由懒加载路径在第一次解析时补上；
4. 任何会改动磁盘的 VFS 操作，必须先解析出真实节点再执行。

## 调试模式：`fs mount -f`

```
fs mount        # 只挂底层 ext2，不建内存树（正常路径）
fs mount -f     # 全量扫描根目录一层到内存树，仅用于调试/对比
```

`ext2_mount()` 已保证**幂等**：同名子节点存在则跳过。
实测（`/mountfull_test` 标记触发）：

```
[MOUNTFULL] rc1=0 rc2=0 children=1/21/21 RESULT: PASS
```

第一次从 1 个已有子节点扩到 21 个，第二次仍为 21 —— 没有重复挂载。

## 不做什么

- 不把 `ext2_mount` 接进启动流程；
- 不做递归全盘建树（只建根目录一层，和现有实现一致）；
- 不在懒加载路径里做“预读整棵子树”。

## 缺口

- 盘上内容在运行中被外部修改时，已缓存的节点不会失效；当前靠“重启后树是新的”规避。
- 目录节点的 `mtime` 已记录但没有用于失效判断，后续需要时再加。
