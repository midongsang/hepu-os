# 赫普OS BUG修复规范（V1.0）

## 目的
避免修复过程中的错删、误判、反复折腾，确保每次修改都有充分证据和验证。

## 修复流程

### 1. 问题确认（Evidence First）
- [ ] 收集完整日志（串口输出、崩溃帧、寄存器状态）
- [ ] 确认问题现象（哪个应用、什么操作、什么错误）
- [ ] 确认问题可复现
- [ ] **禁止**在没有证据的情况下猜测原因

### 2. 根因分析（Root Cause Analysis）
- [ ] 基于日志和代码分析根本原因
- [ ] 验证分析结论（通过反汇编、栈布局计算等）
- [ ] 区分"直接原因"和"根本原因"
- [ ] **禁止**在没有验证的情况下修改代码

### 3. 修复方案（Fix Plan）
- [ ] 明确修改的文件和行号
- [ ] 说明修改的原因（基于什么证据）
- [ ] 评估修改的影响范围（是否影响其他功能）
- [ ] 准备回退方案（如果修改失败）

### 4. 实施修复（Implement）
- [ ] 只修改必要的代码，不做无关修改
- [ ] 保留原代码的注释（如果原代码正确，不要删除注释）
- [ ] 添加新注释说明修改原因
- [ ] **禁止**删除可能正确的代码

### 5. 验证测试（Verification）
- [ ] 编译通过（无警告、无错误）
- [ ] 启动QEMU验证
- [ ] 确认问题已修复
- [ ] 确认没有引入新问题（回归测试）
- [ ] **禁止**在没有验证的情况下宣布修复成功

### 6. 文档记录（Documentation）
- [ ] 记录问题现象、根本原因、修复方案
- [ ] 记录验证结果
- [ ] 更新BOOTLOADER_BUG_HISTORY.md
- [ ] **禁止**不记录就结束

## 关键原则

### 证据优先
- 所有结论必须基于日志、反汇编、栈布局计算等证据
- 不确定时，先添加调试输出收集证据，不要猜测

### 最小修改
- 只修改确认有问题的代码
- 不要"顺便"修改其他代码
- 保留原代码的结构和注释

### 验证闭环
- 每次修改后必须编译+运行验证
- 验证失败时立即回退，不要继续叠加修改
- 验证通过后记录结果

### 回退机制
- 每次修改前确认可以回退
- 修改失败时立即回退到上一个稳定版本
- 记录回退原因

## 常见错误防范

### 1. 栈布局计算错误
- pusha压入顺序：EAX,ECX,EDX,EBX,ESP,EBP,ESI,EDI（高地址→低地址）
- 因栈向下增长，从低地址到高地址为：EDI,ESI,EBP,ESP,EBX,EDX,ECX,EAX
- **每次计算后用反汇编验证**

### 2. 偏移量计算错误
- 逐参数push时，esp递减4，偏移量需同步补偿
- **每次修改后用调试输出验证参数是否正确**

### 3. 误判正确代码为错误
- 原代码经过验证正常工作时，不要轻易修改
- 如果怀疑原代码有误，先添加调试输出确认
- **禁止**在没有证据的情况下修改经过验证的代码

### 4. 反复折腾同一处代码
- 如果同一处代码修改超过2次，停下来重新分析
- 可能问题不在这处代码，而在其他地方
- **禁止**在同一处代码上反复修改而不重新分析
