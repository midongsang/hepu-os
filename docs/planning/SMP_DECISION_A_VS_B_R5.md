## 一、背景：现状「骑墙」的具体危害

### 1.1 什么是「骑墙」

当前内核同时具备两种互相矛盾的特征：

- **有 SMP 外形**：`smp.c` 存在完整 AP 上电路径（trampoline → `ap_c_entry` → LAPIC 使能 → 定时器 → `sti`），`spinlock.c` 有一份自旋锁实现，QEMU `-smp 2/4` 下 AP 会被启动并在线；
- **无 SMP 内核**：绝大多数临界区仍靠全局 `cli/sti` 关中断与全局变量冒充 per-CPU；无 TLB shootdown、IPI 是空处理、per-CPU 存储缺失（详见计划文档 1.2/1.3/1.4 节，附录 A 已逐条复核）。

结果是：系统**既不是经过验证的完整 SMP，也没有显式声明自己是单核**。AP 在线、收中断、跑 idle 循环，但共享状态没有跨核互斥，等于把并发故障以随机概率埋进每一次多核启动。

### 1.2 最严重的一条：PMM 无锁，同一物理页帧可被分给两个进程

- 证据：`kernel/arch/x86_64/pmm64.c:223-254`（`pmm64_alloc_page`）、`260-271`（`pmm64_reserve_range`）、`274-294`（`pmm64_free_page`）、`297`（`pmm64_alloc_pages`）；位图定义 `pmm64.c:122`。
- 触发条件：任一核在分配/释放/保留页帧的窗口内，另一核扫位图命中同一空闲位（单核下串行执行不会发生；多核下随调度与中断节奏随机出现）。
- 后果：同一物理页帧被同时挂进两个进程的页表；两进程各自写入，互相覆盖对方数据；`used/free/next_free/alloc_count` 计数错乱，`reserve_range` 与分配交叉时已保留页可被再发出。
- 可观测症状：用户态数据随机损坏、进程间出现不属于自身的内存内容、auxv/栈上出现疑似内核地址、内存计数单边漂移；**故障高度随机、跨核交叉踩内存，事后从单条栈回溯几乎无法定位**。

### 1.4 为什么「骑墙」比「明确单核」更危险

| 对比维度 | 明确单核（可预期降级） | 骑墙（现状） |
|---|---|---|
| 并发假设 | 代码内只有一个执行流，临界区由 `cli/sti` 串行化，行为可推理 | 有时像单核（AP 不调度），有时又有多核中断/AP 后台活动；假设随启动核数漂移 |
| 故障可预测性 | 出问题可沿单条执行流回溯；降级边界清晰 | 故障由两核时序窗口触发，复现概率随机，需要 `-smp` 压测与取证环境才能抓到 |
| 对外承诺 | 可在启动日志与文档中明确「单核」，上层不期待并行度 | 看起来支持多核，用户/测试容易按多核预期使用，故障预期被错误放大 |
| 调试成本 | 低 | 高：跨核踩内存、TLB 残留、栈串栈均属最难定位的一类 |

一句话：**不确定性比可预期的降级更危险**。明确单核是主动收窄能力边界；骑墙是把未完成的并发安全暴露成随机故障。

### 3.2 单核正确性论证：为什么现有代码在单核下基本安全

- **现有「锁」的实质是全局关中断**：临界区靠 `cli` 保存 RFLAGS → 关中断 → 操作 → 按原 IF `sti` 恢复（例：`gfx64.c:557-591`、`kheap64.c:63-87`）。在单核环境下，关中断阻止了本核中断抢占，临界区不会被第二个执行流插入；`kheap64.c` 的原子交换自旋是当前唯一较完整的中断安全临界区，堆链表在单核串行路径下结构自洽。
- **无跨核并发写者**：所有全局表（进程表、fd 表、TCP/UDP/IP、ext2、图形/窗口）在单核下只有一个执行流按序访问；1.3 节列出的双发、双槽、计数丢失、TLB 残留等故障，触发前提都是「第二个核同时操作」，单核下该前提不成立。
- **中断与主流程串行**：中断在 `cli` 保护的临界区外抢占，处理完返回；单核下不存在两核同时进同一临界区。

**必须诚实指出：单核也修不好的问题**

| 残留问题 | 说明 | 证据/位置 |
|---|---|---|
| 中断 reentrancy / 不可重入路径自伤 | 单核只消除跨核并发，**不消除中断与主流程交叉进入同一非重入路径**。若中断处理程序在主流程持有堆/PMM 状态时再次进入分配/释放，仍可能破坏链表或位图。本轮需把「中断上下文不得调用非重入分配路径」作为核对项，而非自动修好 | 计划文档 1.2 节；PMM `pmm64.c:223-294`；堆 `kheap64.c:38-59` |
| 数据结构自身的单线程缺陷 | 表槽泄漏、未初始化字段、fd 串槽等单线程 bug 与核数无关，单核下仍会出现；主机 6 项测试与 QEMU 单核心回归继续兜底 | 现有主机测试基线 |
| FPU 保存区槽位不足 | 8 槽、下标 `& 7`（`lib64.c:346,614`）在单核心不触发（只有 BSP 用 0 号槽），但缺陷仍在；若未来在同一镜像上临时放开多核 >8 核会立即踩到 | `lib64.c:613-615` |
| 各类竞态的单线程时序版 | 退出复位与使用撞车、缓存槽回收时机等，单核下概率大降，但依赖顺序保证的路径仍需回归观察 | 计划 S7/S14 |

### 3.3 迁移代价：以后再做 SMP 要推翻/重做的部分

| 后续成本项 | 量化说明 |
|---|---|
| 移除单核断言与跳过逻辑 | B1/B2/B3/B4/B5 中约 20–40 行断言/守卫需在 A 落地时摘除；属一次性成本，摘除前须确认对应 SB 条目已上线 |
| per-CPU 机制仍从零开始 | B 不引入 GS 基址、每核栈、每核 TSS/IST；阶段 3（SB-17/18/19/20，245–390 行）工作量不因 B 减少 |
| 测试矩阵重跑 | 单核期间的 QEMU 单核心/主机测试结果不能替代多核回归；进入 A 的阶段 2/4 时需按 2.4 节重新跑 `-smp 2/4/8` 压测 |
| 文档与对外承诺回填 | 单核日志/横幅/文档表述需在 A 验收后改回多核支持口径 |

> 结论：B 不阻塞 A。B 加的断言是「护栏」，A 每落地一条对应能力后逐段拆除；B 期间形成的单核回归基线对 A 阶段 1/2 的单线程不回归验证仍有效。

### 3.4 显式单核对用户的可观测承诺

- 启动日志固定打印 `[SMP] single-core mode (AP disabled)`，并在横幅标明在线核数为 1；
- 检测到多核固件/`-smp>1` 时，打印降级提示 `[SMP] multiple cores detected but single-core build: AP disabled`，明确拒绝启用 AP，而非静默在线；
- 自检/诊断输出按单核口径统计中断计数与 tick；
- 崩溃提示（若 AP 路径被意外进入）直接给出 `[PANIC] AP entry reached in single-core build`，便于识别构建与预期不符。

## 五、推荐与理由

### 5.1 推荐结论

**推荐选项 B（显式单核声明）先行止血，真机闭环跑通后，再按计划分阶段执行选项 A。**

理由（按优先级）：

1. **先让真机跑通一条链路**：当前尚无真机闭环验证（串口取证、AHCI IDENTIFY、网卡覆盖等待确认），并行度收益在真机上无法体现；在链路未打通前投入阶段 3/4 的高并发改造，风险与收益不匹配。
2. **稳定性优先于并行度**：骑墙状态把随机跨核故障埋在每次多核启动里；B 以 25–55 行守卫把能力边界收窄为可预期的单核，先消除不确定性。
3. **SMP 硬化是纯收益但会推迟闭环**：A 的阶段 3/4 涉及入口汇编、per-CPU、IPI 与 TLB 闭环，验收依赖多核压测与真机取证；在这些条件就位前强行推进，只会把稳定性问题后置到更难定位的阶段。
4. **B 不阻塞 A**：B 的断言是一次性护栏，A 逐条落地后摘除；B 期间的单线程回归基线对 A 的阶段 1/2 仍有效。

### 5.2 推荐执行顺序

1. **第一步（B 止血）**：按 3.1 节 B1–B7 加单核守卫与降级日志；跑主机 6 项 + QEMU 单核心回归；版本口径不变。
2. **第二步（真机闭环）**：在单核口径下打通真机启动、串口取证、存储/网卡基本链路，补齐当前缺失的真机验证能力。
3. **第三步（A 分阶段）**：阶段 1（原子/输出）→ 阶段 2（表级粗锁）→ 阶段 3（per-CPU/栈/TSS）→ 阶段 4（IPI/shootdown/队列）；每阶段以计划文档退出准则验收；SB-25 放开 AP 调度单列评估。
4. **护栏摘除**：A 对应条目上线并验收后，逐段摘除 B 的断言与跳过逻辑（标注为一次性成本，不保留双口径长期并存）。

### 5.3 若坚持先做 A 的前置条件

在以下条件全部就位前，不建议直接进入 A 的阶段 3/4：

- 真机串口取证与现场 dump 能力可用，能在 `#GP/#DF/#SS` 时拿到栈与寄存器；
- QEMU `-smp 2/4/8` 冷启动与并发压测环境可重复执行（2.4 节配方）；
- 已接受阶段 3/4 的回退预案：每步可独立回到全局数组 + BSP 单栈 + 本地 `invlpg` 现状；
- 有人日缓冲：高风险阶段按 2.1 节系数 2.0 估算，预留返工时间。
