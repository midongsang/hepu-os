# 多架构移植可行性评估

登记日期：2026-11-18
评估基线：`c9c8f6f`（main）

## 1. 现状：只有 x86 两条腿

`kernel/arch/` 下只有 `x86`（i386）与 `x86_64`（长模式），共用同一份桌面代码。
引导路径是 **UEFI-only**：`tools/hepboot/uefi` 产出 `BOOTX64.EFI`，经 GOP 取帧缓冲、
`ExitBootServices` 后跳转内核。全仓库没有任何 ARM / RISC-V / LoongArch 的执行代码。

`kernel/arch/x86/apk_parser.c` 里出现的 `lib/arm64-v8a/libnative.so` 只是解析 Android APK
时匹配包内路径的字符串，不构成 ARM 支持。

**这条对选型有硬约束**：目标平台必须有可用的 UEFI 固件，否则现有整条引导链（菜单、
加载屏、`0x6000` 帧缓冲描述块、`0x6010` HLDY magic）全部要另做一套。

## 2. 可移植性分层（实测规模与耦合）

| 层 | 文件/行数 | x86 硬耦合 | 移植结论 |
|---|---|---|---|
| `arch/x86_64` | 171 / 92,153 | 全部架构相关 | **必须重写** |
| `arch/x86` | 133 / 68,910 | 全部架构相关 | **必须重写**（且 ARM 侧没有对应 32 位模式） |
| `drivers` | 66 / 19,751 | 部分（端口 IO、e1000、PS/2、UHCI） | 型号需替换，框架可留 |
| `net` | 42 / 13,768 | 几乎无 | **直接复用** |
| `fs` | 31 / 9,015 | 几乎无 | **直接复用** |
| `services` | 16 / 3,019 | 无 | **直接复用** |
| `user` | 124 / 21,676 | 用户态，重编译即可 | **源码复用** |
| 桌面层 | 见下 | 近乎为零 | **几乎直接搬** |

桌面层逐文件实测：

| 文件 | `__asm__` | `cpuid` | `rdmsr/wrmsr` | 端口 IO |
|---|---|---|---|---|
| `hpdesk.c` | 2 | 0 | 0 | 0 |
| `gfx64.c` | 5 | 0 | 0 | 0 |
| `ttf64.c` | 0 | 0 | 0 | 0 |
| `cursor64.c` | 0 | 0 | 0 | 0 |
| `l10n64.c` | 0 | 0 | 0 | 0 |

**结论：桌面这一层（含自研 TTF 光栅化、中文字体、窗口系统）是最不依赖架构的部分。**
移植的真实成本在 arch 层与驱动型号，不在 UI。

全仓库 x86 硬耦合量：`__asm__` 命中 113 个文件、`cpuid` 16、`rdmsr/wrmsr` 20、
端口 IO（`outb/inb`）71、`lgdt/lidt` 9。

## 3. 候选平台（按 UEFI 可用性筛选）

### ARM64 / AArch64 —— 第一梯队

| 类别 | 芯片/板 | 关键点 |
|---|---|---|
| 服务器 | 飞腾（FT-2000+/S2500 系列）、鲲鹏 920、Ampere Altra、AWS Graviton | 服务器级 ARM 通常自带 UEFI + ACPI，最接近现有引导链 |
| 开发板 | Rockchip RK3588S（8 核 2.4GHz、NPU 6 TOPS，**支持 UEFI Boot**） | 便宜、生态活跃，适合做第一块目标板 |
| 开发板 | Radxa Dragon Q8B（**标准 UEFI 启动**、内置默认设备树、可从统一 ARM ISO 起） | 厂商明确写支持标准 UEFI，减少固件改造 |
| 开发板 | 飞腾派（ARMv8 四核：2×FTC664 1.8GHz + 2×FTC310 1.5GHz，开源硬件） | 国产开源硬件，资料开放 |
| 开发板 | 树莓派 5 | UEFI 需第三方固件，非原生，优先级低 |

### RISC-V 64 —— 第二梯队

| 芯片 | 关键点 |
|---|---|
| 算能 SG2042 | 64 核 RISC-V @2GHz、64MB 系统缓存、32 条 PCIe，适合做多核压力验证 |
| SpacemiT K3 | 8×X100 + 8×A100，130 KDMIPS / 60 TOPS；**其 SDK 明确包含 OpenSBI + U-Boot/UEFI** |
| 通用 | Armbian 已有 `uefi-riscv64` 板型，说明 RISC-V 的 UEFI 路径可走通 |

### LoongArch64 —— 第二梯队

| 芯片 | 关键点 |
|---|---|
| 龙芯 3A6000 | 龙芯《统一系统架构规范》V4.2 明确支持 **UEFI 固件 + ACPI**；固件可选 PMON / Kunlun / ByoCore / UEFI |
| 龙芯 3B6000M | 同上，已见与开源鸿蒙的适配新闻 |

## 4. 每条路的最小可启动集

| 能力 | ARM64 | RISC-V64 | LoongArch64 |
|---|---|---|---|
| 固件 | UEFI（BOOTAA64.EFI） | UEFI（部分板）/ OpenSBI + U-Boot | UEFI（规范明确） |
| 串口 | PL011 / 厂商 UART | 16550 兼容或 SBI console | 16550 兼容 |
| 帧缓冲 | UEFI GOP（与现有 `0x6000` 描述块同构） | GOP（板级差异大） | GOP |
| 中断 | GICv2/v3 + 异常级别 EL1 | PLIC + CLINT | 龙芯 ICU + 定时器 |
| 定时 | CNTPCT/CNTV | mtime/mtimecmp | 恒定计数 |
| 页表 | 4 级（可选 39/48 位） | Sv39/Sv48 | 三级映射 |
| 上下文切换 | `sp_el0`/`elr_el1`/`spsr_el1` | `mepc/mstatus` | `csr` 类寄存器 |
| 内存管理 | 需重写（现有 `pmm64` 与 x86 页表强绑） | 同 | 同 |
| ELF 加载 / 调度 / 文件系统 / 网络 / 桌面 | 全部可复用 | 全部可复用 | 全部可复用 |

## 5. 工作量排序（按"新写 arch 层 + 换驱动型号"估）

| 路线 | 新写规模（估） | 主要难点 | 建议优先级 |
|---|---|---|---|
| ARM64 | arch 层约 3–4 万行（可参照现有 92K 的设计，但不是抄） | GIC/EL 切换、页表、GOP 在某些板不保证 1920×1080 | **P0，首选** |
| RISC-V64 | 相近 | 板级 GOP/PCIe 一致性差，驱动生态弱 | P1 |
| LoongArch64 | 相近 | 固件与 ACPI 实现差异、外围驱动少 | P2 |

**注意：ARM64 上不存在"32 位兼容模式"这条退路。** 现有"32 位 i386 + 64 位长模式共用桌面"
的双架构卖点，在 ARM 上要么重新定义为"AArch32 + AArch64"，要么放弃。

## 6. 建议的推进方式

1. **先做架构抽象层，再做第二个架构**。当前 `hpdesk.c` 直接包含 `<arch/...>` 的东西，
   先把"帧缓冲提交、rdtsc、中断开关、临界区、端口访问"抽成 `hal_*` 接口，
   让桌面只依赖 `hal`。这一步在 x86 上是零风险重构，且是后续任何架构的前置。
2. **ARM64 从 QEMU `virt` 起步**（有 UEFI 固件、GOP 可用），先打通 M0：
   UEFI 引导 → EL1 → 页表 → 串口 → 帧缓冲清屏。
3. 再上真板（建议 RK3588S 或 Dragon Q8B，前者便宜、后者官方声明标准 UEFI）。
4. RISC-V / LoongArch 等抽象层成型后再评估，届时代价会降一个数量级。

## 7. 风险与前提

- **UEFI GOP 分辨率不保证**。现有展示页全部按 1920×1080 拍，ARM 板上可能只有 1280×720
  甚至 1024×768，UI 缩放档位需要重测。
- **无真机验证只能算半成品**。这台机器上只能跑 QEMU（`qemu-system-aarch64 -M virt`），
  真板的 GOP、PCIe、USB 行为都不同。
- **现有 32 位文本模式遗留（OBS-06）不会自动消失**，但 ARM 侧是全新代码，没有这个包袱。
- 本评估只盘点"能不能"，不含具体排期与人力评估。
