# Hepu 模块化设计准则 (xiulihe 原话记录)

## 定性
设计上模块化潜力很强，工程上还没成型。目前属于「纸上架构」阶段。

## 天生优势（架构自带）
1. **隔离域是最高模块边界**：比 Linux ko 粒度强——域=资源+地址空间+DMA+IPC全套隔离
2. **设备模型按能力抽象**：上层不关心后端是原生驱动/UIO/Linux代理沙箱
3. **兼容层是独立上层服务**：不侵入内核主干，不启动就不影响系统
4. **Shell/工具全用户态**：换 Shell 不动内核
5. **VFS 后端可插拔**：接口稳定，实现可换
6. **热重载面向插件**：核心走域重启+快照，不原地 patch

## 易耦合点（必须靠代码规范卡死）
1. **调度/内存/IPC 之间隐性耦合**：调度只认域标签和配额，不认识"驱动代理"业务
2. **TTY/pty 不要被兼容层污染**：tty只管字符流，Linux语义翻译放兼容层
3. **VA管理器是最大耦合点**：独立自包含模块，只提供 分配/释放/查询/TLB同步
4. **hepu 命令是用户态工具**：内核只给数据接口，格式化/过滤/展示全在用户态
5. **跨模块用句柄/ID/能力令牌**：禁止裸指针跨域传递

## 两个概念区分
- 内核模块（类ko）：尽量少，只放极小原生驱动
- 系统组件/业务模块（隔离域+用户态插件）：这才是主力模块化单元

## 验收清单
写完一个组件后问自己：
1. 能单独关掉它，其余正常启动？
2. 替换实现，上层要不要改？
3. 有没有直接访问别的模块私有变量？
4. 卸载后有没有残留全局状态/PTE/回调？
5. 是否只依赖契约接口，不依赖内部实现？
