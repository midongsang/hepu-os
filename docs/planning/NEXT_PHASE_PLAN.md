# 下一阶段路线：从"能跑"到"跑得好"

当前状态：0.62.1，双架构可构建，x86 桌面功能基本成型，ARM64 完成 M1d（全 RAM 映射 / GIC+定时器 / ExitBootServices 换栈），M2（首次出界面）进行中。

**核心判断：系统已经跨过"能不能跑"，现在的短板不是功能数量，而是缺度量、缺可靠性、两套架构在分叉。** 下一阶段按下面三条主线走，不再以"加功能"为目标。

## 主线 A：度量（先有尺子，再谈优化）

现在所有"快/慢/稳"的判断都来自 `[PERF]` 一行日志和目测截图，没有基准就没有优化，也没有回归保护。

| # | 事项 | 交付 | 验收 |
|---|---|---|---|
| A-1 | 启动基准 | 从 OVMF 起跳到桌面可交互的分段时间戳（固件/加载器/内核/桌面），串口出结构化行 | 同一镜像连跑 5 次，各段耗时可比较、偏差可解释 |
| A-2 | 帧率基准 | 稳态 60s 采样：平均帧间隔 + P95/P99 帧间隔（卡顿比慢更影响体验） | 报告出 P99；改动前后同一脚本可对比 |
| A-3 | syscall 基准 | 一组固定调用（read/write/epoll_wait/poll/fork/exec）的单次与批量延迟 | 基线数字落库，作为 epoll 等新功能的对比锚 |
| A-4 | 存储基准 | 顺序读写 + 小文件创建/删除吞吐 | 数据落库；与 ext2 代码改动前后对比 |
| A-5 | 内存基准 | kmalloc/kfree 延迟分布 + 长时间运行碎片趋势 | 跑 30 分钟不劣化 |

**说明**：TSC 在 QEMU 不代表真机频率，A-1~A-5 全部按"周期数 + 相对比较"出数，不换算绝对 fps 或 MB/s 对外声称。

## 主线 B：可靠性（出事时系统还站着）

| # | 事项 | 现状 | 目标 |
|---|---|---|---|
| B-1 | 崩溃自动重启 | **已完成 2026-11-25**：`shell_main` 入口 supervisor + `sys_exit` 崩溃重入主线栈；同一启动内 `crashsvc` 连续崩溃 3 次、PID 3/4/5，`restarts=3`，第 3 次后回到 `hepu@os:~`；见 `docs/design/CRASH_CTX_LANDING.md` 6.4。**边界**：仅 32 位 QEMU AUTO 构建，独立常驻 supervisor 未做 | 崩溃后自动重启并保留现场，同一启动内可连续 3 次 |
| B-2 | 文件系统断电一致性 | 未验证 | 写操作中途断电/复位后，fsck 可修复且不丢已 fsync 数据 |
| B-3 | 长时间运行 | 未验证 | 连续 24h 无泄漏（句柄/内存/中断计数稳定） |
| B-4 | 32 位 ICMP/TCP | **已修复 2026-11-25**：ARP/TCP 收发字节序统一；补 ARP/TCP 等待；`tools/test_net32.sh` 实测 ping 4/4、TCP established、ifconfig UP | 保持 QEMU e1000 回归；真机网络另立 |

## 主线 C：架构收敛（别让 ARM64 变成第二套代码）

| # | 事项 | 现状 | 目标 |
|---|---|---|---|
| C-1 | 绘制基元共享 | ARM64 在 `kernel/arch/aarch64/m1/` 里自写最小 fill_rect/draw_char（有意为之，避免过早耦合） | M2 出界面后，把 UI 层抽成与架构无关的 `shared/`，两边共用 |
| C-2 | 帧缓冲抽象统一 | x86 有 `gfx64` + 双缓冲 + region present；ARM64 直接写 GOP | 抽一个后端接口（init/present/present_region），两架构各自实现 |
| C-3 | 输入抽象统一 | x86 键盘/鼠标/触摸分别实现 | 事件结构（key/motion/button）统一，桌面代码只认事件 |
| C-4 | 共享桌面完整性 | x86 桌面约 7k 行 hpdesk.c，ARM64 还没有 | 桌面渲染层可移植，ARM64 能用同一份布局逻辑 |

## 明确不做（至少本阶段不做）

- **继续堆桌面小功能**：屏保/账户/电源菜单已够用，再丰富是自我满足
- **无基准的"优化"**：present memcpy 改动方向对，但收益必须靠 A-2 的 presentK 实测确认，否则就是猜
- **提前做 P3**：GPS（无网络调用且 QEMU 无 NMEA）、Rust（本机无 cargo/nightly）、HTTPS 路由（底层 TLS 是模拟桩）——阻塞点见 `P3_BLOCKERS.md`，前置没到就做等于空转
- **真板移植**：评估报告已出（`ARM64_REALBOARD_EVAL.md`，结论"可行但不能直接搬"，需改串口/PSCI conduit/GIC/内存锚点），但当前没有板子，做也只能停在纸面

## 顺序建议

1. **A-1、A-2**（启动 + 帧率基准）—— 一周内可出数，且立刻能给后续所有优化当锚
2. ~~**B-1**（崩溃自动重启闭环）~~ **已完成 2026-11-25**；后续可评估独立 supervisor 进程与真机/64 位覆盖。
3. **A-3、A-4**（syscall + 存储基准）—— 与 epoll 合并后的回归一起做
4. **C-1、C-2**（绘制基元 + 帧缓冲抽象）—— 等 M2 出界面后立刻做，越晚越难收敛
5. **B-2、B-3、B-4**（断电/长跑/网络修复）—— 依赖前面基准就位后再排

## 与 ROADMAP 的关系

本文件不替代 `ROADMAP.md`（P0-P3 仍是优先级事实源），而是**把 P1/P2 里"加功能"的部分让位给"度量 + 可靠性 + 收敛"**，作为下一阶段的执行重点。任何与本文件冲突的优先级判断，以 ROADMAP 为准；本文件视为对 ROADMAP 的补充视图。

## 2026-11-18 进展快照（供 B 线承接）

**A 线**：
- A-1 启动基准：5 次连测已出数，`app_framework` ≈ 2.05G 周期为最大头；
  `hw_driver`/`net`/`sys_service` 出现 15–23 倍离群 → 启动存在**非确定慢路径**（可靠性视角比性能视角更值得查）。数据见 `docs/status/PERF_BASELINE_2026-11-18.md`。
- A-2 帧率 P99：实测 **p99 ≈ 平均的 9.8 倍**，平均值把卡顿抹平。
- A-3 sysprof：命令已实现，串口 shell 通路已接通（`shell64.c` 输入源 + `kernel_main_64.c` 桌面旁路），但 `-serial pty` 的往返验证未完成。

**B 线**：
- B-1 已完成 2026-11-25：同一启动内 3 次真实重启闭环，证据见 `docs/design/CRASH_CTX_LANDING.md` 6.4。
- B-4 已完成：ARP/ICMP/TCP 字节序与等待修复，QEMU e1000 实测 ping 4/4、
  TCP 三次握手成功；见 `docs/design/B4_NET32_ARP.md`。
- **新增关注**：A-1 里三个 phase 的 15–23 倍离群，本质是"启动不确定性"，应并入 B-3（长时间运行）之外单独跟踪。

**C 线**：
- C-2 有实质进展：x86 侧 `gfx64_present_region` 后端已存在，ARM64 侧 M2S 已量化脏区收益（24×24 相对整屏 **151.8×**）。
- **但 x86 桌面实际没走局部刷新**：`[P0] cursor-only frames=0` / `dirty-region frames=0`，兜底放宽后仍为 0（OBS-09）。C-2 的"后端已备好"和"桌面真在用"是两件事，后者没闭环。

**度量/可靠性交叉的一条**：`present memcpy` 收益（`a50a4b1`）必须靠 A-2 的 `presentK` 前后对比确认，否则就是猜——这条已写进"明确不做"的约束里。
