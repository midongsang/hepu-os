# 赫普 OS 技术路线：内核开发编程语言选型

> 本文档记录赫普 OS 内核及用户态服务的开发编程语言选型决策、依据与渐进式迁移路线。
> 决策日期：2026-09-20 ｜ 状态：已确认

---

## 决策结论

**C 语言（核心内核）+ 汇编（最底层）+ Rust（用户态服务，逐步引入）**

不完全重写，渐进式迁移，核心内核保持 C 语言确保稳定性。

---

## 当前状态

赫普 OS 已用 C 语言开发了大量内核代码，包括：
- 微内核（调度、内存管理、IPC）
- 系统调用接口
- 文件系统
- TCP/IP 协议栈
- 设备驱动框架
- 用户态 shell 与基础工具

引导链（bootsect + stage2）使用 x86 汇编。这是宝贵的现有资产，重写成本极高。

---

## 各语言适用性对比

| 语言 | 内核开发适用性 | 优点 | 缺点 |
|------|---------------|------|------|
| C | ⭐⭐⭐⭐⭐ | 成熟稳定、硬件接近、可移植性好、大量现成代码、工具链完善 | 内存安全问题、类型系统较弱 |
| Rust | ⭐⭐⭐⭐ | 内存安全、零成本抽象、并发安全、现代语言特性 | 学习曲线陡、与 C 互操作需要绑定、编译时间长 |
| C++ | ⭐⭐⭐ | 兼容 C、支持 OOP、性能好 | 复杂、内存安全问题、标准库在内核受限 |
| Zig | ⭐⭐⭐ | 简洁、与 C 互操作好、编译期执行 | 生态不成熟、语言还在演进 |
| 汇编 | ⭐⭐ | 直接控制硬件、最高性能 | 可移植性差、开发效率低 |
| Go | ⭐ | 简洁、并发好 | 有 GC 和运行时、不适合最底层 |

---

## 各层语言分配

### 1. 核心内核：C 语言

**目录范围**：`kernel/`（调度器、内存管理、IPC、系统调用、中断处理、异常处理）

**原因**：
- 已有大量 C 语言代码，重写成本太高
- C 语言是操作系统开发的事实标准（Linux、Windows、macOS 内核均为 C）
- 微内核核心部分需要极致性能和稳定性
- 工具链最成熟，交叉编译、调试工具完善
- 可移植性最好，支持 x86、x86_64、aarch64 等多种架构

**建议**：
- 保持核心内核用 C 开发
- 加强代码质量：静态分析、单元测试、代码审查
- 使用现代 C 标准（C11/C17），利用其新特性

### 2. 用户态服务：逐步引入 Rust

**适合用 Rust 的模块**：
- 文件服务（file-server）
- 网络服务（net-server）
- 图形合成服务（graphics-server）
- AI 运行时（ai-runtime）
- 隐私数据金库（privacy-vault）
- 设备驱动（部分，非性能关键路径）

**原因**：
- 赫普 OS 强调安全（"双模式安全"、"用户数据金库"），Rust 的内存安全正好契合
- 用户态服务崩溃不影响内核（微内核优势），可以大胆尝试新语言
- Rust 的并发安全对网络服务、图形服务很有价值
- 可以通过 FFI 与 C 内核交互

### 3. 最底层代码：汇编语言

**必须用汇编的部分**：
- 启动引导代码（`boot/`、`tools/bootloader.S`）
- 上下文切换
- 中断处理入口
- 特殊寄存器操作
- 关键性能优化路径

**原因**：
- 这些部分需要直接操作硬件，C 语言无法完全表达
- 量很少（通常不到内核代码的 1%），但至关重要

### 4. 不推荐的语言

- **C++**：虽然性能好，但过于复杂，内核中使用标准库受限，且没有解决 C 的内存安全问题
- **Go**：有垃圾回收和运行时，不适合最底层内核开发，用户态工具可以考虑
- **Zig**：虽然理念很好，但生态还不成熟，生产环境使用风险较大
- **Python/JavaScript 等**：有解释器和 GC，完全不适合内核开发

## 渐进式迁移路线图

### 第一阶段：夯实 C 语言基础（当前 — 优先）

- 完善 C 语言内核代码，修复引导链和内核启动问题
- 建立代码规范和质量检查
- 完善单元测试和集成测试
- 编写完整的 API 文档

### 第二阶段：工具链与 FFI 基础设施（Rust 引入前置）

在引入 Rust 之前，必须先建设以下基础设施：

1. **构建系统支持**：在 Makefile / 构建脚本中增加 Rust 交叉编译支持，目标为 freestanding（`no_std`）
2. **FFI 绑定规范**：建立 Rust 与 C 内核的 FFI 绑定，包括：
   - syscall 封装（Rust 调用内核系统调用）
   - IPC 消息序列化/反序列化
   - 共享内存管理
3. **运行时支持**：为 Rust 用户态程序提供最小运行时（堆分配、panic 处理、启动入口）
4. **验证链路**：先用 Rust 写一个独立的用户态测试程序/工具（如 `hepu-utils` 中的某个命令），验证工具链 + FFI + 加载运行全链路跑通

### 第三阶段：Rust 试点服务

- 选择一个用户态服务用 Rust 重写（建议从文件服务或网络服务开始）
- 验证 Rust 在赫普 OS 环境下的可行性和性能
- 积累 Rust 开发经验
- 建立 Rust 服务的开发模板和最佳实践

### 第四阶段：逐步推广

- 新的用户态服务优先用 Rust 开发
- 关键安全模块（隐私金库、安全审计）用 Rust 重写
- 保持核心内核用 C，确保稳定性
- 建立 C/Rust 混合开发的最佳实践

### 第五阶段：生态完善

- 提供 Rust 内核开发库（类似 Redox OS 的 `rust-core`）
- 完善 Rust 交叉编译工具链
- 编写 Rust 开发指南和教程
- 吸引 Rust 开发者贡献代码

---

## 关键原则

1. **不要完全重写** — 已有 C 代码是宝贵资产，完全重写风险大、成本高
2. **渐进式引入** — 从用户态服务开始，核心内核保持 C
3. **安全优先** — 赫普 OS 强调安全，Rust 的内存安全是很好的补充
4. **工具链先行** — 引入新语言前，先完善交叉编译、调试、构建工具
5. **文档同步** — 新语言开发时，同步编写文档和示例
6. **社区考虑** — C 语言开发者基数大，Rust 增长快，可以兼顾两者
7. **性能验证** — Rust 服务上线前必须与 C 实现进行性能对比，确保不引入可感知的性能回退
