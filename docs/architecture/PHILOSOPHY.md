# Hepu OS 核心哲学与原生契约

> 作者：xiulihe
> 日期：2026-10-29
> 地位：本文档是 Hepu 未来所有代码、取舍、架构决策的最高准则。
> 任何与本文档冲突的方案，以本文档为准。

---

## 零、为什么要写这份文档

开发操作系统，最容易犯的错就是「先堆功能、先抄现有系统的表象」。
操作系统的根本，不是「有调度、有文件系统、能跑Linux程序、有驱动」——这些都是表象产物、解决手段，不是它的本质。

我们一层层往下挖，先定义根本，再用这个标尺去过滤所有需求、方案、取舍。
以后遇到「又冒出一堆要做的功能」时，拿这套标尺自己判断：这件事是不是根本需要，还是只是模仿别人的附带产物。

---

## 一、操作系统的本质是什么

剥离所有外壳（shell、桌面、文件格式、syscall、驱动、兼容层），
操作系统内核本质只有一件事：

> **安全、可控地仲裁和复用有限硬件资源，为上层执行单元提供一套稳定、可预测的抽象契约。**

拆成四个最基础的本原命题，这就是所有设计的根：

### 1. 资源是有限的
CPU时间、内存、存储、带宽、硬件寄存器；内核就是资源仲裁器。

### 2. 隔离是刚需
不同执行实体（进程）不能互相随意破坏状态、偷看数据；隔离是安全和稳定性的根基。

### 3. 抽象是契约
硬件本身是杂乱、异构、寄存器碎片化的；内核把混乱硬件包装成统一抽象，给用户态一个约定好的接口。接口一旦对外定型，就是契约，不能随便乱改。

### 4. 确定性优先于丰富性
上层程序依赖「规则稳定」；不确定的行为、隐含副作用、微妙的语义差异，是所有bug、兼容噩梦的源头。

所有后面看到的：调度器、VFS、内存管理、驱动、信号、syscall，全部是实现上面四条本原的工具，不是目的。

- 不是「我要写一个调度器」，而是「我需要仲裁CPU时间、隔离不同任务，所以我需要调度器」。
- 不是「我要做Linux兼容层」，而是「我想复用已有软件生态，但兼容层不能破坏内核原本的隔离与资源契约」。

这就是区分「模仿式开发」和「本原式开发」的分界线。

## 二、用根本标尺复盘已有选择

### 1. 语言选择：C + Rust 混合

**根本诉求**：在资源极致可控（C，贴近硬件、零开销）和隔离安全（Rust，在编译器层面消除一类内存破坏）之间找到平衡点。

✅ 贴合本质：隔离、安全是内核本原目标之一。
- 纯C：隔离和安全只能依靠人工，违背「可靠隔离」；
- 纯Rust：很多硬件底层操作、老旧固件交互会被语言本身增加额外成本，违背「资源可控、零开销」。

不是跟风Rust，而是从「安全隔离、硬件资源可控」这两个本原推导出来的。

⚠️ 底线：Rust 不是用来炫技的。凡是不承担隔离、资源仲裁职责的地方，没必要强行上Rust；凡是高风险、破坏隔离的模块，优先Rust收敛unsafe。

### 2. 兼容层方案：边界翻译，不侵入内核、不加载 .ko

很多人的选择是：为了跑Linux程序，把内核内部改成Linux结构、加载ko。
他们的出发点是表象：「要跑程序，所以我要拥有Linux内核内部结构」。

我们的出发点是本质：**内核本身的资源仲裁、隔离契约是 Hepu 的根本，不能为外部ABI污染内核内部模型；兼容只是上层附加的翻译适配，是一个遵守内核原生契约的普通用户态/轻量内核模块。**

✅ 非常贴合本质：
- 兼容层是消费抽象契约的客户，不是去改写契约本身。
- Linux程序看到的是翻译后的假象，Hepu内核内部的资源模型、隔离规则自始至终是独立、统一的。

这也是为什么之前反复强调：绝对不要把Linux内核内部结构搬进主干。

### 3. 驱动方案：原生驱动 / UIO / 驱动代理VM

表象思路：「别人有很多驱动，我也要写一堆驱动」
本原思路：**驱动的本质：把异构硬件，接入内核的资源抽象和隔离模型。**

驱动只有两个评判标准：
- 是否正确遵守内核的资源、隔离契约；
- 是否高效地把硬件能力转换成内核对外的抽象。

所以三种驱动方案本质上只是三种接入方式，没有高低贵贱：
- **原生内核驱动**：最高性能接入；
- **UIO用户态驱动**：隔离性更强，驱动崩溃不破坏内核；
- **驱动代理VM**：把一整个Linux实例包装成一个遵守Hepu隔离规则的「硬件服务进程」。

代理VM本质上就是：把Linux整个驱动栈封装在一个强隔离沙箱里，作为Hepu的硬件后端。
它没有破坏内核本原，只是一种特殊的驱动实现形式。
这个视角下，你不会因为「我靠虚拟机代理驱动」而觉得这是一种妥协、低人一等；它只是在现阶段人力有限时，满足「硬件接入抽象」这个根本目标的手段。等以后需要更高性能，再逐步迁移成原生驱动。

### 4. 文件系统、VFS

表象思路：Linux换btrfs、bcachefs，我也要跟上做COW、快照。
本原思路：**VFS的本质：对块存储资源的统一抽象，提供命名空间、字节流、权限、元数据，并且维持隔离。**
文件系统只是VFS后端实现。快照、校验、压缩，是附加特性，不是VFS的本质。

推导顺序应该是：
1. 先定义VFS抽象契约（打开、读写、权限、隔离）
2. 再选择后端实现，满足契约
3. 快照、校验等能力，是在契约之上的扩展，不是VFS必须自带

你可以选择ext4、btrfs、自研FS，唯一评判标准：是否符合VFS抽象契约、资源是否可控、隔离有没有被打破。而不是跟风下一代文件系统。

### 5. 调度器

表象思路：CFS很好，我复刻一个CFS。
本原思路：**调度器的本质 = CPU资源仲裁器。**
先回答：Hepu希望给任务提供什么样的CPU契约？
- 桌面优先低延迟？
- 服务器优先公平吞吐？
- 是否区分原生任务、兼容层任务的调度契约？

契约定好了，调度算法才是为契约服务的工具。
如果你的目标是低延迟桌面，硬抄CFS（偏向公平吞吐），就是本末倒置。

## 三、决策流程：以后再也不会被无穷无尽的功能淹没

以后你冒出任何一个想法（加一个功能、上一个子系统、引入一个方案），都按这个顺序自问：

### 1. 本原问题
这个需求，最终是为了服务内核四大根本目标里的哪一条？
（资源复用？隔离？抽象契约？可预测性？）
如果一条都沾不上，它就是装饰性功能，可以延后甚至砍掉。

### 2. 契约检查
它会不会破坏 Hepu 原生的核心契约？
比如：会不会为了兼容，让进程突破隔离边界、让资源模型出现特殊特例？
如果破坏契约，再好用的方案都拒绝。

### 3. 放置检查
能不能放在抽象边界之外（用户态/独立沙箱）实现？
内核主干只保留最本原的仲裁和隔离；凡是可以放到上层的，绝不进主干。

### 4. 不确定性检查
这个方案有没有引入隐式、不确定的行为？
任何「有时候这样、有时候那样」的隐含语义，都是对契约的伤害，优先剔除。

### 5. 简化检查
有没有更简单、更直接的方式达成同一个本原目标？
很多复杂方案，只是因为模仿别人，而不是解决根本问题。

#### 示例：ioctl翻译子系统
1. 目标：为兼容程序提供硬件抽象，复用软件生态（属于消费内核已有的硬件契约）
2. 检查：翻译层只是转换参数，不修改内核资源和隔离规则 → 不破坏契约
3. 放置：可以做成内核轻量钩子，或者用户态加载器里的翻译层
4. 风险：ioctl大量私有语义，极易产生不确定行为 → 所以策略是复杂ioctl不走翻译，交给驱动代理沙箱
5. 简化：不做全量翻译，只翻译基础通用ioctl

## 四、Hepu 的核心哲学（与Linux、BSD拉开根本差异）

Linux 的历史起点：为兼容UNIX，先复刻一套现成ABI，内核内部模型长期跟着ABI历史包袱一起演化。很多内部设计，是为了兼容几十年前的语义而存在。
也就是：**先有ABI契约，内核实现去适配契约。**

而 Hepu 可以反过来，这就是根本路线：

> **先定义内核原生的资源模型、隔离模型、基础抽象契约（本原）；
> 原生ABI是这套本原模型自然导出的产物；
> 外部ABI兼容（Linux）只是运行在这套本原之上的、可选的翻译层。**

顺序反过来，是本质层面最大的不同。

- Linux：ABI优先，内核跟着ABI走；
- Hepu：内核资源与隔离本原优先，ABI是结果，兼容是附加层。

这也解释了为什么前面反复强调：不要让兼容层绑架内核结构。这不是一个工程技巧，是这套底层哲学的必然推论。

---

## 五、从本质出发 ≠ 闭门造车

从本质出发，不是否定前人。
Linux、BSD、Redox 踩过的坑，都是非常宝贵的：他们证明了哪些抽象在现实硬件、软件下会失效，哪些隔离模型有漏洞，哪些资源仲裁策略会引发饥饿、死锁。

你可以吸收他们的经验，但不要直接吸收他们的表象结构。
先回到本原推导一遍：这个子系统，我为什么需要它？它在我的资源、隔离模型里承担什么角色？再看别人的实现，作为参考。

## 六、开发顺序锚定

操作系统根上就四件事：**资源仲裁、执行隔离、硬件抽象、稳定契约。**
所有模块都是手段，不是目的。

开发 Hepu 的正确顺序：

1. **先严谨定义**：Hepu 的资源模型、隔离模型、基础抽象契约（这是根基）
2. **然后推导**：为了实现这套契约，我需要哪些最小子系统
3. **再考虑**：附加层（兼容、驱动代理、桌面、文件系统高级特性）如何在不破坏契约的前提下接入
4. **凡是和根基无关、或者会污染根基的，延后、外包、舍弃**

## 七、既有准则补充（xiulihe 此前确立）

> 以下是项目开发过程中已经确立的准则，同样作为最高准则的一部分：

### 7.1 交付准则
- 每次交付 = 项目源码包（tar.gz）+ 混合镜像（img.gz）
- 交付前 gzip -t 校验压缩包完整性
- 镜像用 gzip 压缩后交付（256MB → ~1.2MB）

### 7.2 兼容层路线
- 阶段1：原生 POSIX，源码级兼容，不碰二进制兼容
- 阶段2：用户态 Linux ELF 加载器 + syscall 翻译，不污染内核
- 阶段3：高频 syscall 选择性下沉到内核快路径
- 阶段4（远期）：完整内核 Linuxulator，仅当桌面生态刚需时启动
- Windows 兼容：非常后期，等 Linux 稳定后再启动
- 接受 5~30% 兼容损耗，不追求零损耗

### 7.3 内核预埋路线（优先级）
- 第1档：syscall 入口兼容分支、errno 统一映射表、vDSO、VFS compat_ctx、env_type 标记
- 第2档：VMA 红黑树、task 预留兼容扩展字段、ASID、tickless
- 第3档：调度器细粒度锁、中断线程化、pagecache 调优
- 第4档：libc POSIX 补齐、ld.so 优化、Vulkan
- 第5档（延后）：io_uring、evdev、tracepoint
- 第6档（最后）：Linux ELF 加载器原型

### 7.4 避坑清单
1. 不要为兼容把内核改成 Linux 结构
2. errno 转换集中在一处，不散落
3. 内部结构和 ABI 输出分开
4. 高频 syscall 走快路径/vDSO
5. 不要在阶段2就做完整 Linuxulator
6. 不要把 Linux syscall 号直接硬编码进内核
7. 不要追求零损耗
8. 不要先做 Windows 兼容
9. 不要为了跑某个软件改内核语义——改兼容层，不改内核

- 根因待查（可能：VBE 不兼容、SMP AP 启动失败等；USB mass storage BOT 驱动已编入 `usb64.c`，非当前怀疑点）
