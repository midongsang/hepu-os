## 开发规范（硬性约束，所有开发者必须遵守）

> 以下三条为赫普OS**兼容层与多平台支持开发**的最高优先级约束，任何迭代不得违反。
> 违反视为架构级事故，必须回滚修复。

### 约束一：兼容层用户态化（禁止入内核）

多平台兼容层（Windows EXE / Linux ELF / macOS 应用等**外部格式**的加载、ABI 翻译、
运行适配）**必须作为用户态服务实现，禁止移入内核态**。

- 内核只提供最小、稳定、经过审计的系统调用接口，不内置任何外部格式的解析/翻译逻辑；
- 兼容层故障（崩溃、越权、异常退出）只影响其自身，不得波及内核或其他进程；
- 此举保护微内核的**隔离能力与攻击面边界**——外部格式代码天然不可信，
  必须被关在用户态沙盒里，而不是获得内核信任。

### 约束二：统一沙盒（禁止绕过）

所有应用类型（.hug 原生应用、EXE、Linux、macOS 兼容应用）**必须经过同一套沙盒**，
提供**一致的资源限制、权限模型与 IO 隔离**。

- 不允许任何兼容格式绕过沙盒获取额外权限（内存/CPU 限额、文件访问、网络、
  外设访问均受同一策略约束）；
- 兼容层加载外部程序时，权限**降级而非升级**——外部格式默认比 .hug 原生应用
  更受限，而非更宽松；
- 沙盒参数统一下发，格式差异只在翻译层处理，不渗透到安全策略层。

### 约束三：兼容性预期管理

兼容层对外定位：**尽力兼容，不承诺 100% 软件/游戏全部完美运行**，控制用户预期。

- 官方文档、宣传材料、应用市场须明确标注每个应用的**兼容等级**
  （完全兼容 / 基本兼容 / 运行异常 / 不支持）；
- 禁止使用"完美运行所有 X 软件/游戏"等绝对化表述误导用户；
- 兼容问题按「可复现 → 记录归档 → 排期修复」流程处理，不承诺修复时间表；
- 兼容等级由**实测结论**判定，禁止未验证即宣称兼容；
- 性能损耗不得以固定百分比对外承诺（如"仅慢 5%"）；以固定二进制清单的
  实测通过率、按 workload 分类的实测数据为准。

## 0. 设计本原与决策准则

> 本节是判断"该不该做、放在哪一层"的最高准则：先定义本原，再推导子系统；
> 模块是实现手段，不是目标。与约束一/二/三冲突时，以硬约束为准。

### 0.1 内核的四个本原

1. **资源有限**：CPU 时间、内存、存储、带宽、硬件寄存器 → 内核是资源仲裁器；
2. **隔离刚需**：执行实体不能越界破坏或窥探彼此状态 → 隔离是安全与稳定的根基；
3. **抽象是契约**：把异构、碎片化的硬件包装成稳定接口；契约对外定型后不随意改；
4. **确定性优先**：稳定、可预测；隐含副作用与"有时这样、有时那样"是 bug
   与兼容噩梦的源头。

调度器、VFS、内存管理、驱动、信号、syscall 都是实现上述本原的工具，不是目的。

### 0.2 推导顺序（赫普与 Linux 的根本差异）

- **Linux**：ABI 优先，内核实现长期适配历史 ABI；
- **赫普**：先定义资源模型、隔离模型、基础抽象契约；原生 ABI 是这套模型的
  自然导出；外部 ABI（Linux/Windows）兼容是运行在本原契约之上的**可选翻译层**。

推论：兼容层是契约的**消费者**，不是契约的改写者；禁止为兼容把 Linux 内部结构
搬进内核主干。这也是约束一/二的哲学依据，而非单纯工程技巧。完整公理见 0.7。

### 0.3 决策流程（五问）

新增任何功能、子系统或方案前依次回答：

1. **服务哪条本原？** 资源仲裁 / 隔离 / 抽象契约 / 确定性；一条不沾 → 装饰性功能，
   延后或砍掉；
2. **是否破坏原生契约？** 破坏 → 拒绝，不论方案多好用；
3. **能否放到抽象边界之外？** 能放用户态或独立沙箱 → 不进内核主干；
4. **是否引入隐式、不确定行为？** 是 → 优先剔除或隔离；
5. **是否有更简单直接的方式达成同一目标？** 有 → 选简单方案，不模仿别人的结构。

### 0.4 用五问复核既有结论

| 议题 | 本原归属 | 结论 |
|------|----------|------|
| 语言选型 | 隔离 + 资源可控 | C 保硬件对接与零开销，Rust 收敛高风险模块；不为炫技而上 Rust |
| 兼容层 | 抽象契约的消费者 | 边界翻译、可选可关；禁止 `.ko` 与 Linux 内部结构入主干 |
| 驱动 | 硬件接入抽象 + 隔离 | 原生 / UIO / 代理 VM 是三种接入方式；代理 VM 是沙箱化硬件服务，不是妥协 |
| 文件系统 | 存储抽象契约 | 先定契约（若引入 VFS），再选后端；COW/快照/压缩是扩展，不是本原 |
| 调度 | CPU 资源仲裁 | 先定 CPU 契约（桌面低延迟 / 服务器公平），算法服务于契约，不硬抄 CFS |

### 0.5 边界提醒

- **本原推导不等于闭门造车**：吸收 Linux/BSD/Redox 的失败经验，但不复制其表象结构；
- 本节不替代约束一/二/三；兼容层最终位置仍待 3.4 的 A/B 决策，
  但任何选项都必须满足"不污染内核契约、不绕过统一沙盒"；
- 在 16.2 的三分法下，"本原需要"不等于"V1 必须做"，仍受 V1 范围冻结约束。

### 0.6 待产出

- 《赫普原生契约》：内存契约、进程隔离契约、文件与设备访问契约。
  在写出之前，不以任何现有实现（含 Linux 结构体）反向定义为"契约"。

### 0.7 核心公理：内核与 ABI 的边界

本节把"内核 = 资源隔离管理器"展开为七条可判定公理。任何子系统与其中一条冲突时，
先改设计，不改公理。

1. **内核只提供资源原语**：域、内存、CPU、设备、IPC。任何 ABI 语义
   （Linux/POSIX/Win32/Android/Binder/ART）不得进入内核主干。
   判定：若一个功能的描述里出现 Activity、Manifest、AIDL、信号语义或 Linux
   内部结构体，它就不属于内核。
2. **能力是唯一的跨域授权单位**，句柄是能力在域内的名字。授权与撤销由内核记账，
   不依赖路径、全局名字或"约定俗成"。
3. **数据面默认零拷贝**：跨域共享内存由内核授权映射；内核搬运控制消息，
   不搬运业务数据。
4. **每个应用进程/兼容实例 = 独立隔离域**。兼容性不得以牺牲隔离为代价；
   把所有 Android 应用塞进一个兼容实例只是演示形态，不是可交付形态。
5. **安全底座在内核强制，业务权限在用户态**：域隔离、发送者身份、设备能力由内核
   裁决；Manifest、组件权限、包管理属于兼容层。两者混同会高估用户态的能力。
6. **兼容层可嵌套**：Linux ABI 实例是 Android 层的组件，不是内核的全局模式。
   兼容层之间通过同一套能力 IPC 组合，而不是互相打补丁。
7. **IPC 命名空间化**：总线不是全局单例。Android 的 binder/hwbinder/vndbinder
   对应三条互不越权的总线；把总线做成单例，等于提前做死未来所有隔离需求。

公理 1 回答"放哪一层"，公理 2/3 回答"跨域怎么授权与搬运"，公理 4/5 回答"隔离与
安全由谁强制"，公理 6/7 回答"兼容层如何组合与隔离"。七条同时成立时，
"新增一个 ABI"退化为"新增一个域内运行时"，内核主干不需要改动。

### 0.8 Binder 的本质与归属

#### 0.8.1 事实边界（三个必须纠正的误判）

- Android 依赖的不是笼统的"Linux ABI"，而是一族 **Linux 特有内核接口**：
  binder、ashmem/memfd、SELinux、cgroups、epoll/futex/eventfd/timerfd、
  ion/dmabuf、fence。仅有 POSIX syscall 翻译不足以承载 Android。
- Anbox/Waydroid 并未绕开 binder 驱动，而是复用宿主内核的 binder/ashmem
  （binderfs 或 binder 内核模块）。这说明 binder 的内核部分是硬依赖，不是可选项。
- Android 权限不是纯用户态：Manifest 与组件权限是用户态约定；UID/GID 沙箱与
  SELinux 是内核强制。两层必须分开讨论，否则会得出"内核完全不懂权限"的错误结论。

APK 本身确实不直接调用任何内核 syscall，它依赖的是 Android Framework 与系统服务；
但承载这些服务的运行时，仍会落到上述内核接口上。

#### 0.8.2 分层：只有两层需要内核

| 层 | 内容 | 归属 |
|----|------|------|
| 传输 | 发送方一次陷入写内核缓冲；接收方 mmap 同一物理页直接读 | 内核：单拷贝 + 共享映射 |
| 会合 | 接收线程池阻塞，内核唤醒；同步调用等回复，oneway 不等 | 内核：阻塞/唤醒/取消 |
| 调度 | 处理请求期间提升接收线程优先级，防优先级反转 | 内核：优先级捐赠 |
| 对象 | node/proxy/handle、每进程句柄表、引用计数、死亡通知 | 内核：能力表 + 生命周期 |
| 身份 | transaction 附带发送者 uid/pid，SELinux/UID 检查 | 内核：域身份 + 强制隔离 |
| 语义 | parcel 编码、AIDL、接口描述符、servicemanager、oneway、线程池策略 | 用户态 |

一句话：**Binder = 内核提供的能力式同步 RPC 传输 + 用户态的 parcel/AIDL/服务语义**。
内核部分不含任何 Android 业务概念；Activity、权限、包管理全部在用户态。

历史边界：Binder 并非 Android 首创，它源自 OpenBinder（BeOS 系），Android 将其
移植并绑定到 Linux。其本质是"带引用计数、对象传递与权限检查的跨进程远程调用框架"，
与 Android 业务无关。

#### 0.8.3 与赫普原语的对应关系

```
Binder ≈ 能力 IPC（消息 + 句柄传递 + 引用计数与撤销）
       + 跨域共享内存授权（零拷贝）
       + 同步会合 / 唤醒 / 超时 / 取消
       + 优先级捐赠
       + 域生命周期事件（死亡通知）
       + 内核背书的发送者身份
       + 命名空间路由（binder / hwbinder / vndbinder）
```

前七项都是通用资源原语，正好落在内核职责内；parcel、AIDL、servicemanager 及
AMS/WMS/SurfaceFlinger 等全部是域内用户态。由此得到形态判断：

- **不做内核级 Binder 驱动**：那等于把 Android ABI 写进主干，违背公理 1，并把
  hwbinder/vndbinder 的命名空间策略带进内核。
- **不把 Binder 私有塞进单个 Linux 兼容实例**：只要 APK 进程独立成域，跨域传输
  必然落到 Hepu IPC；所谓"兼容层内复用"最终仍需要一个跨域 broker。
- **正确形态**：内核通用能力 IPC + 用户态 `binder broker` 域（句柄表、引用计数、
  服务注册、多上下文命名空间）+ 兼容层只做 `/dev/binder` 的 ioctl/ABI 外壳。

#### 0.8.4 目标形态与代码现状（不得混为一谈）

目标形态即 0.8.3 的第三方案。代码现状（2026-11-02）：

- 已有的 `hsipc` 是核内命名通道，`pipe`/`futex` 是进程内设施，二者都不构成
  跨域能力模型；
- 以下原语尚未提供：能力令牌与每域句柄表、跨域共享内存映射、同步会合
  （阻塞/唤醒/超时/取消）、引用计数与能力撤销、域死亡事件、优先级捐赠、
  多命名空间路由。

推论：在前五项落地前，任何 "Binder" 实现都只能是同域伪实现，可演示，
不可承载真实隔离。因此实现顺序被依赖链锁死：

```
能力令牌 + 句柄表
  → 跨域共享内存
    → 同步会合 / 取消
      → 引用计数 + 撤销
        → 域死亡事件
          → 优先级捐赠
            → 多命名空间路由
              → binder broker（用户态）
                → /dev/binder 外壳（Linux 兼容层）
                  → Android 系统服务与 APK
```

#### 0.8.5 兼容层嵌套模型

```
Hepu 内核（能力 IPC / 共享内存 / 会合 / 生命周期）
   └─ binder broker 域（句柄表、引用计数、服务注册、多上下文）
        ├─ Android 进程 A（独立域：Linux ABI 实例 + bionic + ART）
        ├─ Android 进程 B（独立域：同上）
        └─ 系统服务域（AMS / WMS / SurfaceFlinger / PackageManager，各自独立）
```

关键约束：**每个 Android 应用进程 = 独立隔离域**；Linux ABI 运行时可以共享代码与
服务，但绝不共享地址空间。若所有应用共享一个地址空间，UID 沙箱与应用隔离消失，
兼容性即降级为演示。

- 可复用：syscall 翻译、POSIX 语义、bionic、ELF 链接器、基础文件/线程设施。
- 不可复用：Binder 语义、ART、Activity/AMS 生命周期、Surface/图形栈、包管理、
  Android 权限模型。

#### 0.8.6 Android 系统服务的归属

Android 系统服务是一组常驻用户态进程：对外暴露 Binder 接口，对内调用文件、
ioctl、设备节点与 socket，并自行维护窗口栈、Activity 栈、权限表、通知队列。
内核对其完全无感知。

需要单独说明的是：SurfaceFlinger、AudioFlinger 一类的服务还依赖设备能力与
零拷贝缓冲（dmabuf/fence 类原语）。这属于**设备能力模型**，与 Binder 是并行的
另一个原语族，不能靠 IPC 语义替代。

#### 0.8.7 两条路线建议的事实核对

外部常见的"路线 A：兼容层内模拟 Binder / 路线 B：自研 HepuBinder"二分法方向可用，
但其中若干前提不成立，落地前必须校正：

- **"不改内核"是错觉**。Binder 语义可以放用户态，但它依赖的内核原语——共享页
  授权、阻塞会合与唤醒、能力/句柄转移、死亡事件、优先级捐赠、内核背书的发送者
  身份——赫普目前都没有。路线 A 同样要先补这些原语，只是不把 Binder 业务写进内核。
- **"用户态模拟 ioctl"不成立**。ioctl 是字符设备入口，纯用户态代码无法让
  `/dev/binder` 生效。理论上有三种形态：内核侧字符设备转发、CUSE/FUSE 设备、
  直接替换 `libbinder`/`libbinder_ndk` 后端；但 binder 依赖设备 mmap 与高频 ioctl，
  CUSE/FUSE 无法提供可用语义，实际可行的只有"内核侧设备"与"替换系统库"两种。
- **单域承载全部 Android 进程只能做 PoC**。它确实能让 Binder 变成同域调用、
  零内核改动，但所有应用共享地址空间，UID 沙箱消失，不符合公理 4。
- **"安卓源码零修改"的前提比描述更宽**。除 Binder ioctl 外，还需 ashmem/memfd、
  epoll/eventfd、SELinux/UID 语义、dmabuf/fence、HAL/gralloc；缺一项就跑不起
  完整框架。替换系统库则意味着要自建 Android 系统镜像，而非"直接复用现成镜像"。
- **路线 B 不是 Binder**。它是原生能力 RPC：不应复制 Binder 的 ioctl/parcel 形态，
  而应直接以能力 IPC 定义接口。它可以与路线 A 共用同一个 broker 底座，避免出现
  两套引用计数、死亡通知与生命周期实现。
- **事实修正**：Binder 是单拷贝而非零拷贝（发送方拷入内核缓冲，接收方 mmap 同一
  物理页直读）；驱动维护的是按进程句柄的强/弱引用计数，不是"跨进程 GC"（Java 层
  GC 仅触发引用释放）；Binder 驱动位于 Linux 主线源码树（`drivers/android`），
  并非第三方外挂模块，只是多数发行版默认不编译。

顺序结论：A 与 B 不冲突，但都排在通用能力 IPC 之后。先补原语，再决定 Binder
profile 与原生 RPC 的接口形态；否则会为 PoC 写两套临时协议，之后全部重写。

#### 0.8.8 Binder 命令集的能力映射

Binder 的 ioctl 面分两类：`BINDER_WRITE_READ` 承载的 BC_/BR_ 命令流，以及独立的
控制 ioctl。逐组拆解后的结论是：**没有一条命令需要"内核理解 Binder"，但多数命令
需要内核提供通用会合、共享页、句柄与生命周期能力。**

| 组 | 代表命令 | 语义 | 内核职责 | broker 职责 | 可行性 |
|----|----------|------|----------|-------------|--------|
| 事务 | BC_TRANSACTION / BC_REPLY / BR_TRANSACTION / BR_REPLY / BR_TRANSACTION_COMPLETE / BR_DEAD_REPLY / BR_FAILED_REPLY | 同步调用、单向调用、回复与失败码 | 同步会合、取消、会话令牌 | 路由、队列、事务栈、状态码 | 高 |
| 缓冲 | BC_FREE_BUFFER、设备 mmap | 单拷贝数据面与缓冲回收 | 共享页授权与回收 | 缓冲分配、异步配额 | 高 |
| 线程池 | BC_ENTER_LOOPER / BC_REGISTER_LOOPER / BC_EXIT_LOOPER、BINDER_SET_MAX_THREADS、BINDER_THREAD_EXIT | 收包线程注册、阻塞、退出 | 阻塞收包与唤醒 | 池策略、按需扩容 | 高 |
| 引用计数 | BC_INCREFS / BC_ACQUIRE / BC_RELEASE / BC_DECREFS、*_DONE、对应 BR_* | 强/弱引用增减与握手 | 能力撤销、回收兜底 | 每域句柄的强/弱计数 | 中高 |
| 死亡通知 | BC_REQUEST_DEATH_NOTIFICATION / BC_CLEAR_DEATH_NOTIFICATION、BR_DEAD_BINDER、BC_DEAD_BINDER_DONE | 对端消失事件订阅 | 域死亡事件 | cookie 表、回调派发 | 中高 |
| 服务发现 | BINDER_SET_CONTEXT_MGR / _EXT | handle 0 与命名空间注册 | 仅提供引导端点的能力 | 服务注册表、多上下文命名空间 | 高 |
| 对象传递 | flat_binder_object（BINDER / HANDLE / FD / FDA / PTR） | 跨进程对象、fd、散页引用 | 能力转移、fd 虚拟化底座 | 类型翻译、句柄映射 | 中 |
| 控制/调试 | BINDER_VERSION、GET_NODE_DEBUG_INFO、GET_NODE_INFO_FOR_REF、GET_EXTENDED_NODE_FLAGS | 版本协商与诊断 | 无 | 版本与降级策略 | 高（可 no-op） |
| 冻结 | BINDER_FREEZE / GET_FROZEN_INFO、BR_FROZEN_REPLY | 缓存进程挂起/恢复 | 域挂起与恢复 | 状态跟踪 | 中低（可先 stub） |
| 反滥用 | BR_ONEWAY_SPAM_SUSPECT | 单向调用风暴检测 | 无 | 配额与限流 | 低优先 |
| 调度 | 非 ioctl：优先级继承 | 防止优先级反转 | PI 捐赠原语 | 线程与事务关联 | 中 |
| 身份 | sender_euid、secctx | 发送者身份与安全上下文 | 内核背书的域身份 | SELinux/UID 策略映射 | 低（最大不确定项） |

可行性判断：

- **协议层没有不可翻译的命令**。卡点不在 BC_/BR_ 本身，而在三处：通用内核原语、
  fd 虚拟化、SELinux/UID 语义。
- **fd 传递比 Binder 本身更难**。Android 假定收到的 fd 是可 `read/write/ioctl/dup/
  epoll` 的真内核 fd；赫普必须由 VFS 与设备句柄转发支撑，否则只能得到同域伪 fd。
- **分水岭是"跑现成镜像还是自建镜像"**：
  - 跑现成 Android 镜像：`libbinder` 直接 `open("/dev/binder")`，必须有内核侧
    字符设备语义。可以在内核实现一个"通用能力总线字符设备"，其 ioctl 是 binder
    形状的转发层——这不是把 Binder 业务写进内核，但内核确实要理解这套编码。
  - 自建 Android 镜像：把 `libbinder` 换成 broker 客户端，纯用户态可行；此时
    "应用源码零修改"成立，"系统库零修改"不成立。
  - 因此**"零修改 + 零内核改动"不能同时成立**，必须显式二选一。
- **最小可行切片**：先做事务、缓冲、线程池、服务发现四组，引用计数与死亡通知用
  broker 简化实现，冻结与反滥用先 stub；以一条 AIDL 往返验证闭环。若这四组跑不通，
  后续投入不成立。

### 0.9 源码自由度的边界（Android 移植）

"有源码就能做很多功能"只对一半：源码给的是**上层语义的控制权**，换不来硬件能力、
内核原语、许可与生态认证。先区分三层"源码"：

| 层 | 可控性 | 说明 |
|----|--------|------|
| 应用（APK/DEX） | 不可改 | 必须按标准行为运行，改了就不再是通用兼容 |
| Android 用户态（framework、libs、系统服务） | 可控 | AOSP 以 Apache-2.0 为主，可裁剪、替换、插桩 |
| Linux 内核、GKI、binder 驱动 | 不可搬用 | GPLv2 且与赫普架构不兼容；只能自行实现通用原语 |

#### 0.9.1 源码能解决的

1. **语义对齐**：按 AOSP 源码精确定义行为，不靠黑盒猜测；但仍需兼容性测试验证，
   源码可见不等于运行时行为可控（vendor blob 与内核实现不在 AOSP 内）。
2. **裁剪**：去掉不需要的服务与模块，但受 CTS 与组件依赖约束，不是任意裁剪。
3. **替换组件**：把 AudioFlinger、SurfaceFlinger 等换成对接赫普设备能力的实现。
4. **插桩调试**：在 ART、Binder、系统服务中加 trace 与断点。
5. **定制发行版**：轻量环境、无 GUI 后台服务、场景化子集。

补充：Wine 的对照不准确。Wine 依据公开文档与兼容性测试实现 Win32 语义，并非
纯逆向猜测；AOSP 开源带来的优势是"可读、可改、可裁剪"，不是"能猜对行为"的替代品。

#### 0.9.2 源码解决不了的五个硬边界

1. **硬件与 BSP**：闭源固件、GPU 驱动、基带、DRM、寄存器手册不在 AOSP 内；
   没有文档与固件，改源码写不出驱动。
2. **内核原语**：缺同步会合、共享页授权、句柄转移、死亡事件、优先级捐赠时，
   改 AOSP 不会让这些能力凭空出现（见 0.8.4、0.8.7）。
3. **许可与生态**：GPLv2 的内核代码不能搬进赫普内核；Apache-2.0 需保留声明；
   Android 商标、CTS、GMS、Play Integrity、Widevine 由认证与商业协议授予，
   不由源码授予。
4. **跨层开销**：翻译与跨域转发是结构性成本，源码能优化浪费，不能消除层级。
5. **应用预期**：标准 APK 可能依赖 GMS、DRM、Play Integrity；AOSP 源码里没有
   这些组件，能编译不代表能跑通认证类应用。

#### 0.9.3 "内核一行不动"是错误表述

正确表述是：**内核不新增 Binder 业务，但必须新增通用原语**。兼容层需要的能力
不会因为拿到了 AOSP 源码而消失；源码改变的是"谁调用、怎么调用"，不改变
"被调用的能力是否存在"。

#### 0.9.4 正确的移植缝隙是 HAL，不是 Binder

Android 自 Treble 起就把系统与 vendor 分离：gralloc、composer、audio、camera、
sensors 均通过稳定 HAL 接口（HIDL/AIDL）对接。移植的正确切入点是**实现这些 HAL**，
把设备能力接到赫普；Binder、AIDL、系统服务、ART 全部保持原样。

- 收益：标准 APK 兼容性保留、CTS 可测、可同步上游；改动面从"整个框架"缩到
  "若干 HAL 实现"。
- 反面：直接改 Binder/AIDL 去接赫普原生 IPC，等于做 Android 平台分支，失去 HAL
  稳定契约与 CTS。它不是"路线 B 的延伸"，而是另一条产品线。

#### 0.9.5 两种思路的准确命名

- **思路 1 = 兼容发行版**：上游 AOSP + 兼容层模拟 + HAL 移植。目标是跑标准 APK，
  可与上游同步。
- **思路 2 = 平台分支**：深度改造框架通信层，服务原生生态。目标是性能与安全模型
  融合，代价是脱离标准安卓。

两者不是同一目标的两个阶段，而是两个产品。在"跑 APK"的目标下选思路 2，
等于用兼容性的代价换性能，方向就错了。

结论：源码带来的是"语义可定义、可调试、可裁剪"，不是"硬件无限、原语自生、
许可自动获得"。真正的杠杆在 HAL 缝隙，不在重写 Binder。

### 0.10 Android HAL 移植的具体步骤

> 详细展开与可执行清单见 [ANDROID_HAL_PORTING](../planning/ANDROID_HAL_PORTING.md)。

0.9.4 只定了缝隙，本节把它拆成可执行顺序。先给结论：**HAL 移植不是第一件事，
也不是工作量主体**。标准 HAL 服务是动态链接的 Android 进程，它要先能加载、
能注册、能通过 Binder 被调用，之后才谈"把设备接进来"。顺序被依赖链锁死：

```
Android 用户态域（bionic + linker + 大 VA + init/servicemanager）
  → Binder 传输（broker + /dev/binder 外壳）
    → 设备能力模型（令牌 + 共享缓冲 + 事件 + fence）
      → HAL 适配器（标准 HAL 接口 → 赫普设备能力）
```

工作量结构大致是：用户态域与传输占大头，设备能力次之，单个 HAL 适配器最小。
把 HAL 当主线，会低估前置成本。

#### 0.10.1 先定三件事（否则无法排序）

| 决策 | 建议 | 影响 |
|------|------|------|
| 目标版本与传输 | Android 14/15，新增 HAL 一律 AIDL | AIDL 走 `/dev/binder` 与 `servicemanager`，和 broker 同一传输；HIDL 另需 `/dev/hwbinder` 与 `hwservicemanager`，只在复用旧 vendor 包时保留 |
| 参考设备 | 先 QEMU x86_64（virtio 显示/输入/音频/网卡），再开发板，最后手机 | 手机 BSP 会让 HAL 工作与闭源驱动纠缠，不能作为第一步 |
| 验收口径 | 三层：`lshal` 可见、VTS 单模块通过、framework 客户端真实调用 | 只有第一层是"接口通了"，不是"移植完成" |

#### 0.10.2 依赖链现状核对

| 环节 | 现状 | 缺口 |
|------|------|------|
| Android 运行时 | ELF 加载器只支持 ET_EXEC 与 static-PIE，拒绝 `PT_INTERP`；用户窗口固定 1 GB（22.3） | 动态链接、bionic、linker、大 VA 与 ASLR 预期 |
| Binder 传输 | `hsipc` 是核内命名通道；`pipe`/`futex` 是进程内设施 | 能力令牌与句柄表、同步会合、跨域共享页、死亡事件（0.8.4） |
| 设备能力 | H-HAL 是核内驱动注册表（函数指针加设备树）；devfs 仅 `null`/`zero`/`fb0`/`console`/`mem` | 面向域的设备授权、共享缓冲、fence、IRQ 事件化、DMA 与 IOMMU |
| HAL 适配 | 无 AIDL/HIDL 运行时，无 VINTF 清单，无 HAL 服务宿主 | HAL 服务进程、注册发现、生命周期、VINTF 生成 |

结论：三条前置各要一个最小闭环。缺任一条，HAL 只能做成同域伪实现，
可演示，不可交付。

#### 0.10.3 前置原语清单（按 HAL 需求倒推）

| 原语 | 服务的 HAL | 最小验收 | 现状 |
|------|------------|----------|------|
| 设备对象与稳定 ID | 全部 | PCI/ACPI/DT 枚举出资源集（MMIO、IRQ、DMA） | 设备树已有，资源字段有限 |
| 能力令牌与每域句柄表 | 全部 | 只授予目标设备；域退出即撤销 | 未提供 |
| 域内 MMIO 映射 | vibrator、light、power、sensors | 寄存器读写生效，越界拒绝 | 未提供 |
| IRQ 事件化 | composer、audio、sensors | 中断变事件，可阻塞等待与超时 | 仅核内回调，未到域 |
| 共享缓冲与格式/修饰符 | gralloc、camera、audio | 跨域分配、映射、释放，格式元数据随缓冲走 | 未提供 |
| fence 与 timeline | composer、camera、audio | 生产者信号、消费者等待，顺序可验证 | 未提供 |
| 快速消息队列（FMQ） | sensors、audio、camera 快路径 | 共享内存加事件通知的无锁环形队列 | 未提供 |
| DMA 与 IOMMU | composer、camera、wifi | 设备只能访问授权窗口 | 无 IOMMU；仅核内 DMA 缓冲原型 |
| evdev 语义 | 输入（非 HAL） | `EVIOC*` ioctl、`input_event`、epoll | 未提供 |
| 热插拔与设备事件 | 全部 | 到达/移除可被域订阅 | 有 hotplug 原型，未到域 |
| 复位与恢复 | 全部 | HAL 崩溃可重启，内核不受影响 | 未提供 |
| 电源、时钟、稳压 | power、audio、camera | 按设备上下电、门控时钟 | 未提供 |

硬约束：无 IOMMU 时不得把可 DMA 设备直接交给用户态域（15.2）。显示与相机
可先用"内核中介缓冲"跑通，但这不是最终形态。

#### 0.10.4 HAL 清单与优先级

| 级别 | HAL | 为什么在这个级别 | 依赖 |
|------|-----|------------------|------|
| T0 骨架 | `servicemanager`/`hwservicemanager`、属性服务、VINTF | 不是 HAL，但注册与发现全靠它们 | Binder 传输 |
| T1 最小闭环 | `vibrator`、`light` | 无缓冲、无 DMA、接口简单，用来验证缝隙 | MMIO 与令牌 |
| T2 显示与音频 | `graphics.allocator`、`graphics.mapper`、`graphics.composer`、`audio.core` | 决定能否有可用桌面与声音 | 共享缓冲、fence、IRQ 事件、DMA |
| T3 输入与电源 | evdev（非 HAL）、`power`、`health`、`thermal` | 输入不是 HAL；其余为可用性必需 | 事件与设备节点 |
| T4 感知与连接 | `sensors`、`camera`、`wifi`、`bluetooth`、`gnss` | 体验核心，但依赖更重 | 缓冲、DMA、固件 |
| T5 通信与安全 | `radio`、`nfc`、`keymaster`、`gatekeeper`、`drm`、`biometrics` | 依赖基带、TEE、许可证，属硬边界 | 厂商与授权 |

#### 0.10.5 关键 HAL 的映射

| HAL | 标准接口要点 | 赫普后端 | 关键原语 | 验收 |
|-----|--------------|----------|----------|------|
| `vibrator`/`light` | AIDL，无缓冲 | 寄存器或 PWM | MMIO 与令牌 | `lshal`、VTS、实际震动或 LED |
| `power`/`health` | AIDL，枚举与回调 | 调度、睡眠、电池与温度 | 设备事件、suspend | VTS、休眠唤醒、读数 |
| gralloc 与 mapper | 分配、导入、lock/unlock、格式与修饰符 | 缓冲对象与域间映射 | 共享缓冲、格式元数据、令牌 | gralloc VTS、跨域往返 |
| composer | display 配置、layer、validate/present、vsync | 显示控制器：plane、mode、vsync | MMIO、IRQ 事件、fence、DMA | SurfaceFlinger 起、合成正确、无撕裂 |
| `audio.core` | stream、port、patch、周期事件 | PCM 环形缓冲、路由、音量 | 共享缓冲、IRQ 事件、时钟 | AudioFlinger 播放与录音回环 |
| `sensors` | multihal、poll 事件队列 | 传感器事件流与时间戳 | FMQ、事件队列 | VTS、framework 读数 |
| `camera` | provider 与 device、每帧请求与 fence | 采集、ISP、3A | 共享缓冲、fence、DMA 与 IOMMU | 虚拟相机预览，再接真传感器 |
| `wifi`/`bluetooth` | AIDL，芯片或 HCI 访问 | 802.11 设备或 HCI 传输 | DMA、固件加载、事件 | 扫描连接、扫描配对 |
| `radio`/`keymaster`/`drm` | AIDL 或 HIDL，厂商实现 | 基带、TEE、Widevine | 厂商专有 | 按授权推进，不设源码级承诺 |

输入需要纠正：触摸与按键不是 HAL。Android `InputReader` 直接读
`/dev/input/event*`，需要的是 evdev 字符设备语义，不是实现一个 HAL。

#### 0.10.6 里程碑与验收

| 里程碑 | 内容 | 验收 |
|--------|------|------|
| M0 冻结 | 定版本、传输、参考设备、HAL 清单与能力矩阵 | 每行有接口版本、后端原语、验收命令、缺口 |
| M1 能力底座 | 令牌与句柄表、MMIO 映射、IRQ 事件、共享缓冲、fence | 两个测试域完成授权、映射、事件、缓冲闭环，越权被拒 |
| M2 传输闭环 | `/dev/binder` 外壳、broker、注册发现、一次 AIDL 往返 | 自编译 HAL 服务可注册，客户端按接口名找到并同步调用 |
| M3 用户态域 | 动态 ELF（`PT_INTERP`/bionic）、init、属性服务、标准 `servicemanager` | 一个现成 HAL 二进制可加载并出现在 `lshal` |
| M4 首个真实 HAL | `vibrator` 或 `light`，接真实设备能力 | `lshal`、VTS、framework 调用三层全过 |
| M5 显示与音频 | gralloc、mapper、composer、audio | SurfaceFlinger 起、图层合成、vsync、音频回环 |
| M6 输入与电源 | evdev、power、health、thermal | 触摸键鼠、休眠唤醒、电量温度 |
| M7 感知与连接 | sensors、camera（虚拟到真实）、wifi、bluetooth、gnss | 各模块 VTS 与 framework 路径 |
| M8 通信与安全 | radio、nfc、keymaster、gatekeeper、drm、biometrics | 按可获得授权推进，明确未获授权项 |

M2 允许先用赫普侧服务注册表承担发现语义，M3 再替换为标准 `servicemanager`。
这只是缩短反馈环，不改变最终形态。

#### 0.10.7 并行与收敛

三条工作流可以并行，但汇合点固定在 M4：

- A 运行时与传输：M2、M3；
- B 设备能力：M1；
- C HAL 契约：按 AOSP 的 AIDL 定义生成桩，写后端适配层，用 B 的测试域验证后端。

契约先行只用于验证注册与调用路径。接口桩必须换成真实设备能力与真实 framework
客户端，才能计入验收。

#### 0.10.8 明确不做

- 不改 AOSP framework、Binder、AIDL 去接赫普原生 IPC：那是平台分支（0.9.5）；
- 不把 HAL 业务写进内核：内核只加通用原语；
- 不把同域伪 HAL、`lshal` 可见当作移植完成；
- 不在无 IOMMU 时给用户态域裸 DMA 权限；
- 不承诺闭源 GPU、基带、TEE、Widevine；
- 不先啃手机 BSP：参考设备从 QEMU 与开发板开始。

#### 0.10.9 第一批具体动作

1. 冻结 0.10.1 三项，写成一页决策记录；
2. 产出 HAL 清单与能力矩阵：每个 HAL 一行，含接口版本、后端原语、验收命令、缺口；
3. 做 M1 能力底座 PoC：令牌、每域句柄、MMIO、IRQ 事件、共享缓冲、fence，
   用两个测试域验证；
4. 并行做 M2 传输闭环：`/dev/binder` 外壳、broker、注册发现、一次 AIDL 往返；
5. 两者汇合后选 `vibrator` 或 `light` 做 M4 首个真实 HAL，跑通 `lshal`、VTS、
   framework 调用三件事。

### 0.11 内核权限模型（修正版）

先把权限定义收窄：**谁，在什么条件下，对哪个资源，执行什么操作**。赫普的分层是：
内核只回答"这个域是否持有该资源的能力"，ABI 层回答"这个应用是否拥有该业务
权限"。两者不能合并，也不能让前者依赖后者。

#### 0.11.1 六条关键修正

| 错误模型 | 为什么错 | 修正 |
|----------|----------|------|
| 内核只管"底层硬件" | 网络、存储、IPC 端点、共享缓冲同样可能被越权占用；只管硬件会让 `INTERNET`、分区存储、fd 传递失去承载点 | 内核管全部可占用资源：设备、内存与缓冲、CPU 配额、IPC 端点、存储卷、fence；网络与存储由服务域持资源能力，应用持服务端点能力 |
| 一个兼容层一个域 | 单域被攻破即继承整域能力，Android UID 沙箱消失 | 每个应用进程与 HAL 服务进程各自成域；应用域不持硬件能力，服务与 HAL 域持有 |
| 兼容层自己签发令牌 | 把 mint 权交给 Android 框架，框架被攻破即可自批硬件能力 | 独立权限 broker 域持有 mint 权；ABI 层只能申请；mint 权本身是能力，按资源类拆分 |
| 吊销令牌即刻失效 | MMIO 已映射、DMA 在途、缓冲已共享时，删句柄不等于停访问 | 撤销是一套协议，见 0.11.3 |
| 令牌是字符串名字 | 名字可猜、可伪造，无法表达权利与约束 | 能力是不可伪造句柄加权利位加约束；名字只用于审计 |
| 兼容层把设备句柄透给上层 | Linux 兼容层的 root 可绕过虚拟 uid 检查直接使用句柄 | ABI 层只暴露虚拟资源；底层句柄留在兼容层或服务域 |

#### 0.11.2 对象、权利与约束

| 能力对象 | 权利 | 典型持有者 |
|----------|------|------------|
| 设备 | probe、mmio、irq、dma、reset、power | 原生驱动或 HAL 服务域 |
| 缓冲 | read、write、map、share、dma | gralloc、camera、audio 服务域 |
| IPC 端点 | send、receive、transfer | broker 与服务域 |
| 服务端点 | call、register | 系统服务域 |
| 存储卷 | read、write、create、delete | 存储服务域 |
| 域管理 | create、destroy、configure | 系统初始化域 |
| 令牌权威 | mint、derive、revoke | 权限 broker 域，按资源类拆分 |

约束项：设备实例、操作范围、时间窗、一次性、用途标签。派生只能衰减，不能放大。
每域一张句柄表，句柄带代际计数，防止释放后重用。

#### 0.11.3 撤销协议

1. 停止向目标域发放新句柄；
2. 句柄表项失效并递增代际；
3. 解除 MMIO 与共享缓冲映射；
4. TLB/EPT shootdown，跨核 IPI；
5. 停设备、等 fence、清在途 DMA；
6. IOMMU 失效并等待完成；
7. 级联撤销由该能力派生的子能力；
8. 向域发送撤销与死亡事件；
9. 写审计记录。

无 IOMMU 时，DMA 类能力不得授予不可信域，只能用内核中介缓冲。任何"一键吊销、
立即生效"的表述都不成立。

#### 0.11.4 信任边界

| 被攻破对象 | 最坏后果 | 不能获得 |
|------------|----------|----------|
| 内核 | 全部资源 | 无 |
| 权限 broker | 该类资源的签发权 | 其他资源类 |
| Android framework | 应用级权限判定与已授权限的代申请 | 未经用户同意的新硬件能力，前提是同意权威在原生域 |
| HAL 或系统服务 | 该类设备 | 其他设备类 |
| 应用 | 自身数据与服务调用 | 任何直接硬件能力 |

前提：同意权威必须独立于被约束对象。若把"用户已同意"的判定交给 Android
framework，则 framework 被攻破即可代申请，隔离叙事退化。

#### 0.11.5 用户同意与面板

- 两层同意：Android 应用权限由 PMS 判定，设备级授权由 broker 记录。高风险设备
  （相机、麦克风、定位）以原生同意域为准；其余可由 Android 弹窗触发。
- 同一资源只保留一个用户可见的最终确认点，不允许双重弹窗。
- 能力分两类：可撤销（相机、麦克风、定位）与基础（显示、输入、存储）。
  基础能力不允许用户面板随手吊销，否则合成器与系统服务会崩。
- 面板展示域、能力、持有者、最近使用与派生链，不只展示一个开关。

#### 0.11.6 与现状的差距（不得混为一谈）

- 64 位主线编入 `hsipc.c`、`hsservices.c`、`drv_register64.c`、`drv_mgr64.c`、
  `storage_hal64.c`、`network_hal64.c`；未编入 `kernel/security/*`、
  `kernel/hal/*`、`kernel/fs/devfs.c`。
- 32 位原型把 Android 风格权限枚举与校验放在核内：`permission_manager.h`、
  `permission_manager.c`，并被 `kernel/sched/mobile*.c` 直接调用；`security.c`
  还有路径级 MAC。
- 迁移方向：冻结新增的内核业务权限；把业务判定移到原生权限服务或兼容层；
  内核只保留域、能力、句柄、撤销、审计与配额。原型代码在替代实现就绪前可保留，
  但不得进入 64 位主线，也不得作为对外能力表述。

#### 0.11.7 明确不做

- 不在内核增加 uid/gid/cap 或 `android_camera_permission` 一类业务权限；
- 不允许字符串令牌与"按名字查找"的授权；
- 不允许 ABI 层自行签发硬件能力；
- 不允许把底层句柄透给不可信程序；
- 不在无 IOMMU 时给不可信域裸 DMA。

权限模型的验收标准不是"有没有权限弹窗"，而是"撤销协议能否在跨域缓冲与 DMA
在途时仍然生效"。

### 0.12 系统 AI 服务（`hepua`）

AI 在赫普的定位是**可选的高权限租户**，不是内核功能。它用统一契约向原生、
Linux 兼容层与 Android 兼容层提供受控的模型能力；但它拿不到不该拿的数据，
发不出未经授权的动作，也出不了未经同意的网。

判定三句话：

1. 不进内核：内核不解析 prompt、不持 token、不加载模型、不做 AI 路由；
2. 不做全局数据经纪商：数据能力留在数据拥有者域，AI 只拿一次性只读快照；
3. 不绑定厂商：契约稳定，后端可插拔，远端与本地二选一。

#### 0.12.1 "一等公民"的判据

"一等公民"指契约地位，不是内核依赖。满足以下六条才算：

| 判据 | 含义 | 反例 |
|------|------|------|
| 稳定服务名与版本化契约 | 调用方按契约编程，不按厂商 schema | 直接暴露单一厂商 JSON |
| 能力门禁 | 每次调用都过权限 broker | 装完即用的全局 AI |
| 独立生命周期 | 可启动、停止、崩溃、缺席 | 开机依赖 AI 服务 |
| 审计与配额 | 每域可查、可限流、可计费 | 无审计的共享密钥 |
| 跨 ABI 有绑定 | 原生、Linux、Android 各有绑定层 | 只给原生程序用 |
| 后端可插拔 | 远端/本地、不同厂商可替换 | 硬编码单一模型 |

缺任何一条，都只是"系统里带了个 AI 应用"，不是系统能力。

#### 0.12.2 分层

```
应用 / Linux 兼容层 / Android APK
  ↓ 三类绑定：libhepua / 兼容层 shim / Android 系统服务
hepua 服务域（会话、路由、配额、审计）
  ├─ 上下文提供者（诊断/日志/文件/进程），各自持数据能力
  ├─ 工具 broker，按工具发能力，危险操作需确认
  ├─ egress proxy，持网络能力与 provider 密钥，负责脱敏与出境策略
  └─ 推理后端域，本地模型，默认无网络，持 GPU/NPU 能力
内核：通用 IPC、能力裁决、域配额、撤销与审计事件；不含任何 AI 逻辑
```

内核只提供 0.11 的通用能力模型；`hepua` 是用户态服务契约，不是 syscall。
AI 服务域不持数据能力、不持 provider 密钥、不直接执行工具。

#### 0.12.3 能力与数据边界

沿用 0.11.2 的对象模型，AI 相关能力单独列出：

| 能力 | 权利 | 持有者 | 约束 |
|------|------|--------|------|
| AI 服务端点 | call、cancel、subscribe | 应用域（经绑定层） | 服务缺席时返回不可用，不阻塞调用方启动 |
| 上下文快照 | read、expire | 诊断/日志/文件/进程服务域 | 一次性、只读、带范围与用途；不暴露源对象句柄 |
| 工具 | invoke、confirm | 工具 broker 域 | 模型输出不可信；危险操作需用户确认 |
| 出网通道 | connect、send | egress proxy 域 | provider 密钥不离开该域 |
| 模型卷 | read、verify | 推理后端域 | 只读、签名校验、版本化 |

四条硬规则：

1. AI 服务不持有数据能力；上下文由拥有者域生成只读快照，AI 只消费快照；
2. 上下文用快照句柄，不用源对象句柄；可过期、可撤销；
3. AI 服务不得 `mmap` 其他域内存，也不得持有全局诊断能力；
4. 模型输出视为不可信输入；工具调用是能力请求，不是动作，必须经工具 broker。

prompt injection 的边界不在模型，而在工具 broker：模型能"请求"什么，由工具
能力集决定；模型不能"直接"做什么。

#### 0.12.4 三类 ABI 绑定

统一的是契约，不是绑定方式：

| ABI | 绑定 | 身份归属 | 约束 |
|-----|------|----------|------|
| 原生 | `libhepua` → 服务 IPC | 域 ID | 直接申请能力 |
| Linux 兼容层 | 兼容层内 shim | 虚拟 uid 映射到 scope | 兼容层中介，不把底层句柄透给程序 |
| Android | Android 系统服务/AIDL + 运行时权限 | 应用域归属 | 桥接层代申请；高风险设备以原生同意域为准 |

Android 侧沿用 0.11.5：PMS 做应用语义判定，设备级授权由 broker 记录。framework
仍在 TCB 内，因此不能把"用户已同意"的判断交给它单独完成。

#### 0.12.5 出网与本地推理

远端模式：

- 默认关闭，逐 provider 显式授权；
- 禁止本地失败后静默回退远端；
- 出境前脱敏，界面有可见指示；
- provider 密钥只存在 egress proxy 域；
- 审计默认记域、范围、provider、token 数、内容哈希与策略决定，不记全文。

本地模式：

- 独立域，默认无网络能力；
- 模型卷只读、签名校验、版本化；
- 内存、功耗、热预算按域配额；
- GPU/NPU 为单独能力，不随 AI 服务自动授予；
- 推理框架是攻击面，必须沙箱；闭源 NPU 驱动按厂商授权推进，不做源码级承诺。

#### 0.12.6 最小契约

六个核心操作，工具调用走独立 broker：

| 操作 | 语义 | 关键约束 |
|------|------|----------|
| `Open` | 按模型类与策略开会话 | 不指定厂商，按能力类选择 |
| `Submit` | 提交输入引用与参数 | 输入是上下文快照句柄，不是裸数据 |
| `Stream` | 订阅增量、工具请求、用量、结束、错误 | 事件有类型，不复用厂商 JSON |
| `Cancel` | 取消请求 | 幂等 |
| `Close` | 关闭会话 | 释放配额与快照 |
| `Describe` | 查询模型类、能力与配额 | 不泄露 provider 密钥 |

工具 broker 单独一个 `Invoke`：参数校验、能力检查、必要确认、审计。契约只定义
语义与能力要求，不定义传输编码；编码由绑定层决定。

#### 0.12.7 阶段与验收

| 阶段 | 范围 | 验收 | 不做 |
|------|------|------|------|
| 现在 | 契约、威胁模型、数据分级 | 文档评审通过；不写实现 | 不做服务、不做模型、不改内核 |
| Alpha | 仅原生调试工具（如 `explain-panic`），开发者模式，远端经 egress proxy | 默认拒绝成立；审计可查；AI 缺席不影响启动 | 不向 APK/Linux 开放，不做本地模型 |
| Beta | 本地推理、Linux shim、Android 系统服务与运行时权限 | 本地模式无出网；撤销生效；APK 身份归属正确 | 不做自适应调度 |
| v1 | 桌面助手、窄能力策略 agent | opt-in、可逆、全程审计 | 不把 AI 设为开机依赖 |

#### 0.12.8 与现状的差距

- 64 位主线尚无 AI 服务、`hepua`、推理后端或模型卷；本节定义的是契约与边界，
  不是已具备能力，对外不得表述为"系统级 AI 已实现"。
- 不新增内核 AI syscall，不为 AI 修改调度器；AI 只使用 0.11 的通用能力模型。
- 自适应能力属于独立策略 agent，不能由通用 AI 服务直接改调度、缓存或窗口布局。

#### 0.12.9 明确不做

- 不把 AI 写进内核，不在内核解析 prompt、token 或模型；
- 不让 AI 服务持有全局数据能力或 provider 密钥；
- 不让模型直接执行系统动作；
- 不做本地到远端的静默回退；
- 不默认记录全文 prompt；
- 不承诺闭源 NPU/GPU 驱动支持；
- 不把 AI 设为开机依赖。

AI 服务的验收标准不是"能不能聊天"，而是四条：默认拒绝是否成立、数据是否最小化、
工具是否经授权、出境是否可见。

### 0.13 图形攻击面与无头模式

结论先行：**无头模式的价值是缩小攻击面，不是"更安全"的证明。** 图形栈不启动，不等于
图形驱动不可达；只有显示、输入、合成与 GPU 驱动都不被加载、相关能力不被签发时，
"无头"才成立。当前 `hepu_nographics` 只是运行时跳过桌面初始化，属于最弱的一层。

#### 0.13.1 三种"无头"不是一回事

| 层级 | 做法 | 生效时机 | 当前状态 | 主要缺口 |
|------|------|----------|----------|----------|
| L0 运行时跳过 | `hepu_nographics=1` 时 `desktop64_init` 直接返回 | 运行时 | 已存在该变量与检查 | 图形代码仍在镜像中；`gui` 命令可反开 |
| L1 构建期无头 | 不把图形、桌面、字体、输入、显示驱动编入镜像 | 构建期 | 未实现 | 无裁剪开关；无产物差异校验 |
| L2 用户态图形域 | 图形栈在独立域，无头镜像不启动该域 | 架构目标 | 未实现 | 无用户态合成器；无输入/显示/GPU 能力门禁 |

三层是叠加关系，不是替代关系：L1 是发布形态的最低要求，L2 是架构目标，L0 只适合
开发调试。任何一层都不能替代对网络、文件系统、IPC 与驱动攻击面的处理。

#### 0.13.2 启动 profile

沿用已有的启动参数通道（`hepu.safe`、`hepu.recovery` 已走同一路径），新增两个参数：

| 参数 | 取值 | 语义 |
|------|------|------|
| `hepu.profile` | `headless` / `desktop` / `game` | 本次启动加载的服务集合 |
| `hepu.display` | `none` / `fb` / `gpu` | 显示后端；`none` 表示不初始化任何显示设备 |

规则：

- 只解析一次，启动期冻结；运行期不得改写 profile，切换只能重启；
- `profile=headless` 与 `display!=none` 视为配置冲突，按更严格的 `display=none` 执行并记录；
- `profile=headless` 下 `gui` 命令必须拒绝，不得把 `hepu_nographics` 置 0 后启动桌面；
- `profile=game` 只表示服务集合与显示偏好，不构成帧率、延迟或反作弊承诺。

`hepu.profile` 与 `hepu.display` 目前均未接入启动参数解析；现有 `hepu_nographics`
注释中的参数名只是命名约定，不是可用参数。

#### 0.13.3 无头要关什么、保留什么

| 面 | 无头时 | 说明 |
|----|--------|------|
| 显示与帧缓冲 | 不初始化 | 不签发显示设备能力 |
| 本地输入（键盘/鼠标/触摸） | 不启动输入域 | 不等于关闭串口或带外管理 |
| 合成器与桌面 | 不启动 | 图形域不创建 |
| 剪贴板 | 不启动 | 无图形会话则无共享剪贴板 |
| 通知与托盘 | 不启动 | 不产生弹出与焦点抢占 |
| GPU/DRM 驱动域 | 不加载 | 无 IOMMU 时不得向不可信域直通 DMA/MMIO |
| 串口控制台 | 保留 | 恢复与诊断入口 |
| 网络管理 | 保留，受能力约束 | 管理面不能退化为无认证通道 |
| 日志与监控 | 保留，只读聚合 | 经用户态服务，脱敏与限流 |

要点：无头不等于"关掉所有输入与网络"。它指**没有本地图形会话**；服务器形态仍需串口、
带外管理与受控远程管理。反过来，无头也不消除网络、文件系统、IPC 与驱动的攻击面。

#### 0.13.4 与现状的差距

| 能力 | 现状 | 差距 |
|------|------|------|
| `hepu_nographics` | 在 `desktop64.c` 定义并在 `desktop64_init` 检查 | 未解析启动参数；默认 0；仅运行时生效 |
| `gui` 命令 | 在 `shell64.c` 中置 0 并启动桌面 | 可绕过无头约束，且无审计 |
| 图形代码编入 | `vg64.c`、`desktop64.c`、`font64.c` 在 64 位主线 | 无构建期裁剪，L1 不成立 |
| 合成与桌面 | 核内 HepuShell 渲染 | 无用户态合成器域 |
| 输入 | PS/2 与 USB HID 在核内轮询 | 无输入域，无按域能力门禁 |
| GPU/DRM/IOMMU | 无 | 不能向不可信域直通图形设备 |

#### 0.13.5 迁移顺序与验收

1. 接入 `hepu.profile` 与 `hepu.display`，启动期冻结，并记录来源与最终取值；
2. `profile=headless` 下拒绝 `gui`，对所有运行时反开通道逐一列出并封死；
3. 增加构建期无头产物：不编入图形、桌面、字体、HepuShell 与本地输入代码；
4. 无头启动不创建合成器、剪贴板、通知与 GPU 域，不签发显示/输入/GPU 能力；
5. 无 IOMMU 时，GPU 设备不得直通不可信域；驱动域与用户域分离；
6. 验收：无头镜像无图形初始化日志；`gui` 被拒绝并留审计；显示与 GPU 驱动未加载；
   `desktop` 与 `game` profile 不受影响；profile 切换只能通过重启完成。

#### 0.13.6 明确不做

- 不把无头模式当作安全认证、安全模式或"高安全"卖点；
- 不把无头等同于关闭全部输入与网络；
- 不把赫普定位改写为"服务器操作系统"，主定位仍是个人终端；
- 不做运行时 headless 与 desktop 的静默切换；
- 不在无头 profile 加载 GPU/DRM 驱动或签发显示能力；
- 不因无头删除文本控制台、串口与恢复入口。

### 0.14 双视图与开发者模式

结论先行：**同一套内核能力、隔离域与监视数据，两种视图。** 视图只决定"展示多少、
开放哪些入口"，不改变授权；开发者模式不是全局开关，而是认证后签发的限时调试会话。
把视图切换当成权限边界，是这一块最容易犯的错误。

#### 0.14.1 五条铁律

1. 视图只做展示过滤，不改变内核调度、隔离与权限裁决；
2. 开发者模式不改变内核行为，只额外签发观测与干预能力；
3. 两种视图共用同一数据源，界面不得直读内核进程表，也不得用占位数据充数；
4. 普通视图默认最小信息、最小打扰；开发者视图默认完整、可追溯；
5. 关闭开发者模式必须撤销调试能力，追踪停止、入口隐藏、已发放句柄失效。

#### 0.14.2 四层职责

| 层 | 职责 | 禁止 |
|----|------|------|
| 内核 | 通用 `stat`/`event` 能力、受保护操作裁决 | 定义"应用"、生成业务权限文案 |
| monitor 服务 | 唯一只读快照、应用组聚合、脱敏、限流、审计 | 直读内核结构、伪造数据 |
| 视图层 | 普通/开发者两套渲染，只做过滤 | 决定授权、直接改调度 |
| debug broker | 认证、限时调试能力、trace/dump/restart 签发与撤销 | 把调试能力等同于 root |

#### 0.14.3 普通用户视图：应用是第一主体

- **应用组不是内核概念**。内核只有域与进程；monitor 按包身份、域集合与进程集合聚合，
  兼容层内部线程与子进程折叠进应用组。
- 应用卡片只展示：资源占用、是否异常、停止、权限设置；标签（原生 / Linux / 安卓）
  来自 `env_type` 与包元数据，不靠进程名猜。
- 权限文案由 broker 元数据生成：资源类、风险等级、作用域、是否可撤销。界面只渲染，
  不手写"允许 fd / mmap / DMA"这类底层名词。
- 资源提醒只在持续占用时出现，最多两个动作：【限制资源】【忽略】；不向普通用户投放
  内核 panic、ABI 报错或加载栈。
- 资源模板（办公 / 游戏 / 安静）由 QoS 服务执行（见 0.15），界面不直接改优先级。
- 跨域剪贴板与文件选择默认关闭，用户显式确认后才允许跨域传输。

#### 0.14.4 开发者视图：可观测、可干预、可追溯

- 域树、进程/线程、阻塞原因、句柄、驱动、syscall 与 QoS 标签，全部来自 monitor 的
  同一快照与事件流；图形选中对象后可在 Shell 中继续追踪。
- 危险操作（终止域线程、dump 内存、改配额、重挂兼容 rootfs）需二次确认并留审计；
  内核基础驱动与核心域默认拒绝终止，除非额外持有 `unsafe_debug` 能力。
- 日志分四级：用户日志 / 应用日志 / 兼容翻译日志 / 内核日志。普通视图只收前两类；
  开发者视图可按域、进程过滤订阅。
- 兼容层调试项（翻译失败、ABI 不匹配、独立 rootfs、缺少接口模拟）属于用户态工具，
  不进内核。
- 热重载与 ELF 符号/重定位面板是用户态工具，不是内核功能。
- Shell 形态：当前 64 位 Shell 在核内用 C 实现；目标态是用户态 Shell。结构化 Shell
  （如 Nushell）只能作为用户态前端，不作为内核依赖。图形与无头（见 0.13）共用同一
  套命令与数据源。

#### 0.14.5 开发者模式的正确形态

开发者模式是一个**调试会话能力**，不是 `hepu_dev_mode` 这样的全局整数：

| 属性 | 要求 |
|------|------|
| 主体 | 绑定认证后的会话与域，不是全局可见 |
| 会话 | 图形桌面与串口各持一份，互不继承；一个会话开启不影响另一个 |
| 范围 | 明确可观测对象与可干预操作，最小授权 |
| 时限 | 有有效期，超时自动撤销 |
| 可撤销 | 关闭即撤销，trace/dump 句柄立即失效 |
| 审计 | 开启、使用、撤销全部留痕 |
| 入口 | 设置界面需验证；`hepu.dev=1` 仅开发镜像或本地控制台可用，生产镜像拒绝 |

`hepu_dev_mode` 这类全局整数只能作为兼容期的界面缓存，不能承担授权判定；判定必须
落在会话持有的调试能力上。

开发者 ≠ root。调试能力不等于管理能力；内核基础驱动、核心域与内存保护不因调试会话
而放开。

#### 0.14.6 与现状的差距

| 能力 | 现状 | 差距 |
|------|------|------|
| 视图开关 | `hepu_dev_mode` 为全局 `int`，`hepu hep dev on/off` 可任意切换 | 无认证、无时限、无审计，不是能力 |
| 进程数据 | `ps` 已改用 `process64_snapshot`；图形任务管理器仍读 `user_process_list`（8 槽），`gtop` 为硬编码文案 | 快照未统一，图形与 Shell 数据不可比 |
| 应用组 | 内核只有域与进程 | 无包身份与聚合层 |
| 权限文案 | 无权限 broker 元数据 | 无法生成"人话权限" |
| 资源模板 | `mode office\|game\|quiet` 只打印文案 | 未接 QoS 服务 |
| 日志分级 | 全部混在 VGA 控制台 | 无用户态日志服务与过滤 |
| 剪贴板 | 仅 32 位 `kernel/sched/share.c`，未进 64 位主线 | 无跨域确认与能力门禁 |
| 系统 AI | 不存在（见 0.12） | `hep explain` 为占位 |

#### 0.14.7 迁移顺序

| 阶段 | 内容 | 验收 |
|------|------|------|
| P0 | 统一 `stat` 快照；`ps` 已迁移；把图形任务管理器与 `gtop` 迁到同一快照 | 两种视图读同一份数据；无影子结构与越界循环 |
| P1 | 用户态 monitor、应用组聚合、资源提醒 | 应用卡片数据可追溯到域与进程；普通视图不暴露内核指针 |
| P2 | 用调试会话能力替换 `hepu_dev_mode`；认证、时限、撤销、审计 | 关闭后 trace/dump 立即失效；未认证不可开启 |
| P3 | 权限文案元数据、QoS 模板、日志分级、跨域剪贴板、无头同源工具链 | 权限文案与真实能力一致；模板真实改变调度 |

#### 0.14.8 与启动形态的边界

- 视图切换是会话内的展示与能力变化，不重启内核、不重启系统；
- `headless`/`desktop`/`game` 是启动 profile，启动期冻结，切换需重启（见 0.13）；
- 两者不得互相替代：无头镜像可以在串口会话开启开发者视图，桌面镜像也可以在图形
  会话保持普通视图。

#### 0.14.9 明确不做

- 不做两套独立桌面或两套割裂系统，只做视图过滤；
- 不把开发者模式当 root，不因调试放开内存保护与核心域；
- 不让界面直读内核 `process_t` 或暴露内核指针；
- 不在普通视图使用硬编码、占位或推测数据；
- 不用全局布尔量作为授权边界；
- 不把 Nushell/Rust 作为 64 位内核 Shell 的依赖；
- 不声称 trace、dump、热重载或 AI 诊断已可用。

### 0.15 生产力与游戏 QoS

结论先行：**内核不做业务策略，只提供通用资源类与执行机制；策略在用户态 QoS 服务。**
游戏是延迟敏感负载，不是实时负载；把游戏设成 RT 会破坏系统可调度性。

#### 0.15.1 通用资源类

| 类 | 适用 | 约束 |
|----|------|------|
| `latency` | 前台交互、输入响应、音频 | 低延迟优先，但不无限抢占 |
| `throughput` | 编译、批处理、大文件复制 | 允许较长连续时间片 |
| `background` | 更新、索引、清理 | 仅在无更高类就绪时运行 |
| `ai` | 本地推理 | 默认低于前台交互，可被暂停 |
| `rt` | 内核与驱动的短临界区 | 不开放给普通应用域 |

游戏归入 `latency`，不是 `rt`。办公模板=前台 `latency` + 后台 `background`/`ai` 降速；
安静模板=暂停 `background` 与 `ai`。三者都是策略组合，不是内核枚举。

#### 0.15.2 执行机制

| 机制 | 语义 | 归属 |
|------|------|------|
| 域权重 | 按域分配 CPU 份额 | 内核执行，参数由 QoS 服务设定 |
| 周期预算 | 每周期 CPU 时间上限 | 内核执行 |
| 预留 | 为关键域保留最低带宽 | 内核执行 |
| 亲和 | 绑定 CPU 集合 | 内核执行 |
| 内存与 IO 限额 | 按域配额 | 内核执行 |

参数变更必须经能力校验并审计；QoS 服务只持策略权，不持设备能力。

#### 0.15.3 现状差距

| 能力 | 现状 | 差距 |
|------|------|------|
| 优先级 | 32 位三档 `RT/NORM/BKG`；64 位 `int priority` | 无域权重、周期预算、预留 |
| 内存限额 | 32 位 `uint32_t mem_limit` 按字节；64 位 `uint64_t mem_limit` 按页 | 单位不一致，跨 ABI 不可比 |
| 策略入口 | `mode office\|game\|quiet` 仅打印文案 | 未接 QoS 服务 |
| 域聚合 | 只有 `env_type` 分组 | 无域级 QoS 对象与统计 |
| 图形 | 无 GPU/DRM 驱动 | 无帧节拍与 GPU 优先级可谈 |

#### 0.15.4 阶段

| 阶段 | 内容 | 验收 |
|------|------|------|
| P0 | 统一内存限额单位与字段；补域级资源统计 | 32/64 位口径一致，可跨 ABI 比较 |
| P1 | 域权重、周期预算、预留；QoS 服务最小接口 | 参数真实生效，可查询、可回滚 |
| P2 | `latency` 类与前台识别；三个模板接真实策略 | 模板改变调度而非打印文案 |
| P3 | 游戏场景验证、审计与回滚 | 有可复现的前后对比，不依赖厂商承诺 |

#### 0.15.5 明确不做

- 不把游戏设为 RT，不按进程名或游戏名单硬编码；
- 不承诺 Proton、Steam、Docker、CS2 反作弊或 12G 显存上限；
- 不在没有 GPU 驱动时承诺帧率、帧节拍或 GPU 优先级；
- 不让 AI 服务直接修改调度策略；
- 不做静默策略覆盖，所有模板必须可查、可撤销。

## 1. 系统基础信息

### 1.1 系统名称
- 全称：**HEPU Hyper Evolve OS 赫普超感操作系统**
- 简称：**赫普OS / HEPU OS**

### 1.2 命名释义
- **赫**：赫然革新、突破壁垒、性能显赫，代表打破传统移动系统架构垄断
- **普**：普惠自由、全员可控、全设备通用，代表极致开放与用户平等
- **HEPU**：Hyper Evolve Pure Union（超进化·纯净·统一系统）

### 1.3 系统定位
面向下一代智能移动终端的自研微内核操作系统。
核心理念：**用户主权优先、AI原生驱动、安全自由共存、全设备统一生态**。
其中"AI原生驱动"指系统级 AI 契约与服务定位（见 0.12），不代表内核内置 AI。
对标替代：安卓、iOS传统双系统体系（长期愿景；阶段执行口径见 1.6，本原准则见 0）。

### 1.4 核心口号
**系统归人，数据归己，自由可控，极致纯净**

### 1.5 能力表述规范（优势、潜力与边界）

> 对外介绍、README、市场材料统一遵循本节，禁止把"目标"写成"已具备"。

**事实基线（0.54.6）**
- 64 位内核主线为 **C**；Rust 目前只用于用户态服务（`user/rust`，i686 目标），
  64 位构建不含 Rust；
- 64 位图形为帧缓冲 + 桌面绘制，无 Vulkan 驱动/合成器；
  `gfx2` 仅为 32 位树中的 API 常量与设备信息骨架；
- VFS、trace/perf、VMA 等模块位于 32 位树或仅有头文件，未接入 64 位主线；
- 已落地安全基础：seccomp strict/filter、每进程 fd 表、COW、栈保护。

**可对外宣称的优势（有代码依据）**
1. 内核主干保持自有模型，不复制 Linux 内部结构；
2. 兼容采用边界翻译策略，原生 ABI 可独立演进；
3. 已建立源码级 POSIX 路径，C/Rust 源码重编译门槛低；
4. 兼容层按进程环境开关（`ENV_LINUX_COMPAT`），不拖累原生程序；
5. 兼容层与原生应用共用同一沙箱边界（约束二）；
6. 可称"**C+Rust 混合系统**"：C 内核主干 + Rust 用户态工具/服务。

**只能表述为"潜力/目标"**
- "C+Rust 混合内核"或"内核核心子系统用 Rust 写"：Rust 尚未进入 64 位内核；
- "内存/调度/兼容/图形/权限子系统由 Rust 写"：当前均为 C；
- "Vulkan 底座""Win32 兼容""完整 Linux 二进制兼容"：尚未实现；
- "task 扩展字段 / VFS compat_ctx / VMA 分层标记 / tracepoint / vDSO 预留"：
  多数未落地（现状见 14.1）；
- 任何具体性能损耗百分比。

**表述红线**
- 可以称"**C+Rust 混合系统**"，但必须注明 Rust 当前在用户态；
- 在 Rust 进入内核前不称"Rust 内核"或"内核核心子系统由 Rust 写"；
- 不在驱动/合成器落地前称"Vulkan 底座"；
- 不做"安全上碾压 BSD""比 Linux 更安全"等无法验证的横向断言；
- 兼容等级与性能数据一律以实测为准（约束三）。

**优势的正确落点**
相对 Linux/BSD/Redox/Windows 的差异化，应落在可验证事实：自有 ABI 与干净边界、
C 硬件生态对接能力、兼容层可选可关、开源可控；而不是"语言组合自动带来安全/兼容"。

**风险**
一旦内核内部直接复用 Linux 结构体、散写兼容分支、扩大 unsafe，
上述优势即失效；这与 3.4 结论五的 A 决策一致：兼容翻译不得留在内核主干。

### 1.6 目标用户与阶段定位（评估结论）

> 本节区分"现在能服务谁"与"长期想服务谁"，避免用远景替代当前验收标准。

**三层用户**
1. **种子用户（当前可服务）**：操作系统/内核爱好者、C/Rust 开发者、
   自托管与轻量服务器/嵌入式玩家。前提是能稳定启动、shell、基础工具链可用、
   构建文档完整；
2. **潜在用户（需先补硬件与稳定性）**：桌面普通用户。门票不是 syscall 翻译，
   而是 GPU、音频、USB/输入、睡眠、包管理、更新回滚；
3. **基本不会主动迁移**：重度 Windows 闭源软件用户、零排错小白、
   无厂商支持与合规认证的企业生产环境。

**两条路线**
- **路线 A（建议早期采用）**：开发者/专用系统。验收标准是稳定启动、
  NVMe/网卡/串口可用、内核可裁剪、文档完善、提供虚拟机镜像；
  兼容层定位为可选实验功能；
- **路线 B（长期目标）**：桌面日常系统。硬门槛包括 GPU 驱动稳定（AMD 优先）、
  图形/音频/蓝牙/睡眠正常、兼容层可稳定跑浏览器与游戏、包管理与故障回滚、
  桌面体验统一。任一短板都会让普通用户试用一次即流失；
- 早期不同时铺两条战线；路线 B 以路线 A 的稳定性为前提。

**现状与门槛（0.54.6）**
- 已有：帧缓冲与桌面绘制、PS/2/USB 输入、AHCI/IDE、AC97、RTL8139/e1000、
  ext2、shell、镜像/ISO 构建脚本；
- 缺口：GPU/DRM/合成器、音频与蓝牙的真实设备验证、电源管理/睡眠、
  包管理与更新回滚、真实硬件回归；
- 结论：当前能力更接近路线 A 的可用性，尚未达到路线 B 的门槛。

**兼容层的能力边界**
兼容层只解决"软件有没有"，不解决"硬件稳不稳"。Linux 图形/音频程序还依赖
DRM、evdev、ALSA、udev 等语义；这些子系统缺失时，即使 syscall 翻译完善，
程序仍会黑屏或无声。桌面路线必须先补驱动子系统，而不是先扩大 syscall 覆盖。

**提高采用率的落地顺序**
1. 定位为"补充型系统"，不喊替代 Linux/Windows/安卓；
2. 先稳住一个场景（路线 A），兼容层明确标注实验性；
3. 提供虚拟机/ISO 一键镜像与已知问题清单；
4. 差异化只用可测指标（内存占用、权限模型、输入延迟），实测后再宣传；
5. 构建文档、故障排查与已知问题优先于兼容覆盖率。

**表述红线**
- 不以"Rust 内核 / 内核核心子系统由 Rust 写"作当前卖点；
  "C+Rust 混合系统"可用，但需注明 Rust 当前在用户态（见 1.5）；
- 不以"可替代 Linux/Windows/安卓"作初期承诺；
- 不把"能跑 Linux ELF"等同于"桌面可用"；
- 兼容等级一律按约束三实测标注。

### 1.7 对外沟通、社区定位与许可证（评估结论）

**沟通对象分层**

| 对象 | 关注点 | 预期态度 | 应对 |
|------|--------|----------|------|
| 内核核心维护者 | 是否解决新问题、有无可复用产出 | 理性审视，不站台 | 用文档/基准/工具说话，不用口号 |
| Rust/内核爱好者 | 架构是否干净、边界是否清晰 | 友好，首批贡献者 | 公开设计、保证可构建、欢迎 patch |
| 发行版维护者 | 稳定性、维护负担 | 中立观望 | 不主动求打包，先把稳定性做出来 |
| 桌面普通用户 | 能否日常使用 | 只看体验 | 不以兼容层宣称可替代 Linux |
| 保守社区 | 是否重复造轮子 | 质疑，声音大但非主流 | 不争辩，明确互补定位 |

**统一对外口径（当前事实版）**

> 赫普OS 是一套 **C+Rust 混合的自研 POSIX 操作系统**：
> 内核主干为 C，Rust 用于用户态工具/服务；走原生 POSIX 路线，
> 规划按进程可选的 Linux ELF 兼容层（实验性）。
> 不宣称替代 Linux、Windows 或安卓。

"混合"指 C 内核 + Rust 用户态，不指 Rust 已进入内核；
"Rust 内核 / 内核核心子系统由 Rust 写"仍属未实现项（事实基线见 1.5）。

**社区策略**
1. 不喊替代，定位为互补/补充型系统（与 1.6 一致）；
2. 兼容层标注实验性，兼容等级按约束三实测；
3. 公开构建文档、已知问题与失败清单，提供可一键运行的虚拟机/镜像；
4. 优先产出可复用成果：ABI 文档、errno 映射表、seccomp 设计、基准与回归工具；
5. 不与保守声音争论"是否重复造轮子"。

**许可证与法律边界**
- 现状：README 声明核心代码 **GPLv3**，但许可证尚未正式确定；
  [6.2 开源协议](#62-开源协议) 写的是"GPLv3 核心内核 + 附加商业约束补充条款"；

  公开发布前必须补齐；

- ABI 兼容本身不构成侵权；红线是不复制 Linux 内核源码与内部实现，
  架构上不加载 Linux `.ko`（见 15）。

**表述红线**
- 不复制 Linux 内核代码；
- 不宣称"替代 Linux"；
- 不在 Rust 进入内核前称"C+Rust 混合内核"；
- 不把"能跑静态 ELF"等同于"兼容 Linux 软件"。

## 2. 系统总体架构设计

赫普OS采用**自研微内核分层隔离架构**，区别于安卓宏内核、iOS半封闭内核。

整体分为四层：

```
┌─────────────────────────────────────────────┐
│  应用与交互生态层                            │
│  (.hug原生应用 / APK兼容沙盒 / 桌面UI)       │
├─────────────────────────────────────────────┤
│  AI原生系统基座层                            │
│  (本地推理 / 跨应用服务 / 算力调度)          │
├─────────────────────────────────────────────┤
│  系统基础服务层                              │
│  (文件/网络/图形/电源/隐私沙盒/H-HAL)        │
├─────────────────────────────────────────────┤
│  核心微内核层                                │
│  (进程调度 / 内存隔离 / 硬件中断 / 权限总控) │
└─────────────────────────────────────────────┘
```

### 2.1 内核层
自研纯微内核，不基于Linux / Unix。内核仅处理四项最基础工作：
1. 进程调度管理
2. 内存隔离分配
3. 硬件中断响应
4. 系统最高权限总控

图形、网络、文件系统、音频、AI推理全部运行在**用户态系统服务**，不跑在内核态。

- **故障隔离**：单个应用、单个用户态服务崩溃，不会造成整机死机重启
- **攻击面极小**：内核代码精简，漏洞风险显著降低

> **实现状态**：微内核定位覆盖 32 位与 64 位内核。用户态服务框架已存在
> （服务注册、IPC、`services/` 下的文件/网络/图形/隐私服务），但 64 位主线
> 仍有 ext2、网络、图形/桌面等核内实现作为过渡路径，尚未全部下沉。
> 对外表述使用"微内核架构 + 服务逐步下沉"，不称"所有服务已在用户态"。

### 2.2 系统基础服务层
所有非内核基础能力模块化运行在此层：
- **H-HAL赫普硬件抽象层**：实现新老设备兼容，基础镜像与机型驱动包H-DPK解耦
- 文件服务、网络服务、图形合成服务、电源功耗管理
- 隐私沙盒、用户数据金库服务，统一管控所有应用权限与数据访问
- APK兼容沙盒服务，负责安卓应用隔离运行

**硬件适配机制**：
完整系统 =【赫普OS通用基础镜像】+【H-DPK机型设备适配包】
基础镜像一套通用，不同机型只需维护体积较小的H-DPK适配包。

### 2.2.1 Shell 与终端（概念边界）

- **Shell**：用户态命令解释器，解析命令、调用系统调用、启动其他程序；
- **终端 / tty**：字符输入输出的设备抽象，负责回显、信号、窗口大小等；
- **终端模拟器**：运行在终端之上的图形窗口程序，和 Shell 不是一回事。

赫普的设计边界：

- 原生 Shell 是一等用户态程序，绑定赫普原生 ABI，不承诺 POSIX/bash 语法兼容；
- POSIX 脚本交给 Linux 兼容沙箱内的 bash，通过显式 `linux-sh` 或 `.sh` 自动调度；
- tty/pty 属于内核设备契约，原生与兼容进程共用同一套字符流抽象，信号映射在兼容层完成；
- Shell 的完整设计准则见 [SHELL_DESIGN.md](SHELL_DESIGN.md)，本节只记录架构位置。

**实现状态（0.54.6）**：

- 64 位 `shell64.c` 是**内核内置的过渡 Shell**（70+ 命令、`hepu` 命名空间），不是用户态一等程序；
- 64 位主线尚无独立 tty/pty 子系统，输入输出直接走 VGA/串口；
- `linux-sh`、原生/兼容命名空间隔离、资源配额展示、结构化管道均未实现；
- V2 计划改造 Nushell 作为原生 Shell；在此之前不得对外称"原生 Shell 已完成"。

### 2.3 AI原生系统基座层
AI不是独立APP，属于系统基础服务：
- 支持本地离线推理，默认不上传用户数据
- 跨应用信息读取必须用户手动授权
- 根据硬件NPU能力动态分配算力；老设备无NPU可自动降级或关闭AI能力

### 2.4 应用与交互生态层
1. **原生应用格式 `.hug`**（Hyper User Gear）：自带独立沙盒，轻量化，权限全部显式授权，文件加密防篡改
2. **兼容层**：运行安卓 `.apk`，全部强制装入隔离沙盒，限制高危行为
3. 弹性自由桌面、自由缩放窗口、内核级后台冻结
4. 系统UI、设置、应用商店、系统套件

### 2.5 开源与厂商分发架构规则
1. 内核、H-HAL、沙盒、窗口管理器核心代码开源；AI模型权重、商店服务端闭源
2. 开源主协议GPLv3，附加补充约束：内核修改后再分发，必须公开修改后的源码
3. 内核镜像内置**只读版权指纹**，无法被上层UI删除
4. OEM厂商分发版本强制三处标注内核来源：「关于本机」页面、刷机下载页、开机版权提示
5. 商标授权：只有官方审核版本可使用"赫普OS"商标；第三方衍生版本必须改名

## 3. 官方原生应用规范

### 3.1 应用格式
- 原生应用后缀：**`.hug`**
- 释义：HUG = Hyper User Gear（用户级超感组件）
- 寓意：系统拥抱用户、极简、纯净、无捆绑、无追踪

### 3.2 `.hug` 格式设计标准
1. **极致轻量化**：去除冗余代码、广告插件、追踪代码，安装包体积远小于APK
2. **原生隔离沙盒**：每个 `.hug` 应用独立容器运行，互相隔离，无法私自读取隐私
3. **权限完全透明化**：所有权限必须用户主动授权，无静默权限、无后台偷取
4. **内核级原生优化**：专为赫普微内核编译，帧率更高、功耗更低、后台零驻留耗电
5. **防篡改加密结构**：文件结构固化加密，无法植入病毒、追踪脚本、恶意代码

详细二进制结构见 `docs/HUG_FORMAT.md`。

### 3.3 双生态兼容机制
- 原生生态：`.hug`（高性能、安全、纯净）
- 兼容生态：支持运行安卓 `.apk`，所有APK全部运行在隔离兼容沙盒内
- **兼容层开发须遵守「开发规范（硬性约束）」三条**：兼容层用户态化、
  统一沙盒禁止绕过、兼容性预期管理（见文档开头章节）

### 3.4 外部二进制兼容能力边界（架构结论）

> 本节为兼容路线的决策记录，供阶段 2/3 实施与评审使用。

**结论一：内核语言不等于兼容能力。**
C + Rust 只能降低「对接 C ABI、源码级移植」的成本，不自动带来任何外部系统的
二进制兼容。一个二进制能否直接运行取决于完整 ABI：系统调用号与调用约定、
可执行文件格式、动态链接器/加载器、libc 行为（errno、信号、内存分配）、
进程/内存/文件系统/IO 语义、目标指令集。故：

- **源码级兼容**：实现 POSIX 语义后重新编译即可，C/Rust 生态容易做到；
- **二进制兼容**：必须按上述 ABI 逐项对齐，兼容层是独立子系统，不是内核语言的副产品。

**结论二：兼容方案取舍。**

| 方案 | 实现位置 | 主要代价 | 赫普决策 |
|------|----------|----------|----------|
| 内核内翻译（Linuxulator 风格） | 内核态 | 内核复杂度与攻击面最大，需长期跟随 Linux 演进 | 阶段 4 远期再评估，阶段 2 禁止 |
| 用户态加载器 + syscall 翻译 | 用户态 | 每次 syscall 多一层，信号/fork/线程劫持难 | **阶段 2 目标形态** |
| 用户态内核（gVisor / Sentry 类） | 用户态 | syscall 开销大，适合容器而非桌面 | 不采用 |
| 轻量虚拟机（内置 Linux guest） | 虚拟化层 | 内存与启动开销高，图形栈难整合 | 不采用为默认方案 |
| 跨架构指令翻译（Box64/QEMU 类） | 用户态/内核辅助 | 损耗大且波动大 | 远期可选附加能力，不作主力 |
| Win32 兼容（Wine 路线） | 用户态 | 与 syscall 翻译不是同一体系，工作量巨大 | 明确不在当前阶段 |

> 术语校正：vDSO 只覆盖 `clock_gettime/gettimeofday` 等少数调用，不能拦截全部
> syscall；真正的拦截需要加载器改写入口、`ptrace` 或 seccomp。Box64 本质是
> 二进制翻译器，不是"纯 syscall 加载器"的范例。用户态加载器还必须处理信号、
> fork 后的子进程与线程创建；`ptrace` 方案开销过大，只适合调试。

**结论三：范围与优先级。**
- 唯一优先的外部二进制格式为 **Linux x86_64 ELF**；Windows PE、Mach-O 当前不做；
- 同指令集是前提，跨架构翻译不计入兼容层能力；
- 不以"兼容一切"为目标，兼容等级按约束三实测标注。

**结论四：性能不作为百分比承诺。**
损耗由程序特征决定：CPU-bound 最低，syscall-bound 最高，IO-bound 被磁盘掩盖，
图形程序瓶颈在图形栈而非 syscall。验收以固定二进制清单通过率与分类实测为准；
热点 syscall 下沉（阶段 3）只在 profile 证明必要时进行，禁止提前堆完整 Linuxulator。

**结论五：架构决策 A —— 兼容翻译迁出内核（2026-11-02 已决策）。**
0.54.6 存在两处内核侧号翻译：64 位 `ENV_LINUX_COMPAT` + 系统调用号映射表，
以及 32 位树的 `kernel/compat/linux_abi.c`（由 `kernel/arch/x86/syscall.c` 调用）。
经决策，二者均判定为**待迁移的技术债**，不属于目标形态：

- 内核只保留 ABI 中立的系统调用入口、内存/域/线程原语，不含 Linux 调用号映射、
  errno 映射、Linux 结构体布局与信号语义；
- Linux ELF 加载、号翻译、语义适配全部移入用户态兼容域；
- 为避免"用户态翻译无法拦截 syscall"的死结，内核提供**通用 syscall 用户态分发原语**
  （按域开关、把系统调用重定向到该域注册的用户态处理入口），该原语不含任何 Linux 语义；
- 32 位树按同一原则迁移，不保留双标准。

**迁移验收标准**（全部满足才算完成）：

1. 内核源码不再出现 Linux 调用号映射表与 `ENV_LINUX_COMPAT` 分支；
2. 原生系统调用路径与迁移前行为一致，回归通过；
3. Linux 静态 ELF 示例在用户态兼容域中运行，结果与迁移前一致；
4. `compat-api-v1` 草案可支撑该兼容域，不需要内核新增 Linux 专属接口。

**迁移前的纪律**：冻结内核侧翻译范围，不再新增 Linux 调用号、结构体或语义；
在此之前不对外宣称"支持第三方兼容层"。

### 3.5 三平台兼容的分阶段路线与风险门禁（评估稿）

> 定位：Linux 为唯一 P0；Windows 为 P1（Linux 兼容稳定后）；macOS 为 P2（观察，不立项）。
> 三套兼容层不得并行开工；每阶段以固定二进制清单通过率验收，不以"能跑多少软件"宣传。

**3.5.1 优先级与入口条件**

| 平台 | 优先级 | 入口条件 | 当前差距 |
|------|--------|----------|----------|
| Linux ELF x86_64 | P0 | 动态链接 + `libc.so.6` + vDSO；4.4 的 P0 安全项关闭 | 仅静态 ELF 有限支持，无动态链接器 |
| Windows PE / Win32 | P1 | Linux 兼容稳定；图形、窗口、音频接口稳定 | 无 Wine 移植基础，无 Vulkan |
| macOS Mach-O | P2 | 前两者稳定后独立立项评估 | 无 Mach-O 加载、无 Darling 适配 |

- "独立命名空间（pid/mount/net）"当前不存在，不能作为阶段 1 的既成条件；
  需要时按 0.3 五问单独立项。
- 三套兼容层共用约束二的统一沙盒；格式差异只在翻译层处理，不进入安全策略层。

**3.5.2 阶段交付与验收**

**阶段 1｜Linux ELF（P0）**
- 内核侧：只补 POSIX 子集与安全边界，不把 Linux 语义搬进内核（约束一）；
- 用户态：ELF 加载器、动态链接、syscall 翻译、固定二进制清单；
- 图形：暂不列 Vulkan/OpenGL 转发为交付物；无图形栈时只验收控制台程序；
- 验收：固定清单通过率 + 无内核 panic + 沙盒逃逸测试；
- 不以"80% 简单 Linux 桌面软件"作为里程碑。

**阶段 2｜Windows PE（P1）**
- 复用 Wine 的用户态 Win32 实现，不实现 NT 系统调用翻译层；
- 图形依赖 DXVK/VKD3D + 宿主 Vulkan；赫普当前无 Vulkan，
  故图形类 Windows 程序不具备前置条件；
- 反作弊：明确不支持，不做绕过；黑名单只作产品提示，不是安全机制；
- 验收：固定程序清单 + 沙盒隔离 + 开源许可审计。

**阶段 3｜macOS Mach-O（P2，观察）**
- 仅技术观察，不进入 V1/V2 路线图；
- Darling 成熟度低且依赖大量私有 API/框架，不承诺桌面应用或游戏可用；
- 若立项，必须先独立完成 Mach-O 加载、内存/端口语义与许可证评估。

**3.5.3 风险门禁**

| 类别 | 门禁 |
|------|------|
| 性能 | 以 workload 分类基线替代固定百分比红线；统计 syscall 翻译与图形帧时间；对外数字按约束三实测 |
| 稳定 | 损坏 ELF/PE/Mach-O 模糊测试不得 panic；兼容进程崩溃只销毁沙盒；并发文件读写不得错乱 |
| 安全 | 4.4 的 P0 项关闭前不开放兼容层；文件默认只读需权限模型落地；逃逸与恶意样本测试 |
| 知识产权 | Wine（LGPL）、VKD3D（LGPL）、Darling（GPL）需区分动态/静态链接义务；不打包微软/苹果专有 DLL；商业化前审计 |
| 用户预期 | 兼容列表分级；兼容模式窗口标记；崩溃归因区分原生/兼容层；不承诺 100% |

**3.5.4 需要纠正的表述**

- "实现 NT 调用翻译层"：Wine 是 Win32 API 的用户态实现，不是 NT syscall 翻译，
  不需要内核 NT 层；
- "阶段 1 跑 80% 简单 Linux 桌面软件"：无动态链接、无图形栈时不成立，
  改为固定清单通过率；
- "阶段 1 基础 Vulkan/OpenGL 转发"：当前无 Vulkan 驱动/合成器，不能列为阶段 1 交付；
- "性能损耗超过 35% 为红线"：固定百分比不作对外承诺，内部阈值按 workload 实测设定；
- "独立命名空间"：当前无 pid/mount/net 命名空间实现，不能写成已有能力；
- "Darling 封装即可支持 macOS"：Darling 自身成熟度低，不能承诺可用性。

**3.5.5 长期运维**

- Bug 分类：内核 / ELF / PE / Mach-O 分看板管理；
- 回归：每次内核或兼容层变更跑固定清单；
- 上游跟踪：Wine/VKD3D/Darling 只选择性合并补丁，不整树跟进；
- 许可证与版权声明随组件更新同步。

### 3.6 兼容层开放与接入契约（目标形态）

**主张**：内核不绑定任何应用 ABI；兼容层是隔离域内的普通服务，可由内核团队、第三方或社区独立开发；Linux 兼容层只作为参考实现。

要成立，必须把两件东西分开：

| 产物 | 性质 | 开放策略 |
|---|---|---|
| `compat-api-v1` 接入契约 | 内核向兼容层提供的稳定接口：域创建、VA/内存、IPC 与句柄委托、设备能力、配额、日志/审计、事件订阅 | 必须标准化、版本化，与内核版本解耦 |
| Linux 兼容层实现 | 消费上述契约的一个普通服务 | 建议开源作参考实现；许可证随 1.7 一并决定 |

四条红线：

1. 兼容层不得要求内核新增专属 syscall、页表行为或设备 hack；遇到 ABI 难题只能在自身域内解决；
2. 内核不保证任何外部 ABI 的兼容性，兼容范围由兼容层自己声明；
3. 每个兼容层实例仍是隔离域，受同一套配额、DMA、审计约束，开放不降低安全基线；
4. 契约版本独立编号（`compat-api-vN`），新增能力走新版本，旧兼容层不被强制迁移。

**当前差距**：现有 Linux 兼容是内核 dispatch 表 + 内核 ELF 加载器，不是独立域服务；因此第三方兼容层在当前形态下**无法接入**。本主张以 3.4 结论五的 A 决策（迁出内核，已定）为前提，并依赖两项前置：

- 原生契约（0.6）成文并可对外提供；
- 域配额、IOMMU/DMA 隔离、能力 IPC 至少达到可强制执行的基线（见 20.2）。

在此之前，对外只能说"内核目标是不绑定应用 ABI"，不能说"已支持第三方兼容层"。

### 3.7 与 Linux / WSL2 / Wine 的定位对比

> 下表中"赫普"一列全部是**目标形态**，不是现状。引用该表时必须同时给出"赫普现状"列，禁止单独拿目标列做宣传。

| 维度 | 赫普（目标） | 赫普现状（0.54.6） | Linux | WSL2 | Wine |
|---|---|---|---|---|---|
| ABI 绑定 | 内核不绑定应用 ABI，兼容层为独立域服务 | 内核 dispatch 表 + 核内 ELF 加载器 | ABI 即内核 | Windows 内核 + 独立 Linux 内核 | 单一用户态 Win32 翻译 |
| 新增 ABI | 第三方按契约写兼容层，不改内核 | 无用户态接入契约，做不到 | 需内核加 syscall/信号/VFS 特例 | 需另起完整内核 | 只能 Win32→POSIX |
| 隔离 | 兼容层漏洞/崩溃限制在域内 | 无域配额强制力，无 IOMMU | 驱动与子系统在核内 | VM 边界，逃逸仍高危 | 权限等同宿主进程 |
| 开销 | 原生无翻译；兼容域按需启动 | 静态 ELF 加载，开销未实测 | 原生无翻译，驱动常驻内核 | 常驻完整 Linux 内核 | 纯用户态，开销最小 |
| 语义保真 | 取决于兼容层，内核不保证 | 仅少量静态程序 | POSIX 原生 | 接近原生 Linux | 老旧 API/内核特性不全 |
| 维护边界 | 内核只维护隔离/资源/设备契约 | 尚未分离 | 内核承载全部 ABI 历史 | 维护两套内核 | 只维护翻译层 |

定位结论：

- 与 Wine 的区别：Wine 依附宿主 POSIX；赫普兼容层目标是不依附外部 POSIX、直接消费原生契约。
- 与 WSL2 的区别：WSL2 是嵌套完整内核；赫普目标是无嵌套、以域服务承载兼容层。
- 不适合场景：追求 Linux 零损耗、依赖 eBPF/内核模块、HPC 超低延迟；这些不应作为赫普卖点。

### 3.8 设备形态扩展与 Android 兼容边界

> 前提：当前只有 x86 / x86_64，无 ARM64 移植、无虚拟化、无 Android 运行时。本节是路线评估，不是承诺。

**3.8.1 通用底座的边界**

内核通用不等于设备开箱即用。同一套内核要支撑不同形态，每种形态都额外需要：

| 形态 | 额外需要 | 当前状态 |
|---|---|---|
| PC 桌面 | x86_64 BSP、PCIe/ACPI、GPU/显示、桌面套件 | 有基础帧缓冲桌面，无 GPU/合成器 |
| 服务器 | 多核调度、网卡、存储、远程管理 | SMP 骨架存在，无服务器套件 |
| 游戏机 | 独占资源调度、低延迟输入、图形后端 | 无 |
| 移动 | ARM64 移植、电源管理、触控、基带、Android 运行时 | 无 |
| 开发调试平台 | trace、域调试器、快照、插件热重载 | 仅有部分模块原型 |

**3.8.2 在 Android 设备上运行赫普的四种模式**

| 模式 | 做法 | 可行性 | 主要阻塞 |
|---|---|---|---|
| App 内虚拟机 | 安卓 App 里用 microVM/模拟器拉起赫普 | 演示可行 | 需先有 ARM64 构建；普通 App 无 KVM；无 GPU 直通 |
| 替换安卓内核 | 解锁 boot，赫普直接接管 SoC | 技术可行、工程极大 | 厂商闭源 BSP、GIC/定时器/显示/触控/基带、AVB 校验 |
| 双系统 | 分区切换安卓/赫普 | 同模式 2 | BSP 工作量不变 |
| 作为安卓内核模块 | 寄生在 Linux 内核内 | 不推荐 | 隔离域、DMA、SMEP/SMAP 契约全部失效 |

**3.8.3 APK 不等于 Linux ELF**

安卓底层是 Linux，但 APK 依赖的是安卓运行时，不是 Linux syscall：

- `bionic`（非 glibc/musl）、ART/DEX、Binder、Android Framework、SurfaceFlinger；
- Linux 兼容层只覆盖 syscall 与 libc 语义，**即使 100% 完成也跑不了 APK**；
- Android 兼容层是独立项目，可在其内部复用 Linux 兼容层作为 POSIX 底座，但 Binder/ART/Framework 必须另行实现；
- 三个兼容层（Linux / Win32 / Android）平级挂载，彼此独立。

**3.8.4 当前软件生态与里程碑**

- 原生：Shell、`hepu` 命令、测试程序；无办公软件、无游戏；
- Linux 兼容：少量静态 ELF；无动态链接、无图形、无音频；
- "CS1.6 作为第一个游戏里程碑"当前不成立：它依赖 OpenGL/SDL、音频、输入窗口整合，这些均未实现；
- 现实顺序：静态 busybox → 线程/epoll/CLI 工具 → 图形/音频/输入 → 游戏。

**3.8.5 形态优先级**

开发调试平台 → PC 桌面 → 专用设备/服务器 → 游戏机 → 移动与 Android（远期）。
ARM64 先在开发板上验证（树莓派/Rockchip/全志），不要先啃手机 BSP。

## 4. 隐私安全体系

### 4.1 核心机制：用户数据金库
行业首创系统级原生数据主权架构：
1. 所有用户照片、文件、聊天数据、本地记录仅本机存储
2. 系统底层禁止任何自动上传、自动同步、数据抓取
3. 系统本身零数据收集、零用户画像、零追踪

### 4.2 全局隐私防护
1. 设备唯一标识全局随机化，APP无法追踪用户
2. 相册、通讯录、位置、麦克风全部默认空权限
3. 应用只能获取系统脱敏数据，无法获取原始隐私信息

### 4.3 双模式安全系统
- **普通安全模式（默认）**：系统锁死底层防护，防病毒、防恶意篡改、防流氓软件
- **创变自由模式（一键开启）**：无需刷机、无需ROOT，用户可自由修改系统参数、替换系统组件；自带系统快照回滚，不会变砖

### 4.4 兼容层运行前的安全前提

外部二进制兼容层上线前，必须满足以下前提；未满足前不得对外宣称兼容能力。
其中第 2、3 项属于兼容层内部语义，内核只负责域隔离与能力裁决（见 0.11）：

1. 用户虚拟地址范围强制校验：`mmap/munmap/mprotect` 不得触达内核页表或内核虚拟地址；
2. Linux 兼容层的凭据按兼容实例隔离：`uid/euid/gid/egid/umask` 不得作为内核全局状态；
3. Linux 兼容层的文件权限在 `open/read/write/exec` 路径实际执行，而非只保存元数据；
4. `reboot`、`mkfs`、裸盘读写等高危操作必须持有对应能力令牌，
   不得以"是否当前进程"等脆弱条件代替能力检查。

## 5. 全设备刷机适配能力

### 5.1 适配目标
支持新款手机、多年老机型、开发板均可刷入赫普OS，降低设备门槛，让存量旧硬件获得新生。

### 5.2 H-HAL硬件抽象层
1. 抽象硬件接口与具体芯片驱动解耦
2. 两套驱动适配入口：
   - 新设备：对接厂商现代硬件驱动标准
   - 老旧设备兼容桥：适配老安卓设备现有内核驱动接口，做协议转换，复用已有驱动
3. 驱动隔离：驱动故障仅影响硬件模块，不会直接造成整个系统崩溃

### 5.3 刷机镜像设计
- **通用基础镜像**：赫普OS核心系统，不含设备私有驱动
- **设备适配包（H-DPK）**：针对某款机型的驱动、硬件配置补丁包
- 刷机逻辑：基础镜像 + 对应机型H-DPK = 完整可用系统

### 5.4 设备三级分级认证
- ✅ **完整支持**：通话、相机、指纹、移动通信全部正常
- ⚠️ **有限支持**：部分硬件失效，适合WiFi备用机
- ❌ **不支持**：硬件配置过低，直接禁止刷入

### 5.5 刷机安全保障
1. 刷机前自动校验镜像完整性
2. 内置整机快照备份，刷机失败可回滚原有系统
3. 未解锁BL设备仅可运行受限体验版本

## 6. 开源策略与利益保护

### 6.1 开源范围
- 开源：赫普微内核、H-HAL硬件抽象层、`.hug`格式规范、窗口管理器、隐私沙盒核心代码
- 闭源：AI基座模型权重、官方系统应用商店服务端、部分商业组件

### 6.2 开源协议
采用**GPLv3核心内核 + 附加商业约束补充条款**：
1. 修改、分发赫普OS开源内核部分，修改后的内核代码必须继续公开开源
2. 不允许厂商把赫普OS内核封装进完全闭源系统，抹去来源
3. 允许厂商增加闭源上层应用、UI主题、增值服务，但内核部分修改必须开源
4. 利用GPLv3反Tivoization条款，对抗厂商封锁设备不让运行修改版内核

### 6.3 保护机制
1. **内核内置只读版权指纹**：写入内核二进制镜像，不受上层UI控制；启动时自检，发现篡改给出系统警示
2. **商标严格隔离**：只有官方审核通过版本授予赫普OS商标使用权；第三方衍生版本必须改名
3. **漏洞赏金计划**：漏洞优先内部修复完成，再同步公开源码
4. **CI合规扫描**：流水线内置代码指纹扫描，识别厂商私自魔改闭源分发行为

## 10. 现存劣势分析

### 10.1 硬件与刷机劣势
1. 大量手机基带、相机、5G modem、指纹为厂商闭源二进制固件，赫普只能桥接调用
2. 老旧设备内存1-2GB硬件上限低，多任务容易内存溢出卡顿
3. 量产手机普遍锁Bootloader，普通用户刷机门槛高
4. 高通、联发科、展锐各代BSP差异巨大，全机型适配人力成本极高

### 10.2 开源潜在风险
1. 厂商技术规避开源协议，封装隔离层修改内核不公开源码
2. 大量第三方衍生分支破坏沙盒安全逻辑
3. 商标被滥用，劣质衍生版损坏项目口碑
4. 内核全部公开，漏洞对所有人可见

### 10.3 生态短板（最关键）
1. 原生`.hug`应用数量几乎空白，前期高度依赖APK兼容层
2. 缺少完整SDK、IDE、调试工具
3. 电话、短信、相机、输入法等刚需系统套件需从零开发
4. 缺少游戏厂商专项调优，大型游戏性能有差距

### 10.4 厂商分发落地难题
1. 仅靠协议文本约束力有限，UI层标注可被删除
2. 主流手机厂商深度绑定安卓，切换意愿低

### 10.5 AI基座短板
1. 本地AI高度依赖NPU，老设备CPU推理功耗高
2. AI权限逻辑复杂，存在越权读取隐私风险

### 10.6 用户认知迁移劣势
用户长期习惯安卓、iOS，对微内核、`.hug`格式概念陌生。

## 11. 劣势修复方案

### 11.1 硬件、刷机问题修复
1. 设备三级分级认证制度，刷机工具明确展示支持等级
2. 旧设备低内存节流模式：限制窗口数量、降低渲染开销、降级AI能力

2. 内核内置只读版权指纹，UI层删不掉，用于合规取证
3. 商标严格隔离，第三方衍生版本必须改名
4. 漏洞赏金计划 + 优先内部修复再公开

## 14. 优化与兼容预埋路线（评估结论）

> 输入为外部优化建议清单。本节只保留与 0.54.6 现状匹配、且能为 Linux ELF 兼容
> 铺路的项目；原则是「不加功能，只做收敛、消除未来翻译开销、降低 bug 基数」。

### 14.1 现状基线（以 64 位主线为准）

- **内存**：64 位只有 pmm64/vmm64 四级页表与用户窗口，无页缓存、LRU、swap；
  32 位树里的 `kernel/mm/vma.c` 是 32 位地址的链表实现，未编入 64 位构建。
- **调度**：进程/线程模型为简化实现；固定 PIT tick，无 tickless；无 PCID/ASID。
- **syscall**：按进程环境分派 + 号映射；errno 常量集中定义，但无统一
  Hepu↔Linux 转换函数；无 vDSO；参数校验分散在各实现中。
- **IO**：直接调用 ext2_64 + 每进程 fd 表；无 VFS 层、page cache、io_uring、
  ioctl 分派表。
- **可观测性**：32 位 `kernel/drivers/trace.c` 有环形日志/perf 骨架，64 位未接入；
  syscall / 映射 / exec 关键路径无埋点。
- **用户态**：Rust 目前用于部分用户态服务（i686 目标），64 位内核主线仍是 C；
  无完整 POSIX libc 与动态链接器，ELF 加载器在 `elf64.c`，`PT_INTERP` 按 SEC-15 拒绝。
- **图形**：64 位为帧缓冲 + 桌面绘制；`kernel/drivers/gfx2.c` 只是 Vulkan 常量与
  设备信息骨架，不构成可用的 Vulkan 驱动或合成器。

### 14.2 优先级：只做与现状匹配的项

**P0｜安全前提（先于任何兼容功能）**
- `mmap/munmap/mprotect` 用户地址范围强制校验（同时是安全洞与兼容前提）；
  **实施状态（2026-11-02）**：`mmap/munmap` 已完成（长度上限、窗口与溢出校验、
  brk/栈/vDSO 保留区拒绝、部分映射失败回滚）；`mprotect` 已补齐同样的长度上限、
  窗口/溢出校验，并且只作用于当前用户进程的 PML4（不再直接使用 CR3）；
- Linux 兼容层的进程级凭据与文件权限落地，以及高危操作的能力门禁（详见 4.4、0.11）；
  前者在兼容层内实现，后者由内核能力裁决。

**P1｜低成本边界卫生（现在即可做）**
1. **内部结构与对外 ABI 分离**：`stat`、`timespec`、`sigaction`、栈布局等，
   内核内部一套结构，对外兼容输出一套，转换只发生在 syscall 边界；
2. **errno 单一映射表**：集中 `Hepu errno ↔ Linux errno`，禁止在各 syscall
   实现里散落 if/else；
3. **环境标记收口**：`ENV_LINUX_COMPAT` 已存在，补齐 fork/exec 继承与释放清理，
   不新增任何 Linux 语义；
4. **trace 埋点**：syscall enter/exit、拒绝码、mmap/munmap、exec；64 位接入
   环形日志，用于对比 Linux 行为差异；
5. **`MAP_FIXED_NOREPLACE` 等现代 flag 语义**：在 syscall 边界做，不改内存结构。

**P2｜内存与调度（收益大、改造大，按实测触发）**
- 64 位 VMA 抽象（64 位地址、区间查找、权限与兼容标记位）——只有在需要
  按需分配/多区域管理时才接入，不照搬 32 位链表；
- PCID 替换全量 TLB 刷新——需 CPU 能力探测，收益在多进程切换；
- tickless——等调度器稳定后再做，当前先保证 tick 精度与唤醒延迟可测。

**P3｜阶段 2 直接依赖**
- 动态链接器 + `libc.so.6` + vDSO；
- `stat/fcntl/preadv/readlink` 等文件语义转换——当前无 VFS，先在 syscall 层转换，
  不重建 VFS；
- 若未来引入 VFS，再加 `compat_ctx`；不要在直接 ext2 路径上假装有 VFS。

**P4｜明确延后（不是早期优化，是功能工程）**
io_uring、evdev/USB 输入对齐、Vulkan/DXVK、Win32、完整 Linuxulator、
用户态 malloc 替换、Rust/C 内核分配器隔离（64 位主线仍为 C）。

### 14.3 与兼容路线的关系

- **阶段 2（用户态加载器）**：直接受益于 P1 的 ABI 分离、errno 表、trace 与 vDSO，
  不需要等 P2 完成；
- **阶段 4（内核 compat）**：才需要 VMA、task 命名空间扩展字段；现在预埋字段
  属于过度设计；
- **Win32**：Vulkan 底座与窗口模型解耦是前置，但两者都应单独立项，不计入本节。

### 14.4 需要纠正的表述

- 「ASID」是 ARM 术语；x86_64 对应的是 **PCID**；
- 「vDSO 由加载器替换」不成立：vDSO 页由内核映射，加载器只能协作或模拟；
- 「VFS 加 compat_ctx」的前提是先有 VFS；当前是直接 ext2；
- 「Vulkan 后端优先打磨」不成立：现有 gfx2 只是 API 常量骨架；
- 「立刻做 VMA 红黑树 / io_uring / evdev」会拖慢阶段 2，应等 profile 或真实需求触发。

### 14.5 建议迭代顺序

1. P0 安全前提（mmap 范围校验 → 进程凭据/文件权限 → 高危 syscall 门禁）；
2. P1 边界卫生（ABI 分离、errno 表、trace 埋点）；
3. 阶段 2 兼容（动态链接 + vDSO + 固定二进制清单实测）；
4. 按 profile 再决定 VMA、PCID、tickless 与热点 syscall 下沉。

## 15. 驱动子系统路线（评估结论）

> 原则：原生优先、稳定驱动 ABI、分层隔离，**绝不加载 Linux `.ko`**。
> 未具备前置条件的方案明确标注"暂不启动"，不写成已规划能力。

### 15.1 现状基线（0.54.6）

- **已有**：PCI 枚举、ACPI（`acpi.c` 已编入 64 位）、IDE/AHCI、RTL8139/e1000、
  USB UHCI/EHCI/xHCI 代码、AC97、PS/2 键鼠、RTC、帧缓冲与桌面绘制；
- **模块化**：自有 `kmod64` 模块加载器（ELF 重定位、符号解析、`module_init`），
  与 Linux `.ko` 不兼容；`drv_register64` 已有 init/probe 驱动描述符；
- **未具备**：IOMMU（零实现）、用户态驱动框架（UIO）、devfs/热插拔、
  DMA 池、中断线程化/亲和、VirtIO 真正驱动（仅网络 HAL 枚举占位）、NVMe；
- **语言基线**：64 位内核主线为 C，Rust 未进入内核，"Rust 优先"当前不可执行。

### 15.2 四条路线与优先级

**路线 1｜原生内核驱动（当前主线，C）**
- 目标硬件：PCI/ACPI、AHCI/IDE、e1000/RTL8139、USB HID、AC97、帧缓冲；
- 结构：总线枚举 → 设备 ID 匹配 → probe → 资源获取（MMIO/IRQ/DMA/IO port）；
- 约束：驱动只调用稳定导出 API，不直接触碰 task、VMA 等内核内部结构；
- 自有模块可加载，但必须走稳定驱动 ABI；禁止 Linux `.ko`。

**路线 2｜用户态驱动（中期，需前置条件）**
- 适用：USB class、HID、音频、摄像头等可隔离外设；
- 前置：内核提供 MMIO/IRQ 转发、受控 DMA 缓冲、设备权限模型；
- 硬约束：**没有 IOMMU 时不得把可 DMA 设备交给用户态**，
  否则用户态驱动可绕过地址空间保护；
- 收益：驱动崩溃只影响自身进程，不波及内核。

**路线 3｜Linux 驱动代理 VM（远期可选，默认关闭）**
- 形态：裁剪 Linux guest 加载原生驱动，通过共享内存/virtio 向宿主暴露设备服务；
- 前置：虚拟化子系统、IOMMU/VT-d、设备直通、guest 生命周期管理；
- 定位：只用于无原生驱动的复杂设备（GPU/闭源卡），不作默认路径；
- 当前无虚拟化、无 IOMMU，**暂不启动**。

**路线 4｜PCI 透传（远期兜底）**
- 与路线 3 共用前置条件；仅用于闭源专业卡；资源开销大，不作日常主力。

### 15.3 设备路径（原生与兼容不混用）

```
原生 App        → Hepu 原生驱动
Linux ELF App   → 兼容层 → ① 原生驱动（有限 ioctl 翻译）
                          ② 驱动代理前端（远期，默认关闭）
Win32 App       → Wine   → 同上设备后端
```

原则：两条路径共用同一设备服务接口，但不在内核主干复制两套驱动。

### 15.4 明确不做

- Linux `.ko` 加载器：绑定 Linux 内核符号与内存布局，会锁死赫普架构；
- 用 ioctl 全翻译支撑 GPU/音频：私有 ioctl 无标准、不可穷举；
- 把驱动代理 VM 作为默认或唯一路径；
- 在无 IOMMU 时开放用户态 DMA；
- 现阶段投入 AMDGPU KMS、Vulkan、NVMe、VirtIO：
  均为功能工程，不是驱动路线收敛。

### 15.5 需要纠正的表述

- "阶段 0 只做 PCI/ACPI/VirtIO，全部 Rust 优先，开发环境跑 QEMU"：
  64 位主线是 C；当前无 VirtIO 驱动、无 QEMU 回归环境，镜像/真机是现有验证方式；
- "Rust 优先"：Rust 未进入内核，现为 C；
- "驱动代理 VM 可瞬间获得全部 Linux 驱动"：需虚拟化 + IOMMU + 直通，
  代价与隔离边界必须先验证；
- "用户态驱动天然安全"：无 IOMMU 时不成立。

### 15.6 迭代顺序

1. 稳定现有原生驱动与驱动注册 ABI（probe、资源抽象）；
2. 完善 ACPI/PCI 资源枚举，补 IOMMU 能力探测；
3. 收敛 USB HID/存储与输入事件模型；
4. IOMMU 就绪后，再评估用户态驱动（先非 DMA 设备）；
5. 虚拟化就绪后，再评估驱动代理/透传，且默认关闭。

## 16. V1 范围冻结与工作量控制

> 背景：操作系统是依赖闭环，兼容层是工作量放大器；每开一个模块都会繁殖子需求。
> 原则：V1 只承诺"可验证的最小闭环"，其余显式延后或外包；
> 未具备前置条件的方案不进入 V1 依赖链。

### 16.1 膨胀来源（结论）

1. **依赖闭环**：ELF 加载 → syscall 翻译 → vDSO → 信号 → DRM/ioctl →
   GPU/evdev/ALSA/网络/udev，少一环就卡死"能跑浏览器"；
2. **兼容层是放大器**：等于同时维护赫普原生与 Linux 两套语义，
   每个子系统都多一条兼容分支；
3. **完美主义**：为未来预留多种后端，短期直接翻倍代码量；
4. **边界缺失**：没有"必须 / 可选 / 永不自研"的三分法。

结论：V1 不把"跑浏览器/Steam/3A"作为验收条件；兼容层在 V1 只做实验性控制台原型。

### 16.2 V1 三分法

| 类别 | 项目 | V1 状态 | 依据 |
|------|------|---------|------|
| 必须 | 64 位启动、ACPI/PCI、PMM/VMM、IDT/PIT、syscall 分发 | 已有 | 当前主线 |
| 必须 | ext2 读写、shell、原生 C 程序 | 已有 | 直接 ext2，无 VFS |
| 必须 | 静态 Linux ELF 控制台示例 | 已有（有限） | `linux_map` + 测试 |
| 必须 | P0 安全项（4.4） | 发布前必须 | 安全前提 |
| 可选 | 动态链接 + `libc.so.6` + vDSO | 阶段 2 | 兼容 B 级 |
| 可选 | seccomp cBPF 过滤器 | 已完成 | P0-5 |
| 可选 | 桌面打磨、网络应用 | 非 V1 验收 | 现状可用但不承诺 |
| 不做 | VFS 多后端、ext4/btrfs、自研 COW FS | V1–V2 不做 | 直接 ext2 已够 |
| 不做 | VirtIO、NVMe | 无驱动/无 QEMU，不列为 V1 | 见 15.1 |
| 不做 | AMDGPU KMS、Vulkan、合成器重写 | 功能工程 | 见 14/15 |
| 不做 | 驱动代理 VM、PCI 透传 | 缺虚拟化 + IOMMU | 见 15.2 |
| 不做 | Win32、macOS Mach-O/Darling、完整 Linuxulator、io_uring、evdev/udev | 远期独立立项 | 见 14.2/3.5 |

### 16.3 兼容分级（不追求 100% ABI）

- **A 级｜静态控制台 ELF**：少量高频 syscall，ioctl 明确返回"不支持"；
  当前已具备基础能力，作为 V1 的实验性演示。
- **B 级｜动态链接 + 基础网络**：真实 `ld-linux` / `libc.so.6` / vDSO；
  是阶段 2 的主目标，按固定二进制清单计通过率。
- **C 级｜DRM/ALSA/GPU**：不逐个翻译私有 ioctl；只走原生驱动或驱动代理，
  且必须先满足 15.2 的前置条件。

每级验收 = 固定二进制清单 + 实测通过率，不用"兼容多少软件"做口径。

### 16.4 预埋准入规则（只留接口，不实现多后端）

新增抽象前必须回答四个问题，任一为"否"则延后：

1. 是否是 V1 验收所必需？
2. 能否放到用户态，而不是进内核主干？
3. 能否延后且不锁死架构（只留参数/钩子，不写第二套实现）？
4. 是否有可重复的测试或基准能验证？

据此：`compat_ctx` 只在引入 VFS 时才加；不同时实现 ext2/ext4/btrfs；
不同时实现原生驱动与 UIO 两套完整栈。

### 16.5 用户态下沉（方向，不是现状）

目标形态：内核只保留启动、内存、调度、syscall、基础文件后端与设备前端；
以下应独立为用户态组件：

- 设备热插拔/devd、包管理器、桌面合成器；
- Linux ELF 加载器与 syscall 翻译器（与约束一一致）。

现状偏差：`desktop64` 仍在 64 位内核内，ELF 加载与 `linux_map` 也在内核
dispatch 层；拆出需要先定义稳定的内核接口，属长期重构，不计入 V1。

### 16.6 "先跑通，再优化"

- 优化顺序遵循 14.5：P0 安全 → P1 边界卫生 → 阶段 2 兼容 → 按 profile 再优化；
- 兼容层性能损耗不作 V1 承诺（约束三），先保证行为正确；
- 复杂外设在无代理/无原生驱动时，明确标注"不支持"，不做静默降级。

### 16.7 V1 验收清单（可测）

1. 64 位镜像按现有启动路径进入 shell，无 panic；
2. ext2 读写与基础文件操作通过；
3. 原生 C 程序可编译并在系统内运行；
4. 静态 Linux ELF 示例可运行（实验性标注）；
5. seccomp strict / cBPF 自测通过；
6. `check_docs.py` 为 0 warn / 0 error；
7. 4.4 的 P0 安全项关闭。

不包含：浏览器、Steam、GPU 加速、Win32、完整 Linux 桌面软件。

### 16.8 变更控制

V1 期间新增子系统必须附一页说明：目标、非目标、依赖、验收方式、回滚方式；
若要新增，必须同时删掉或延后一项同量级工作，避免清单只增不减。

## 17. 编程语言策略（C 核心 + 汇编底座 + Rust 用户态渐进）

> 结论：内核主线继续 C；汇编只用于必须的底层入口；Rust 从用户态服务试点，
> 不整体重写，不为"上 Rust"而上 Rust。

### 17.1 现状基线

- 64 位内核主线为 **C**（`kernel/arch/x86_64/`），汇编用于启动、上下文切换、
  中断入口与特殊寄存器操作；
- Rust 仅存在于 `user/rust`（i686 目标），**未进入 64 位内核**；
- 构建未显式指定 C 标准（使用 GCC 默认）；若要升级标准，必须先全量构建与自测。

### 17.2 语言取舍

| 语言 | 适用位置 | 赫普决策 |
|------|----------|----------|
| C | 内核主干、驱动、syscall、内存/调度 | 主线，保持 |
| 汇编 | 启动、上下文切换、中断入口、特殊寄存器 | 只用在必须处，控制在极小比例 |
| Rust | 用户态服务、安全敏感组件 | 试点后逐步推广；现阶段不进内核主干 |
| C++ | 内核 | 不采用：复杂度与内存安全收益不匹配 |
| Zig | 内核/用户态 | 观察，不采用 |
| Go | 最底层 | 不采用：GC 与 runtime |
| Python/JS | 内核 | 不采用 |

### 17.3 Rust 引入门槛（与 0.3 五问一致）

1. 先选一个低风险用户态服务试点（目标形态中的文件/网络/隐私金库等；
   当前多数仍在核内，见 16.5），不碰调度与内存内核核心；
2. 建立 C/Rust FFI 规范：类型映射、错误码、内存所有权、panic 边界；
3. 工具链先行：i686 目标已有；若未来进内核，需 `x86_64-unknown-none`
   与 `no_std` 验证；
4. 每个 Rust 组件必须有测试、构建脚本与回滚到 C 的方案。

### 17.4 渐进路线

- **阶段 1（当前）**：C 质量加固——静态分析、单元/集成测试、API 文档；不整体重写；
- **阶段 2**：单个用户态服务 Rust 试点，验证 FFI 与打包；
- **阶段 3**：新用户态服务 Rust 优先，安全敏感组件逐步重写；
- **阶段 4**：完善工具链、文档与贡献指南；内核核心仍为 C。

### 17.5 表述红线

- 不称"Rust 内核"；可称"C+Rust 混合系统"（Rust 在用户态）；
- 不把"计划引入 Rust"写成"已用 Rust 重写"；
- 不以语言选型替代性能与安全实测。

## 18. 外部视角与沟通口径（评估假设）

### 18.1 各方关注点与现状差距

| 对象 | 关注点 | 赫普现状 | 可说 / 不可说 |
|------|--------|----------|---------------|
| 硬件厂商 | 适配成本、驱动 ABI 稳定性、故障归属 | `kmod64` 有模块加载，但驱动 ABI 未冻结；无 IOMMU/虚拟化 | 可说"目标是稳定 ABI"；不可说"已稳定" |

### 18.2 两条硬标准

1. **契约稳定性**：驱动 ABI 未冻结前一律标实验性；冻结后版本化，
   破坏性变更必须给出迁移说明；
2. **脏硬件**：ACPI 异常、DMA 越界、固件 bug 下的隔离保持，必须有故障注入/
   模糊测试；纸面契约不算数。

### 18.3 兼容层定位

- 兼容层是**生态脚手架**，不是一等公民；
- 禁止为兼容给内核主干打特例补丁；一旦发生，0.2 的根基自毁；
- 对外始终标注"可选、实验、上层翻译"。

### 18.4 统一表述（对外可用）

> 赫普OS 的设计出发点是：内核负责硬件资源仲裁、任务隔离与稳定抽象契约。
> 我们先定义原生的资源、隔离与设备访问契约，原生 ABI 由契约导出；
> 对 Linux ABI 的支持是运行在契约之上、可选的上层翻译层，用于复用现有软件生态，
> 不会反过来主导或修改内核底层模型。这是与 Linux 不同的演化取舍，而非对现有系统的否定。

引用限制：当前"契约"尚未成文（0.6），Rust 未进内核，驱动 ABI 未冻结；
使用这段话时必须同时标注现状，避免被理解为已交付。

### 18.5 表述红线

- 不说"Linux 是错的/本末倒置"，只说"不同取舍"；
- 不承诺厂商适配，不暗示已有合作；
- 不称驱动 ABI 已稳定，不称代理 VM 可用；
- 不把预期反应写成"社区/厂商已认可"；
- 不把市场假设当作路线依据，仍按 0.3 五问与 16 范围判断。

### 18.6 平台公司视角（微软/苹果，评估假设）

> 两家不会公开评价赫普；以下是基于其公开架构的类比，不是内部态度。

**结构对照**

| 对象 | 公开架构 | 与赫普的相似点 | 关键差异 |
|------|----------|----------------|----------|
| Apple XNU | Mach 原语 + BSD POSIX personality；DriverKit 把驱动移出内核 | "底层原语优先、上层 personality" 的顺序 | 赫普无 Mach/port、无 DriverKit；驱动仍在核内 |
| Microsoft NT | 执行体 + 子系统（Win32/POSIX）；WSL1 做 syscall 翻译，WSL2 是轻量 VM | "内核原语 + 上层 ABI 子系统" 的分层 | 赫普无子系统模型；当前兼容翻译在 dispatch 层 |
| Linux | ABI 优先，内核适配历史 ABI | 无 | 顺序相反（见 0.2） |

**可能的态度（假设）**

- 研究院/内核安全团队：对 C/Rust 边界、隔离契约、兼容层工程学有兴趣；
- 产品/商业团队：无直接利益，基本无视；
- 官方：不表态、不站台、不干预。

**必须纠正**

- "赫普与 NT/XNU 同源"：只有演化顺序相似，不是同一架构；赫普定位为微内核
  （32/64 位内核同属一套体系），但 64 位主线仍有 ext2、网络、图形等核内实现，
  属于待下沉的过渡路径；对外应区分"微内核架构定位"与"当前实现进度"，
  不能把过渡实现说成"全部服务已在用户态"；
- "WSL 就是 NT 上的 Linux 兼容层"：WSL1 是 syscall 翻译，WSL2 是轻量 VM，
  不能混为一谈；
- "C+Rust 混合内核"：Rust 未进内核，当前只是 C 内核 + Rust 用户态；
- "微软/苹果会认可"：没有任何依据，不能写入宣传材料。

**表述启示**

- 对 Mach/NT 背景工程师：用"原语/契约 → personality/ABI"解释，最容易听懂；
- 对 Linux 背景开发者：强调"不同取舍"，不贬低 Linux；
- 只讲设计顺序，不宣称"更先进"或"已被大厂验证"。

## 19. 体积预算与发布形态

> 目标：把"镜像多大"从口头估算变成可测量、可验收的预算项。除非另有说明，
> 本节数字均为**规划目标或外部估算**，不是当前实测值。

### 19.1 当前实测基线（0.54.6，x86_64）

| 项目 | 实测值 | 说明 |
|---|---|---|
| 64 位内核二进制 | 602,440 B（约 0.6 MB） | `build_x86_64/hepu-kernel64.bin` |
| 32 位内核二进制 | 3,847,413 B（约 3.7 MB） | `build_v250/hepu-kernel.bin` |

| 层 | 规划目标 | 备注 |
|---|---|---|

### 19.3 发布形态

- **基础镜像**：只含微内核、基础服务、控制台与最小工具；控制在百 MB 级。
- **桌面镜像**：在基础镜像上叠加图形栈与桌面组件，独立发布。
- **驱动沙箱**：作为**可选外部硬件服务**单独打包、按需获取；不内嵌进基础镜像。
- **调试符号**：单独作为 debug 包发布，不随正式镜像分发。

### 19.4 表述红线

- 驱动代理尚未实现（缺虚拟化与 IOMMU），不得对外承诺"按需下载即可获得完整 Linux 驱动生态"；
- 不得用"约 1 GB""约 2 GB"这类估算作为已达成指标；发布说明只写实测体积与测量方法；
- 体积超标时先裁剪可选组件，不通过压缩内核安全功能来达标。

## 20. 隔离域感知的优化主线

> 区别于"调度更快、内存更少、驱动更多"的通用优化，赫普的独特主线是：
> **CPU、内存、中断、IO、设备、IPC 全部按隔离域管控、限流、审计**，
> 驱动代理沙箱是一等可管控负载，而不是与原生内核混在一起。
> 本节是方向清单，不代表已实现；任何对外表述必须先对照 20.1 的现状。

### 20.1 现状核对（0.54.6）

| 能力 | 现状 | 结论 |
|---|---|---|
| 隔离域视图 | `shell64` 的 `hepu ps`、`hepu sandbox`、`hepu mem` 已有展示 | 是**视图**，不是强制配额 |
| 按域内存管控 | 每进程有 `mem_pages`/`mem_limit_pages`；`mmap`/`brk`/模块加载强制记账，`munmap`/卸载按实际释放页退还 | 配额按域（原生=总量 1/2，兼容=总量 1/4）强制；低水位时兼容域先回收块缓存再限流，原生交互域不阻断；ELF 映像、用户栈、页表自身开销未计入 |
| 按域调度优先级 | 仅有全局抢占调度 | 未绑定隔离域标签 |
| 中断亲和/隔离 | 未实现 | 无专用核绑定 |
| IOMMU / DMA 隔离 | 未实现 | UIO、代理驱动均缺前置条件 |
| 设备能力声明 | 未实现 | 当前只有原生驱动路径 |
| VFS / 快照 / 按域 IO 配额 | 无 VFS；64 位直接 ext2 | 快照、文件域标签、IOPS 限流均缺前置 |
| capability IPC / 句柄传递 | 有 IPC 管道与服务注册 | 无能力令牌、无跨域句柄授权 |
| 命名 IPC 服务总线 | `hsipc` 已有命名通道 | 核内实现，非独立域，无能力校验 |
| VA 区间管理器 | 已进程级化：每进程 16 项区间表 + 模块表；已有 `vmm64_page_present` 存在性查询 | 固定池，未接入热重载 |
| 固件统一服务 | 未实现，无 firmware loader | 签名、版本、原生/代理共用均缺 |
| 内核 trace / 调试原语 | 64 位无 tracepoint 框架 | 域感知 trace、域内调试器未实现 |
| 安全启动 / 镜像签名 | 未实现 | 依赖启动链与包管理 |
| 包管理与域感知更新 | `appstore64` 是界面，不是包管理器 | 原子更新、回滚未实现 |
| 兼容层翻译缓存/实例池 | 仅静态 ELF 有限支持 | 缓存、池化、日志隔离未实现 |
| 合成器 / 显示平面隔离 | 64 位基础桌面与帧缓冲 | 无独立合成器服务、无 GPU 配额 |
| 结构化管道 | `hepu` 命令输出为文本 | 未实现 schema/对象管道 |
| 审计与契约校验 | 32 位有 `sec_audit` 等接口 | 64 位运行时契约校验器未实现 |
| 域感知更新/原子回滚 | 未实现 | 依赖包管理与快照 |

### 20.2 方向与优先级

> 实施状态：**P0-A（mmap/munmap 地址范围校验）已于 2026-11-02 完成**
> （`kernel/arch/x86_64/syscall64_full.c`）。此前进程可改任意地址的共享页表，
> "按域配额"无法强制执行；现在 mmap/munmap 均被限制在用户窗口内，
> 并拒绝与 brk、栈、vDSO 保留区重叠。**P1 VA 管理器进程级化亦已于同日完成**：
> 区间表与模块表按进程槽位隔离，exec 的 PIE 预留在 pending 表、创建后移交，
> 槽位释放时清理模块 kbuf 与区间账本。**P1 按域内存水位与 OOM 策略亦已于同日完成**：

> 长度上限、窗口/溢出校验，并改为只操作当前用户进程的 PML4（不再直接用 CR3）。

### 20.3 非目标（防止膨胀）

- 不为古怪 Linux ioctl 或小众 ABI 在内核主干加特例；
- 不在内核内置大量文件系统与冷门驱动，复杂外设交给代理或用户态；
- 不把 POSIX 语义渗透进原生内核原语，POSIX 只存在于兼容沙箱；
- 不扩张成千上万的全局 syscall，原生 ABI 保持精简，能力扩展优先走 IPC。

## 21. 驱动代理的收益、代价与成立条件

> 本节回答"这套架构有什么独特优势、资源开销是否更大"。
> 所有收益均为**设计目标**，当前驱动代理尚未实现，不能作为已交付能力宣传。

### 21.1 收益成立的前提

| 目标收益 | 成立条件 | 当前状态 |
|---|---|---|
| 驱动漏洞被限制在代理域 | 每设备独立 IOMMU 域，DMA 只能访问授权窗口 | 无 IOMMU，收益不成立 |
| 驱动崩溃不影响桌面 | 代理运行在独立 VM/进程，可单独重启 | 无虚拟化，未实现 |
| 内核主干不含海量驱动 | 代理能覆盖目标硬件，且性能可接受 | 代理未实现 |
| 硬件适配快 | Linux 驱动可在代理内运行，许可与分发合规 | 未验证 |
| 原生域资源优先 | 调度/内存/IO 按域强制配额 | 仅有视图，无强制力 |
| 原生/兼容语义不混 | 命名空间、PID、信号、文件系统隔离 | 兼容层仅静态 ELF，隔离未实现 |

**硬结论**：没有 IOMMU，代理内的驱动仍可发起任意 DMA，所谓"攻击范围锁死在代理域"不成立。IOMMU 是驱动代理安全叙事的前置条件，不是可选项。

### 21.2 资源代价

- 代理 Linux 的内存/磁盘开销取决于裁剪程度，当前**没有任何实测数据**；
- "空闲 200–600 MB""按需拉起、闲置回收"属于规划策略，不是现状；
- 纯原生场景是否比 Linux 更小，取决于桌面、字体、工具链的实际打包，当前无法下结论；
- 代理按需加载还依赖虚拟化启动速度、设备直通与回收策略，均未实现。

### 21.3 必须实测的指标

1. 代理启动/销毁延迟，以及闲置回收后的内存回落；
2. 音频、输入、GPU 路径的附加延迟；
3. 代理域与原生域同时高负载时的调度干扰；
4. IOMMU 开启前后 DMA 越界测试结果；
5. 代理 Linux 的许可证义务与镜像分发方式。

### 21.4 表述红线

- 不说"驱动崩溃只影响沙箱"——除非 IOMMU 隔离已实测通过；
- 不说"资源占用比 Linux 小"——除非有同等功能镜像的实测对比；
- 不说"厂商不用写驱动就能全硬件支持"——代理覆盖率和性能尚未验证；
- 不贬低 cgroup：它是 Linux 内核的正式子系统，不是单纯的"上层附加机制"。

## 22. ELF 加载与地址空间契约

> 本节把"加载地址报错"的常见原因收敛为赫普的设计规则与排查顺序。
> 现状以 64 位 `elf64.c` / `user_process.c` 为准，不按通用 Linux 布局假设。

### 22.1 当前地址布局（64 位）

| 区域 | 地址 | 说明 |
|---|---|---|
| 用户窗口 | `0x40000000`–`0x7FFFFFFF` | 1 GB，超出即拒绝加载 |
| 原生代码基址 | `0x40000000` | `USER_CODE_BASE` |
| 用户栈顶 | `0x70000000` | 256 页（1 MB），向下增长 |
| vDSO | `0x7FFF0000` | 固定映射，一页 |
| 内核 | 高半区 + 低端恒等映射 | 与用户窗口不重叠 |

当前**没有通用 VA 区间分配器**：代码、栈、vDSO 都是固定布局，不随机化、不按空闲区间挑选。

### 22.2 加载器必须坚持的规则

1. `p_filesz <= p_memsz`，`p_vaddr + p_memsz` 不得溢出或超出用户窗口；
2. 所有段先装入**内核临时缓冲**，清零 BSS，完成重定位，再映射到用户页；
   不允许内核代码直接按用户 VA 写入（SMAP 会触发故障）；
3. 页粒度映射，`p_vaddr` 与 `p_offset` 的页内偏移应一致；
4. 段区间不得重叠；重叠必须拒绝，不能"后写覆盖前写"；
5. `p_flags` 必须落到 PTE：可写段才给 W，数据段不给 X，代码段按需给 X。

### 22.3 当前支持与缺口

| 能力 | 状态 |
|---|---|
| 原生 ET_EXEC | 支持 |
| static-PIE（ET_DYN，无 PT_INTERP） | 支持，仅应用 `R_X86_64_RELATIVE` |
| 动态链接（PT_INTERP / ld.so / DT_NEEDED） | ⚠️ 部分：PT_INTERP 解释器加载已接入 exec（`user_process.c:1938-2128`）；DT_NEEDED 符号/重定位由用户态 ld.so 完成，内核遗留 `hepu_dynlink_relocate()` 未接线 |
| `PT_TLS` | 未处理 |
| `PT_GNU_STACK` | 未处理 |
| 段重叠检测 | 未实现 |
| 按 `p_flags` 设置 W/NX | 未实现，代码页当前统一 `PRESENT|WRITABLE|USER` |
| VA 区间分配/冲突检测 | 未实现，固定布局 |

### 22.4 排查顺序

1. 打印每个 `PT_LOAD` 的 `p_vaddr / p_filesz / p_memsz / p_flags`，先查重叠、越界、`memsz < filesz`；
2. 区分 VA 与 PA，确认映射进入的是当前进程的 PML4；
3. 解析 `#PF` 错误码：bit0=页不存在/权限，bit1=写/读，bit2=用户/内核；
4. 加载阶段先用内核缓冲，确认没有直接写用户 VA；
5. 切用户态前确认 CR3 已切到该进程页表，旧映射已 unmap 并 `invlpg`。

### 22.5 表述红线

- 不称"支持完整 Linux 动态链接"：PT_INTERP 解释器虽已加载入库区（`user_process.c:1938-2128`），但内核不自解析 DT_NEEDED 符号/重定位，依赖用户态 ld.so；
- 不称"代码段只读可执行"：当前统一映射为可写，W^X 尚未落地；
- 不把固定布局说成"地址空间随机化"。

### 22.6 插件热重载的边界与前置条件

**允许**：隔离域内的用户态插件（`hepu` 扩展、设备采集插件、协议解析插件）。
**不允许**：内核核心热补丁、运行中的核心服务原地覆盖代码段、驱动代理 Linux 内部进程热 patch。

驱动代理的更新方式是**实例替换**：先起新沙箱，原子切换设备路由，再销毁旧实例；不是原地改内存。

热重载的必要流程（缺一不可）：

1. 停止向模块派发任务，等待所有线程离开模块代码段（`refcount == 0`）；
2. 置空外部函数指针与回调，切断调用路径；
3. `unmap` 旧 VA 区间，释放物理页，按核 `invlpg`，SMP 下发送 IPI 做 TLB shootdown；
4. 在新 VA 区间加载新版本，不复用旧地址（调试期强制）；
5. 校验导出符号版本哈希，重定位后注册新入口；
6. 由模块 `deinit` 主动释放设备句柄与 IPC 通道，内核不强行回收。

前置能力与现状：

| 能力 | 现状 |
|---|---|
| 共享对象/插件加载 | 已有原型：`hepu_module_load/unload` 解析 `PT_DYNAMIC`、`DT_NEEDED`、符号查找与重定位 |
| VA 区间管理器 | 已有雏形：16 项区间表 + 共享库池 `[0x60000000,0x70000000)`，固定池非通用 |
| 模块管理器（refcount/状态） | 有 `refcount` 字段，但无"等待线程退出"的静默期协议 |
| 卸载协议与资源释放 | 部分：unmap + 写 CR3 全刷新，未做跨核 IPI，模块资源靠调用方 |
| 符号版本校验 | 未实现，按名匹配，无版本哈希 |
| SMP / TLB shootdown | 已有 `smp.c`；卸载只用 CR3 全刷，未用于跨核精确刷新 |
| 域快照回滚 | `hepu snapshot` 目前只是 `fsync` 占位 |

因此热重载列为 P4：插件加载与卸载已有原型，但缺少静默期、符号版本与精确 TLB 同步；在此之前，服务更新一律走"重启隔离域"。

## 23. 模块化现状与验收

### 23.1 已有工程基础

模块化不是零起点，以下代码已经存在：

- `kmod64.c`：自有格式内核模块，ELF 重定位、符号解析、`module_init`；
- `user_process.c`：`hepu_module_load/unload` 用户态 dlopen 雏形，解析 `PT_DYNAMIC`、`DT_NEEDED`，符号查找、重定位、`refcount`、每进程 8 个模块槽与 16 项 VA 区间；
- `hsipc.c` / `hsservices.c`：命名通道与服务注册；
- `drv_register64.c` / `drv_mgr64.c`：驱动注册与总线匹配；
- `kernel_contracts.c`：契约查询接口。

结论：**设计层模块化潜力强，工程层已有原型但边界未固化**；不能说"模块化程度为零"。

### 23.2 必须固化的五条边界

1. **调度只认域标签与配额**，不认识"驱动代理/兼容层"这类业务含义；
2. **tty 只负责字符流与终端控制**，Linux 信号/语义翻译留在兼容域；
3. **VA 管理器独立自包含**：只提供分配、释放、查询、TLB 同步，不关心加载的是 ELF、插件还是驱动；
4. **`hepu` 命令的数据来源是内核 IPC**，表格格式化、过滤、展示全部在用户态工具；
5. **跨模块/跨域只传句柄、ID、能力令牌**，禁止裸指针。

### 23.3 现存耦合与缺陷

| 问题 | 位置 | 影响 |
|---|---|---|
| 模块表与 VA 区间表是全局静态 | `g_modules` / `g_va_regions` | 多进程各自页表加载模块时会互相覆盖/误释放 |
| 卸载只写 CR3 全刷 | `hepu_module_unload` | 无跨核 IPI；SMP 下其他核可能仍用旧映射 |
| `refcount` 无静默期 | 同上 | 调用方归还引用后立即 unmap，正在执行的线程可能踩空 |
| 硬上限 8 模块 / 16 区间 / 256 符号 | 同上 | 达到上限即失败，无回收策略 |
| syscall 直接调用 ext2 | `syscall64_full.c` | 没有 VFS 缝，换文件系统要改 syscall |
| 桌面/窗口/输入在核内 | `desktop64.c` / `window64.c` / `hsinput.c` | 与"用户态服务"目标不一致 |
| `hsipc` / `hsservices` 为核内实现 | 同名文件 | 服务不是独立域，隔离性弱 |

### 23.4 模块验收五问

1. 能否单独关闭该模块，系统其余部分正常启动？
2. 替换实现时，上层调用代码是否不用改？
3. 模块是否直接访问其他模块的私有变量？
4. 卸载后是否残留全局状态、PTE、回调指针？
5. 内核模块是否只依赖契约接口，不依赖其他模块内部实现？

五问有一项不通过，就不得标记"模块完成"。
