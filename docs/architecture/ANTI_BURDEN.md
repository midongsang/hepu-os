# 赫普OS内核架构设计：规避历史包袱与系统拖沓

> 核心总原则：**严格划分稳定契约边界，模块之间只依赖契约，不依赖对方内部实现；允许废弃模块，但禁止偷偷在核心路径加临时补丁。**

## 一、两种"包袱"的区分

### 1. 代码包袱（可控）
临时hack、全局状态、杂乱锁、大量条件分支、缺少测试、注释缺失、复制粘贴代码。

### 2. 契约包袱（一旦定下就很难删，自研最需要警惕）
- 内核↔用户态：系统调用号、结构体布局、返回值语义、错误码
- 内核↔驱动：驱动API、设备抽象接口（总线、ops）
- 内核内部子系统之间：子系统导出的内部API

> 自研陷阱：前期为快速跑通demo，随便定系统调用、结构体；等上层应用/驱动写多了，就形成自研项目自己的"历史包袱"。

## 二、架构层面：分层+严格模块边界

### 基础分层
```
用户态应用
————【稳定契约层：syscall、数据结构、错误码】————
内核上层：进程管理、VFS、内存抽象、IPC
————【子系统契约：ops结构体，仅暴露函数指针】————
内核底层：物理内存管理、中断、定时器、总线抽象
————【硬件抽象层 HAL】————
硬件
```

### 边界规则
1. 上层子系统**不能直接访问下层子系统的结构体成员**，只能调用对外暴露的接口
2. 所有子系统对外暴露只有`struct xxx_ops`函数表；内部结构体完全私有
3. 不允许在核心代码里写硬件特例。硬件特殊逻辑全部下沉到HAL/驱动

## 三、接口版本化（禁止到处加if分支）

❌ 糟糕：同一个函数内多版本分支
```c
if (api_version == 1) { old_logic(); }
else if (api_version == 2) { new_logic(); }
```

✅ 方案：不同版本ops，注册不同操作实例
```c
struct mm_ops mm_v1_ops;
struct mm_ops mm_v2_ops;
// 根据版本选择整个ops实例，而不是在函数内部加if
```

旧版本实现放在独立文件目录，迁移完成后直接删除整个旧文件目录，**没有残留分支**。

## 四、ABI设计规则（自研内核最关键）

1. **区分实验版ABI和稳定版ABI**
   - 实验ABI：开发阶段随时改动，只给内部测试驱动/app使用
   - 稳定ABI：一旦对外发布，改动需要版本大升级，不做破坏性修改

2. 系统调用、用户态可见结构体，一旦标记稳定，**不能随意增删字段、调整对齐**

3. 早期开发阶段，所有用户态ABI默认标记为实验，不要过早冻结

## 五、子系统渐进替换方案（自研专属）

1. 新实现：完全独立文件，实现同一套ops接口；不修改旧子系统代码
2. 增加内核启动参数，选择加载旧实现/新实现
3. 并行测试：同一套测试用例，分别跑新旧实现
4. 逐步灰度：先测试环境默认新实现
5. 全部验证完成，删除旧实现整套代码

> 重点：新旧两套实现**共用同一套契约接口**，上层代码完全不用改动。

## 六、硬件驱动包袱控制

1. HAL：CPU、中断控制器、UART、定时器等，全部抽象成统一ops
2. 废弃硬件驱动：放在单独`drivers/legacy/`目录，默认不编译
3. 不允许为某一块板子，在核心代码加`#ifdef BOARD_XXX`
4. 驱动内部可以hack，但hack不能向上泄露到内核核心

## 七、编码与构建规范

### 1. 慎用#ifdef
- 模块级、板级配置：拆分成不同源文件，Kconfig选择编译哪一组
- 禁止在同一个函数内部大量散布`#ifdef`

### 2. 并发与锁模型，文档先行
- 每一个共享结构体，文档写明：保护锁、是否支持中断上下文调用、引用计数规则
- 新子系统先设计锁模型，写文档，再写代码

### 3. 内核自动化测试（尽早搭建）
- Kunit风格单元测试：对子系统ops单独测试
- 集成测试：中断、进程切换、内存分配、异常
- 回归测试集：每次修改自动跑

### 4. 全局状态最小化
- 尽量把状态封装在子系统实例结构体里；支持多实例
- 少全局，多实例化

## 八、版本管理与废弃策略

1. 废弃标记：API/ops标记`__deprecated`，编译告警
2. 预留迁移窗口：给驱动/应用开发者迁移时间
3. 窗口到期后，直接删除代码；不永久保留兼容分支

## 九、常见踩坑点与对策

| 踩坑点 | 对策 |
|--------|------|
| 为快速跑通demo，在核心代码加临时hack | 任何临时hack必须在注释写死截止日期，到期必须删除或重构 |
| 过早冻结ABI | 早期ABI全部标记实验，明确告知上层随时变动 |
| 一个模块承担太多职责 | 继续拆分子模块，各自通过ops交互 |
| 为适配新硬件，不断在核心路径增加特例判断 | 所有硬件特例下沉HAL/驱动 |

## 十、赫普OS当前状态与改进方向

### 当前状态
- 已有微内核、系统调用、文件系统、TCP/IP协议栈、图形子系统等
- 引导器：HepuBoot（UEFI）+ BIOS引导器（自研）
- 版本号：0.10.5（重要版本.默认版本.bug版本）

### 改进方向（按优先级）
1. **P0**: 完成BIOS引导器启动稳定性修复（保护模式IDE PIO驱动方案A）
2. **P1**: 建立子系统ops接口规范，逐步将现有子系统改造为ops模式
3. **P2**: 建立实验ABI/稳定ABI区分机制，所有用户态ABI默认标记实验
4. **P3**: 搭建内核自动化测试框架（单元测试+集成测试+回归测试）
5. **P4**: 建立废弃API标记与删除流程
6. **P5**: 全局状态最小化改造，将全局变量封装到子系统实例结构体
