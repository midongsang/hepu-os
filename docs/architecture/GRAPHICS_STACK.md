# 第一部分 · 现状快照

## 1.1 现役分层（事实）

```
hs_apps.c     应用内容（终端/文件管理器/任务管理器各自的 render 回调）
hpdesk.c      窗口管理 + 面板 + 合成（单进程，一体化）
gfx64.c       绘图原语 + 前后缓冲 + 裁剪 + 渲染目标 + 合成
hsinput.c     键鼠原始输入
font64.c      字形栅格
```

`ARCHITECTURE_LAYERS.md` 描述的就是这条链路。`GUI.md` 明确标注为 32 位遗留树
（`theme.c`/`widgets.c`/`mobile.c`），**不在 Makefile 里，不是现役实现**。

一句话定性：**单进程一体化，用户三层模型里的方案 1，处于阶段 2 后期** ——
多窗口、Z 序、拖动、焦点、遮挡、脏矩形、离屏合成都已具备；缺的是显示后端抽象
与控件级事件/脏区。

## 1.2 三层模型 × 当前进度

| 层 | 用户方案里的职责 | 现状 | 已落地 / 还缺 |
|---|---|---|---|
| **第一层：显示后端** | 帧缓冲 / GPU / 后端切换 | **缺** | gfx64 有 `front_buffer`/`back_buffer`/`gfx_target` 三个目标，但没有"后端接口"这一层，代码直接操作 LFB。`GRAPHICS.md` 里的 VGA/VBE/virtio 三后端是规划，未落地 |
| **第二层：窗口合成器** | 窗口模型、Z 序、脏区、Surface、合成 | **主体已落地** | 已：`hs_window_t`、Z 序、拖动、脏区框架、统一裁剪、ARGB 合成原语、窗口常驻 surface、面板层表面复用。缺：合成仍是整窗 blend（没有按脏区裁剪的合成）、`opacity`、不透明区域、父子窗口 |
| **第三层：GUI 组件库** | 控件树、布局、事件分发、控件级脏区 | **只有布局** | 已：`hs_ui_box_t` 单遍 arrange→paint。缺：控件级 hit-test（点击仍由 hpdesk 按坐标判定，`hs_ui_hit()` 建好未接）、控件级脏区上报、控件状态与样式 |

**这张表的用途**：避免"以为在补三层，其实只在补第二层"。可视化改造之前的很长一段
工作（脏矩形、Surface、层复用）全部落在第二层；第一层至今是空的。

## 1.3 现在生效的机制（含生效前提）

| 机制 | 生效条件 | 生效范围 | 不生效时 |
|---|---|---|---|
| **光标局部刷新** | 无内容变化、无动画、右键菜单未展开 | 鼠标移动只擦旧光标矩形 + 铺新位置背景 + 前台画光标，128×128 | 走正常重绘 |
| **脏区框架** | 拖动/内容变化时累积 `hs_dirty_add` | 单矩形并集，`hs_s(96)` 外扩覆盖投影 | `g_dirty_x1 < 0` 表示无脏区 |
| **局部帧路径** | 有脏区且 `!g_content_dirty && !animating` | 壁纸只铺脏区 → 面板/CC/通知走层复用 → 窗口 → `present_region` | 走全量路径 |
| **统一裁剪** | 调用方显式 `gfx64_clip_set` | 只作用四个叶子函数：`put_pixel`/`get_pixel`/`fill_rect`/`blend_pixel`；圆角、线、圆、TTF 文字都落到这里 | 无裁剪 |
| **窗口离屏表面** | 每窗口常驻 `surface` | `gfx64_target_begin` + origin 平移，窗口内容全部重定向；合成用 `gfx64_blend_image` | 分配失败自动退回直绘 |
| **窗口内容复用** | `!content_dirty` | 直接 blend 上一帧 surface，跳过 memset + 全部绘制 | 重绘 |
| **面板层复用** | 局部帧且 `L->valid` | 顶栏/灵动岛/Dock/桌面时钟/侧栏/控制中心/通知 各自一块 ARGB 表面，内容不变时直接 blend | 全量帧一律重绘；**天气卡不纳入**（定位字段对不上） |
| **投影预渲染 ARGB 缓冲** | 掩膜指纹（宽/高/圆角/pad/半径/偏移）未变 | `sh_build` 出掩膜后同步生成一块黑底 + alpha 的 ARGB 缓冲 `sh_argb`，每帧一条 `gfx64_blend_image` 批量合成，不再逐像素 `blend_pixel`；窗口内部 alpha=0 | 缓冲分配失败退回解析式投影 |

**内存代价**：窗口 surface ≈ `w*h*4`（典型 690×645 ≈ 1.8MB，只在窗口存活期间）；
面板层表面合计约 1.5MB 量级；投影 ARGB 缓冲 ≈ `(w+2pad)×(h+2pad+off)×4`
（690×645 窗口约 912×870 ≈ 3.17MB，全局单份、随尺寸变化复用，不释放）。

## 1.4 六项统一规范 × 当前状态

| 规范 | 状态 | 证据 / 差距 |
|---|---|---|
| **1. 统一坐标系** | 部分 | 全局物理像素整数坐标，一致。缩放是**每个调用点自己乘** `hs_sx/hs_sy/hs_s`，不是全局变换；窗口**没有"客户区 (0,0)"约定**，各 app 自己算 `win->x + 偏移` |
| **2. 统一事件总线** | 部分 | 窗口级已统一：`hs_window_at()` 按 Z 序命中 → 焦点窗口；键盘单点分发 `hs_apps_handle_key()`。**缺控件级 hit-test**（`hs_ui_hit()` 已建未接）；**缺输入服务层**（无键位映射表、无鼠标加速） |
| **3. 统一渲染原语** | **已统一（含裁剪）** | 上层只调 gfx64，不碰帧缓冲。裁剪已落到四个叶子函数，成为单一来源。**缺**：没有 alpha 语义的统一约定（ARGB 只在窗口/surface 路径成立） |
| **4. 统一窗口模型** | 部分 | `hs_window_t` 有 `x/y/w/h`、`visible`、`focus`、`always_on_top`、`workspace`、`title`、拖动状态、`render` 回调、`surface`、`content_dirty`。**缺**：最小/最大尺寸、`opacity`、不透明区域、父子窗口（弹窗全是顶层浮动） |
| **5. 字体/颜色/资源** | 部分 | 颜色：主题变量 + Material 3 色板 + `config.hsqml` ✓。字体：`font64_draw_string(fb, fw, fh, x, y, ...)` 每次传参，无全局字号/字重管理，**`fb` 参数实际已冗余**（TTF 路径忽略它）。图像：PNG 在各使用点各自解码，无全局图像缓存 |
| **6. DisplayBackend 抽象** | **缺** | 同上表第一层 |

## 1.5 性能总表（同一拖动自测，28 帧，单帧千周期；两轮平均）

| 阶段 | V0.59.16 基线 | V0.59.19 | **V0.59.21 现在** | 本轮 vs V0.59.19 |
|---|---|---|---|---|
| 整帧 | 430295 | 297224 | **159763** | **-46%** |
| 面板 | 77809 | 38166 | 34400 | -10% |
| 控制中心 + 通知 | 145999 | 17986 | 16356 | -9% |
| 窗口 | 171702 | 178274 | **46913** | **-74%** |
| 壁纸（局部重铺） | 21395 | 19477 | 20862 | 持平 |
| present | 12344 | 11892 | 11514 | -3% |

**窗口段构成（V0.59.21 两轮平均）**：投影批量合成 ~32990 + memset ~752 + 内容 ~430
+ 底填充 ~296 + 标题栏 ~32 + 边框 ~16 ≈ ~34500，对 `winK`（45280 / 48545，均值
~46913）留 ~10–14K 缺口。缺口主体是**窗口 surface 合成**（`blendK` ~12.6–12.8K，
它计在 `g_cyc_blend` 而未计入窗口段子项）加 surface 确保（<1K）；扣掉这两笔后残差
**-5.5K ~ +1.4K**，来自分段 `rdtsc` 括号的嵌套与取整（子项计时区间彼此包含），
即子项之和与窗口段总量在**噪声量级**吻合，而不是还藏着一条未发现的热路径。
投影仍是窗口段最大子项（约 70%），但单像素 `blend_pixel` 已换成批量 `blend_image`，
逐帧 blend 量级从 ~120K 降到 ~33K。

## 1.6 剩余开销地图（V0.59.22 实测，含 otherK 口径纠正）

**先说一个统计口径的错，因为它会带着后续优化走错方向。**

`[PROF]` 行里原来的 `otherK` 定义是：

```c
otherK = frameK - renderAllK - presentK;
```

这个减法漏掉了**壁纸、面板、控制中心/通知**这三段 —— 它们不在 `hs_window_render_all()`
的计时区间内，于是全被算进了"其它"。结果 `otherK` 长期显示 **102390**，看起来像有
100K 的不明开销；实际把它拆开，其中约 **69% 是面板与壁纸绘制**，并不是黑盒。

还有第二个坑：不能用 `PROF2` 的累加器（`g_cyc_wall` / `g_cyc_panels` / …）去扣这个差额。
那是「blit 阶段」口径，与 `PROF5` 的 ts 时间段口径差一个量级（`g_cyc_wall` 1814 vs
`PROF5` 的 `wallK` 19118），扣了会得到 74997 这种同样无效的数。

正确做法：拿 `PROF5` 那条时间戳链的总和 `g_ts6` 当作「已测部分」，
`otherK = frameK - segK`。改完之后两项精确相加等于整帧，不再有对不上的余额。

**实测（V0.59.22，28 帧拖拽，单帧千周期）**

`frameK = 158722 = segK 125273 + otherK 33449`

| 段 | 每帧 | 占整帧 |
|---|---|---|
| 窗口段 | 44548 | 28.1% |
| ├ 其中投影 blit | 32752 | 20.6% |
| 面板 | 34273 | 21.6% |
| **真残差 otherK** | **33449** | **21.1%** |
| 壁纸 | 19118 | 12.0% |
| 控制中心 + 通知 | 16100 | 10.1% |
| present | 11218 | 7.1% |
| 顶栏 | 16 | 0.0% |

**读这张表的三个结论**

1. **投影仍是单点最大项**（20.6%，占窗口段的 73.5%）。批量合成已经把量级砍到 1/4，
   但它每帧仍在遍历整块 `mw×mh` 缓冲，只是内部透明像素不再写。要再降只能改成
   「按真实环带形状分条带提交」或复用上一次的结果做偏移拷贝。
2. **面板 21.6% 从头到尾没被碰过**。面板层复用（V0.59.20）解决的是"内容不变时别重画"，
   但拖动帧里面板被判为需要重绘时的实际绘制成本没变。这是下一个可观的整块收益。
3. **真残差 33449（21.1%）还没定位到具体环节**。它包含主循环每轮的 `net64_poll` /
   `dhcp64_poll` / `hs_input_poll` 与两个渲染帧之间的间隙。按 2.5GHz 折算约 13ms/帧，
   占每帧 63ms 的两成 —— 值得再挂三个计时点分开，但在拆开之前**不能假设它是空闲等待
   或可以砍掉的开销**。

计时口径：`[PROF6] shadowBuildK/shadowBlitK/titleK/borderK` 为本轮新增的窗口段子项，
`[PROF5]/[PROF4]/[PROF3]/[PROF2]` 既有格式未动。

# 第二部分 · 演进编年史

状态标记：**✅ 已生效** ｜ **⚠️ 部分生效** ｜ **❌ 已回退** ｜ **❓ 未验证**

### V0.59.4 · 光标局部刷新 ✅

原来 `g_content_dirty` 是 bool，鼠标一动就重画壁纸 + 全部窗口再整帧拷 8MB
（1920×1080×4B）。利用"back_buffer 是干净桌面、光标只叠在 front"做快速路径：
只做擦旧光标 + 铺新背景 + 前台画光标，区域 128×128。
实测 30 次连续移动后暗像素只聚成一个 20×20 连通块，无拖影。

### V0.59.5 · 窗口拖动局部重绘 ✅

新增脏区框架 `hs_dirty_add/rect/reset/hits`（单矩形并集 `g_dirty_x0..y1`）。
拖动并入"旧位置 ∪ 新位置"，各外扩 `hs_s(96)` 覆盖投影。顺带修掉一个死锁：
"没脏区 → 跳帧 → 永远不产生脏区"。
实测 `dirty_region_frames=26/28`，窗口精确右移 280px。

**仍缺（记住）**：内容变化（时钟跳秒、状态刷新、通知弹出）仍标记整帧
（`g_content_dirty` 是 bool）。升级需要各 render 回调上报自己的矩形。

### V0.59.6 · `hs_ui` 布局基类 ⚠️

`hs_ui.h/.c` 提供 `hs_ui_box_t`（矩形 + 内边距 + 子项间距 + 排列方向 +
measure/paint 回调 + `hs_ui_hit()` 命中）。单遍 `arrange → paint`，刻意不做约束求解。
试点 Settings 左侧 5 项导航，扫描线验证间距严格 48，视觉零变化。

**只做了布局，没做事件与脏区上报** —— 这是第三层的半成品。

### V0.59.7 · 拖动内容快照 ❌（后来被 surface 取代并移除）

拖动时从后台缓冲抓一块矩形（`gfx64_back_snapshot/back_restore`），贴回新位置跳过内容重画。
已知副作用：快照四角是抓取那刻的背景，贴到新位置有极小块旧背景。
后来被真正的窗口 surface 取代，代码已移除。

### V0.59.9 · 统一裁剪 ✅

`gfx64_clip_set/disable`，**只作用四个叶子函数**（`put_pixel`/`get_pixel`/`fill_rect`/
`blend_pixel`）；圆角、直线、圆、TTF 文字最终都落到这几个入口，所以上层函数不必各自处理
—— 这是"渲染原语统一"第一次有了单一来源。

确定性别验证：在裁剪生效上下文里从窗口底边往下画 `w->width+120 × 60` 品红条，
截图逐像素扫描（1920×1080 原始 PPM，步长 2）**品红像素 = 0**。

**顺带修掉一个真 bug**：终端 `t_put()` 加新行后没置脏，桌面静止时输出 `dmesg` 后
画面停在旧帧，表现为终端空白。现在末尾调 `hpdesk_mark_dirty()`。

### V0.59.10 · ARGB 合成原语 ✅

`gfx64_blend_image(src, sw, sh, dx, dy, opacity)`：逐像素 alpha、走裁剪，
内存格式 `0xAARRGGBB`。

**为什么必须先在它**：gfx64 原有绘制全是覆盖式实色，没有 alpha 通道。窗口一旦画进
自己的 buffer，圆角外像素就没有"透过"语义 —— 不是脏数据就是黑色。

数值验证：128/255 红块叠到 `0xFAF6EE` 得 `after=0xFC7A76`，三通道与理论吻合。

### V0.59.11 · 窗口 surface ✅

三块改动合起来，窗口第一次真正"画进自己的画布再合成"：

1. **渲染目标上下文** `gfx64_target_begin(buf,w,h,ox,oy)` / `target_end()`：目标指针
   + origin 平移 + 自身 pitch，只作用四个叶子函数 —— 窗口内容（圆角、线、圆、图标、
   AA 文字）全部自动跟随，调用点一行没改。
2. **font64 适配**：`draw_char` 入口检测 surface 模式，改指 surface + 平移坐标。
3. **底色**改用 `gfx64_fill_round_rect_argb()` 写 coverage alpha —— 圆角外真透明。
   旧 `fill_round_rect_aa` 与目标已有内容混色，目标是透明 buffer 时会混出灰边。

**踩过的两个坑**：
- `blend_pixel`/`put_pixel` 在 surface 模式下最初没写 alpha 字节（高字节 0）→ 整块被
  当透明，表现为"窗口按钮和色板圆点消失"。修法：surface 内一律写 `0xFF000000|color`。
- `fill_rounded_rect` 走 vg64 矢量管线，但 vg64 最终落到 `gfx64_blend_pixel`，
  叶子适配后它也跟着适配。

逐点比对（步长 2，窗口区域）差异仅 31 个采样点，集中在右下圆角 1px AA 过渡带。

### V0.59.12 · 窗口级脏标记 ⚠️

`content_dirty` + `hover_rel_x/y` + `hover_inside`。设计意图：鼠标**相对窗口**位置
变了才置脏，绝对位置变化不算，这样拖动帧能命中免重画。

实测 `surface_reuse=16 surface_repaint=38`，但整机拖动帧耗时没下降反而"约 2 倍"。
据此当时判断"瓶颈在整窗 blend"，写下"开销翻倍"的结论 —— **此结论后来被 V0.59.15
的数据推翻**（blend 只占 3%），那个"2 倍"本身也是被主循环阻塞污染的帧率推出来的假象。
见第三部分。

**真正的缺陷（V0.59.19 读代码时才发现）**：拖动时窗口 `x` 每帧 +10 而鼠标不动，
`rx = mouse_x - w->x` 每帧都在变 → 条件恒真 → `content_dirty` 每帧置 1 →
**拖动帧一次都没复用**。设计意图在拖动场景下恰好完全失效。

### V0.59.13 · 计时基础设施 ✅

`hpdesk_render` 拆成 `hpdesk_render_inner` + 计时包装，埋累加器：
`g_cyc_panel`（整帧）、`g_cyc_render_all`、`g_cyc_blend`、`gfx64_prof_present`。
后续每次优化都能直接看增量。

### V0.59.14 · 取证失败记录 ❓

桌面主循环被同步 HTTP 请求阻塞十几秒，渲染到 45 帧（自测触发点）的时间不可控。
试过 8/12/20/22/30/40 秒等待窗口、`-nic none` 与 `-nic user`。串口里
`[GEOM-RENDER] frame=60` 证明渲染确跑到 60 帧，但自测块**一次都没执行**。

**教训**：缺的不是计时能力，是一个**不依赖帧号与启动时序的取证入口**。

### V0.59.15 · 把同步网络请求挪出启动路径 ✅

两处同步 HTTP 卡在启动路径：

1. `drv_mgr_update` → `http64_get`（默认 15 秒），**被调在渲染函数里**。
2. 天气在 `desktop64` 主循环，`wx_tick >= 300` 轮触发。

**根因**：`wx_tick` 数的是主循环轮数不是帧数（一轮约 1ms），300 轮只有约 0.3 秒
—— 所以启动后 0.3 秒就发请求、立刻卡住。之前按注释"300 帧≈5 秒"理解一直是错的。

改动：抽出 `http64_get_timeout`，天气 3 秒/驱动仓 3 秒，调用点加 `g_frame_no > 1800`；
天气改 `wx_tick >= 60000`（约 60 秒墙钟）、只试 1 次。
实测启动后 **10 秒内到 `frame=60`**（改前 20–30 秒），10 秒内无任何网络请求。

### V0.59.19 · 面板层表面 ✅

给每层面板一块常驻 ARGB 表面，局部帧直接 blend 上一帧像素。

**第一次尝试（V0.59.18c）画面被拆散** —— 控制中心只剩右缘一条。当时误判为"绘制
路径没统一（`fb` 直写绕过 gfx64）"，**该判断是错的**：`font64_draw_string` 在 TTF
模式下走 `gfx64_put_string`，本来就在 gfx64 入口上。

逐层推进实测：

|---|---|---|---|
| 整帧 | 430295 | 319244 | **297224（-31%）** |
| 面板 | 77809 | 76151 | 38166 |
| 控制中心+通知 | 145999 | **16051** | 17986 |

**踩到的两个坑**：
1. 空表面复用（上面那条），表现是所有层只剩碎块。
2. **包围盒估错就裁边**：桌面时钟按 `(sh-ch)/2` 估位置，实际是 `ui.clock_x/clock_y`，
   上去后时钟被切掉上半；天气卡按"右上"估，实际在右下。改按 `clock_x/clock_y`
   算之后正常；天气卡字段对不上且收益仅 0.6%，保持直绘。

**教训**：层复用的前提只有一条 —— **包围盒必须与真实绘制区域一致**。估错就是裁边。

# 第三部分 · 已被数据否决的做法（别再试）

| 做法 | 当时的判断 | 否掉它的数据 | 结论 |
|---|---|---|---|
| **"整窗 blend 让开销翻倍"** | V0.59.11 写下"每帧多一次全窗 blend，窗口绘制开销约翻倍" | `blendK=12818`，只占整帧 **3%** | 合成不是瓶颈。那个"2 倍"来自被同步 HTTP 阻塞污染的帧率 |
| **"增量来自整窗 blend + present"** | V0.59.12 推断瓶颈在此 | blend + present 合计 **6%** | 同上，方向性错误 |
| **"脏矩形合成"优化方向** | V0.59.13 据此规划 | 能省的上限就是 3%/6% | 收益无意义，放弃 |
| **面板矩形相交跳过** | 以为按矩形跳过就行 | `77809 → 77505` | 脏区横跨全部面板，粒度不够 |
| **把面板绘制裁到脏区** | 以为能省区外写入 | `77809 → 80913`，**更慢** | 裁剪分支开销大于节省 |
| **"面板绘制 `fb` 直写绕过 gfx64"** | V0.59.18c 判定为画面破碎的根因 | TTF 路径本来就走 `gfx64_put_string` | 判断错误；真因是空表面被复用 |
| **"帧率换算渲染耗时"** | 用"28 帧从 <10s 变 >25s"比较快慢 | 自测期间主循环被 HTTP 阻塞 | 帧率不可用作性能指标，必须用 rdtsc |

**一条通用纪律**：任何"某方案更慢/更快"的结论，必须来自 rdtsc 累加器或逐像素扫描，
不能来自帧率、不能来自缩略图目测。

# 第四部分 · 下一步

V0.59.21a/b/c）。剩余项按优先级：

| # | 动作 | 预期收益 | 风险 |
|---|---|---|---|
| 1 | **投影批量合成再收一轮**：`blend_image` 目前遍历整块 `mw×mh` 缓冲，内部透明像素只省写入；可按四条边带分块合成，或预切环带行/列，去掉内部遍历 | 投影 ~33K 中尚未量化的内部遍历部分 | 低，纯合成路径 |
| 2 | **多浮动窗口投影缓冲**：`sh_argb` 全局单份，不同尺寸窗口切换时指纹抖动重建；评估按窗口缓存或把投影烤进窗口 surface 外扩区（复用帧免费携带） | 多窗拖动场景 | 中，涉及 surface 尺寸/Z 序 |
| 3 | 天气卡定位字段核对（`weather_width/margin_right` 与实际绘制区不符） | 0.6% | 低 |
| 4 | 控件级事件分发 + 控件级脏区上报（第三层） | 结构性的，非即时性能 | 中高 |
| 5 | DisplayBackend 抽象（第一层） | 长期，为 GPU 留口 | 高 |

**本轮未采用的备选**：把投影画进窗口 surface 外扩区一起合成（任务原定的 blend 大头
方向之一）。本轮选了独立 `sh_argb` 离屏缓冲变体 —— 不改 surface 几何、不动 Z 序，
回退面小；外扩区方案列为 #2 候选，需先量化复用帧里投影免费携带 vs surface 扩尺寸
的内存代价。

## 明确不做的事

- 不新建第二套组件库（对齐本项目「一套组件库喂所有自带程序」的原则）；
- 不在 App 里碰 framebuffer（现状已守住这条，靠 gfx64 API）；
- 不为分层把现有 `hpdesk` 拆成独立进程 —— 隔离性收益要到阶段 4 才值得付 IPC 成本；
- 不再做"按矩形跳过"类优化 —— 已在第三部分否决。
